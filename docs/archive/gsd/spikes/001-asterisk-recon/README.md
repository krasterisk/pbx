# Spike 001: Asterisk recon

## What This Validates

Дан живой тестовый Asterisk `ipbx.krasterisk.ru`; опрашиваем его через ARI и AMI → знаем
версию, наличие и состояние `app_confbridge`, доступные видеокодеки, полноту WebRTC-обвязки
и — главное — принимает ли сборка SFU-режим видео.

Спайк дешёвый и стоит первым сознательно: если бы в сборке не было `sfu` или SRTP, спайк 002
из «проверим сетку видео» немедленно превратился бы во «внедряем внешний SFU», а это другая
фаза по объёму.

## Research

Ресёрч внешней документации сделан ещё на discuss (`16-CONTEXT.md` → Canonical References):
`video_mode` включая `sfu` появился в Asterisk 15, профили собираются динамически через
`CONFBRIDGE()`, realtime-бэкенда у ConfBridge нет. Здесь проверяется не документация, а
**конкретная сборка**.

Два канала опроса выбраны намеренно, а не для надёжности: доступность и полнота каждого из них
сама по себе улика для **R-ENGINE**. ConfBridge-ветка живёт на AMI (`Command`, события
`Confbridge*`), ARI-ветка — на REST плюс WebSocket. Спайк меряет обе.

## How to Run

```bash
node .planning/spikes/001-asterisk-recon/recon.js
node .planning/spikes/001-asterisk-recon/probe-webrtc-and-sfu.js
```

Доступы читаются из корневого `.env` (`AMI_*`, `ARI_*`). Отчёты складываются в `results/*.json`.

## What to Expect

Обе команды печатают построчный протокол опроса и сводку. Ожидаемый исход — версия Asterisk,
список загруженных `res_ari_*`, набор видеокодеков, и ответ ARI на попытку создать бридж
`video_sfu`. Ничего на сервере не остаётся: пробный бридж удаляется сразу (`status=204`).

## Investigation Trail

**Итерация 1 — `recon.js`.** ARI и AMI ответили с первой попытки, AMI-пользователь имеет право
`command` (это не было очевидно заранее — без него разведка свелась бы к ARI). Первый прогон
дал `majorVersion: null`: сборка представляется как `Asterisk certified-22.8-cert2`, а регулярка
ждала `Asterisk 22`. Починено, стало `22`.

Вывод `confbridge show profile bridge default_bridge` принёс первый настоящий сигнал: строки
`REMB Send Interval` и `REMB Behavior`. REMB — механизм обратной связи по полосе, осмысленный
только в SFU-раздаче; его наличие в стоковом профиле означало, что код SFU в сборке есть.
Косвенно, поэтому потребовалась вторая итерация с прямым доказательством.

**Итерация 2 — `probe-webrtc-and-sfu.js`.** Первый заход не спросил про WebRTC вообще, а без
SRTP и WebSocket-транспорта браузерный участник невозможен — то есть спайк 002 был бы обречён,
и я бы узнал это, потратив на него день.

Прямое доказательство SFU получено через ARI: `POST /ari/bridges?type=mixing,video_sfu` вернул
`200` и тело с `"video_mode":"sfu"`. Это сильнее, чем вывод про версию: сборка не просто
теоретически умеет SFU по номеру релиза, она приняла запрос и создала такой бридж.

## Results

**Вердикт: VALIDATED.** Площадка пригодна, обе ветки R-ENGINE технически доступны.

### Сборка и движки

| Что | Факт |
|-----|------|
| Версия | `certified-22.8-cert2`, собрана 2026-04-11 |
| `app_confbridge` | загружен, Running |
| SFU | подтверждён прямо: ARI-бридж создан с `video_mode: "sfu"` |
| ARI | доступен; `res_ari_bridges`, `res_ari_channels`, `res_ari_events`, `res_ari_recordings` — все Running |
| AMI | доступен, с правом `Command` |
| Таймер | `timerfd`, тест 50 тиков в секунду проходит ровно — микширование ConfBridge обеспечено |

### WebRTC-обвязка — полная

`res_srtp`, `res_http_websocket`, `res_pjsip_transport_websocket`, `res_rtp_asterisk`, `codec_opus` —
все Running. Транспорт `transport-wss` слушает `0.0.0.0:46782` — **тот же порт, что и ARI**, то есть
встроенный HTTP-сервер Asterisk обслуживает и REST, и WSS; `ASTERISK_WSS_URL` в `.env` указывает
именно туда.

Атрибуты видеоформатов есть для **H.264 и VP8** (`res_format_attr_h264`, `res_format_attr_vp8`).
Кодеки H.261/H.263/H.263+/H.265/MPEG4/VP9 ядру известны, но `res_format_attr_vp9` не собран —
для **D-25** («единый видеокодек фиксирует платформа») реальный выбор сужается до **VP8 или H.264**.

### Находки, которые меняют планирование

1. **Профилей в системе ровно два — `default_bridge` и `default_user`, оба стоковые.** Никакого
   `confbridge.conf` с тенантными профилями на сервере нет. Это подтверждает **D-02** с неожиданной
   стороны: строить нечего не только потому, что так решили, но и потому, что стартовать не с чего.

2. **`default_bridge` имеет `Video Mode: no video`.** Умолчание против нас: комната без явно
   заданного `video_mode` будет без видео. Динамический профиль обязан задавать его явно.

3. **`default_user` имеет `Send Events: false` и `Talk Detect Events: disabled`.** Прямое следствие
   для **D-37** («говорит сейчас») и **D-34** (источник событий): индикатор говорящего не появится
   сам собой — нужен `talk_detection_events` в user-профиле, то есть состав событий комнаты
   определяется теми же динамическими профилями, что и всё остальное. Это ложится в спайк 002.

4. **Сервер маленький: 2 ГБ RAM, свободно ~300 МБ, uptime 475 часов.** Для **R-CAPACITY** (спайк 005)
   это и ограничение, и подарок: предел нащупается быстро. Но нагрузочный спайк на этой машине
   надо согласовывать отдельно — на том же хосте живёт БД (`DB_HOST=ipbx.krasterisk.ru`).

### Что это значит для ворот ресёрча

- **R-VIDEO:** нативный путь открыт — внешний SFU пока не нужен. Остаётся главный вопрос, на который
  разведка не отвечает: даёт ли `sfu` **сетку всех участников** (D-24), а не одного активного. Это спайк 002.
- **R-ENGINE:** обе ветки живы, выбор не сузился. ARI-ветка выглядит чуть сильнее по наблюдаемости
  (события уже раздаются как `ari.*`), ConfBridge-ветка — по готовым функциям (PIN, меню, запись).
  Решается сравнением в спайке 004.
- **R-CAPACITY:** появилась первая рамка — 2 ГБ RAM и `timerfd`.
