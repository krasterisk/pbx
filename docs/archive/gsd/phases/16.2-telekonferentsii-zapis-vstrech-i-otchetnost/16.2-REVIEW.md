# Phase 16.2: Code Review Report

**Reviewed:** 2026-09-16T09:30:00Z

## Narrative Findings (AI reviewer)

## Summary

Reviewed the Phase 16.2 recording spine, moderator start/stop, last-leave persist, play ACL, and CDR/History UI. Start/stop never take a client `recordFile`; AMI `recordFile` is always `path.join(records_base_path, conferenceRecordingRel(...))`; DB stores a relative `{vpbx}/conferences/{room}/{meeting}.wav`; SSE `toConferenceRoomStateDto` exposes only `recording: boolean`; UI copy uses ASCII `-` (no U+2014). Those threat checks hold.

The implementation still ships two correctness/security failures: play **fails open** when a meeting has no stored uniqueids (the default spine join fixture omits `Uniqueid`), and last-leave meeting rows are **CASCADE-deleted** when an ephemeral room is collected. Several lifecycle bugs make the empty-uniqueid path easy to hit.

## Critical Issues

### CR-01: Play ACL fails open when no participant uniqueids are stored

**File:** `packages/backend/src/modules/conferences/conference-recording.service.ts:154-171`
**Issue:** D-30 requires the same access-scope as CDR/voicemail (`CdrService.findByUniqueid` → `ensureCallVisible`). `streamMeeting` only runs that check when `listParticipantUniqueids` returns a non-empty list. Empty list skips the loop and streams the WAV after a tenant `findOne(room)`. `findOne` is any JWT user on the same `vpbx`, not CDR scope.

This is the default path in current code: `beginMeeting` persists `uniqueid` only when AMI sends it; the spine `joinEvt` helper and the “Uniqueid missing → null” unit test treat missing Uniqueid as normal. `startByModerator` can also create a meeting via `beginMeeting(room, vpbx, {})` (WR-02) so the only participant row has `uniqueid = null`. Any tenant user who can guess or list `roomUid`/`meetingUid` then plays the conference without `ensureCallVisible`.

Voicemail `requireVisibleRow` never skips `findByUniqueid` when the service and viewer id exist.

**Fix:** Fail closed. Deny play when there is no visible uniqueid. Optionally also require the stored rel to match the locked form (WR-05).

```typescript
const uniqueids = await this.meetingsService.listParticipantUniqueids(meeting.uid);
if (!viewerUserId || !this.cdrService) {
  throw new NotFoundException('Conference recording not found');
}
let visible = false;
for (const uniqueid of uniqueids) {
  try {
    await this.cdrService.findByUniqueid(vpbx, uniqueid, viewerUserId);
    visible = true;
    break;
  } catch {
    // hidden uniqueid is not a leak
  }
}
if (!visible) {
  throw new NotFoundException('Conference recording not found');
}
```

Also persist `Uniqueid` on every ConfbridgeJoin (and do not create meetings with an empty AMI event — see WR-02) so History/CDR listeners have a row to authorize.

### CR-02: Last-leave journal is destroyed when an ephemeral room is collected

**File:** `packages/backend/src/modules/conferences/conference-state.service.ts:328-330`
**Issue:** On last leave, `applyLeave` fire-and-forgets `collectIfEmpty` and *also* returns `persistLeave`. For `kind === 'ephemeral'`, `collectIfEmpty` calls `roomsService.remove`. Schema FK `fk_conference_meetings_room` is `ON DELETE CASCADE` (`setup-conferences-schema.ts:68-69`), which deletes `conference_meetings` and `conference_meeting_participants`.

Even if `persistLeave` wins the race and writes `ended_at` / `left_at` / `recording_file_rel`, the subsequent room delete wipes those rows. The WAV remains under `records_base_path`, but History and `GET recordings-by-uniqueid` can no longer resolve it — D-33 listen-in-CDR is broken for every recorded ephemeral meeting.

If `remove` wins first, `currentMeeting()` is already gone, `endMeeting` no-ops, and `stopForRoom` may still AMI-stop via in-memory identity. Either order loses the journal.

**Fix:** Persist the meeting *before* collect, and keep meeting/participant rows after the room goes away:

```typescript
this.emit(resolved.roomUid, 'participantLeave');
const persist = this.persistLeave(resolved, channel, evt, emptied);
if (emptied) {
  return persist.then(() => this.invokeCollectIfEmpty(resolved.roomUid));
}
return persist;
```

And change the meetings FK to `ON DELETE RESTRICT` (or `SET NULL` on a nullable `room_uid`) so `collectIfEmpty` must archive or detach meetings before `remove`. Do not CASCADE recordings metadata.

## Warnings

### WR-01: `markParticipantLeft` cannot match on channel

**File:** `packages/backend/src/modules/conferences/conference-meetings.service.ts:105-109`
**Issue:** Leave matching uses `row.channel`, but `ConferenceMeetingParticipant` has no `channel` column (`conference-meeting-participant.model.ts`). The cast always yields `''`. If the leave AMI event has no Uniqueid (same gap as CR-01), `left_at` is never written. Last-leave still calls `endMeeting` when the in-memory room empties, so the meeting can close while every participant looks “still in”.

**Fix:** Persist `channel` (or match `caller_id_num`) on join, and compare that on leave:

```typescript
await this.participants.create({
  // ...
  uniqueid,
  caller_id_num: callerIdNum || null,
  channel: channel || null,
});
// leave:
const rowChannel = String(row.channel ?? '').trim();
const rowCaller = String(row.caller_id_num ?? '').trim();
if (
  (uniqueid && rowUnique === uniqueid) ||
  (channel && rowChannel === channel) ||
  (callerIdNum && rowCaller === callerIdNum)
) {
  await row.update({ left_at: new Date() });
}
```

### WR-02: Moderator start seeds a ghost meeting that never attaches live members

**File:** `packages/backend/src/modules/conferences/conference-recording.service.ts:48-56`
**Issue:** When `currentMeeting` is null but `getRoomIdentity` exists (backend restart mid-call, or state/DB desync), `startByModerator` calls `beginMeeting(roomUid, vpbx, {})`. That inserts a participant with `display_name: 'Participant'`, `uniqueid: null`, `caller_id_num: null`. Live channels already in Asterisk do not re-fire Join, so their uniqueids are never stored. Combined with CR-01, play of that recording skips CDR ACL. Combined with WR-01, nobody gets `left_at`.

**Fix:** Do not `beginMeeting` with an empty AMI event. Require an open meeting created by a real join, or snapshot live members from `ConferenceStateService.getSnapshot` / `getLiveChannelPairs` and persist each with whatever uniqueid/caller you have. Reject start with 409 if there is no live meeting to attach.

### WR-03: `has_recording` / `recording_file_rel` are committed before AMI StartRecord succeeds

**File:** `packages/backend/src/modules/conferences/conference-recording.service.ts:121-141`
**Issue:** `meeting.update({ recording_file_rel, has_recording: true })` runs before `ConfbridgeStartRecord`. A real AMI error (not “already recording”) is rethrown, but the row stays dirty. History shows “Есть запись”, `recordings-by-uniqueid` returns a play path, and `safeConferenceRecordingPath` 404s because the wav was never written. `setRecording(true)` correctly stays after AMI.

**Fix:** Write the rel only after a successful (or already-recording) AMI result; on failure, leave `has_recording` false / `recording_file_rel` null (or revert the update in `catch`).

```typescript
const rel = conferenceRecordingRel(userLike.vpbx_user_uid, room.uid, meeting.uid);
await fs.promises.mkdir(dir, { recursive: true });
try {
  await this.amiService.action({
    action: 'ConfbridgeStartRecord',
    conference,
    recordFile: path.join(base, rel),
  });
} catch (err) {
  const msg = err instanceof Error ? err.message : String(err ?? '');
  if (!/already recording/i.test(msg)) throw err;
}
await meeting.update({ recording_file_rel: rel, has_recording: true });
this.stateService.setRecording(room.uid, true);
```

### WR-04: Leave persist is not serialized with `beginMeeting`

**File:** `packages/backend/src/modules/conferences/conference-meetings.service.ts:63-91` and `conference-state.service.ts:333-361`
**Issue:** Joins are queued per room via `enqueue`. `markParticipantLeft` / `endMeeting` run outside that queue. A ConfbridgeLeave that arrives while the first `beginMeeting` is still in the tail sees `currentMeeting() === null`, skips `left_at`/`ended_at`, then the queued join creates an open meeting and may auto-`startForMeeting` for a room that is already empty. `recordingByRoom` can stay true if the later `stopForRoom` never runs, and the next meeting’s `startForMeeting` no-ops on `snapshot.recording`.

**Fix:** Run `markParticipantLeft` and `endMeeting` through the same `enqueue(roomUid, ...)` tail (or a shared mutex on the room). After a successful last-leave stop, `recordingByRoom.delete(roomUid)` so a stale `true` cannot suppress the next auto-start.

### WR-05: Play trusts stored `recording_file_rel` instead of the locked rel

**File:** `packages/backend/src/modules/conferences/conference-recording.service.ts:174` and `conference-recording-path.util.ts:16-25`
**Issue:** `safeConferenceRecordingPath` correctly rejects empty, `..`, absolute, and drive-letter values (same guards as voicemail). It does **not** require `{vpbx}/conferences/{roomUid}/{meetingUid}.wav`. Any relative path that exists under `records_base_path` is streamed — including another tenant’s conference wav if `recording_file_rel` is ever copied or tampered. Start paths are server-built today, so this is defense-in-depth, not a current HTTP injection.

**Fix:** Resolve only the locked rel:

```typescript
const expected = conferenceRecordingRel(vpbx, roomUid, meetingUid);
const stored = String(meeting.recording_file_rel ?? '');
if (stored !== expected) {
  throw new NotFoundException('Conference recording not found');
}
const filePath = safeConferenceRecordingPath(base, expected);
```

## Info

### IN-01: Meetings list returns the filesystem-relative path to the client

**File:** `packages/backend/src/modules/conferences/conference-meetings.service.ts:141`
**Issue:** `listByRoom` includes `recording_file_rel` (`42/conferences/77/15.wav`). SSE is clean (boolean only). History uses the field only as a play-gate (`Boolean(meeting.recording_file_rel)`) and does not render it as a link, but the RTK payload still leaks the on-disk layout. Not a traversal by itself.

**Fix:** Return `has_recording` (and/or a boolean `playable`) and omit `recording_file_rel` from the DTO. Point History at `has_recording` for the player gate.
