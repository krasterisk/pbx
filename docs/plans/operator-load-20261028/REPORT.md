# Нагрузка: 50 операторов и 150 звонков

Прогон 28 октября 2026, 18:13–18:24 (Красноярск, UTC+7). Версия приложения `4.7.1.3`, исходный коммит стенда `f646e20a`. Стенд поднят из этого репозитория в облачной VM: 4 vCPU, гостевые 16 ГБ, PostgreSQL 16.15, Asterisk `20.6.0` из Ubuntu 24.04, Redis 7, Node 22. Коробка заказчика собирает Asterisk certified 22.8 и PostgreSQL 17; этот прогон их не подменяет.

## Стенд

- Миграции `full-pbx` на пустую базу `krasterisk` применились, `/api/health` ответил `200` за ~2 мс: `schema=0055-phone-sessions.sql`.
- AMI `127.0.0.1:5038` и ARI `ws://127.0.0.1:8088` подключились при старте backend.
- Realtime ODBC читает `ps_endpoints` / `queue_table`. После API созданы 50 операторских номеров `2101–2150` и 50 абонентских `3001–3050`; Asterisk показал 100 endpoint.
- Очередь `q8000_2` (внутренний номер 8000), стратегия `rrmemory`, `maxlen=200`.
- 50 пользователей `op01`–`op50`, уровень OPERATOR. Вход в смену `POST /api/callcenter/agent/login` прошёл у всех 50, интерфейс `PJSIP/e21xx_2`.
- 50 SIP-агентов зарегистрировались и отвечали PCMA. 150 вызовов с `127.0.0.1` входили в контекст `loadtest-in` на номер 8000.
- Frontend Vite `http://127.0.0.1:3010`.

До qualify контакт был `NonQual`, участник очереди — `Unavailable`, и вызов в очередь не распределялся на зарегистрированный SIP. После успешного OPTIONS контакт стал `Avail` (RTT 0.5–3 мс), и очередь начала соединять. В AOR продукта `qualify_frequency` равен 60.

Пока BYE уходил с некорректным заголовком `To`, Asterisk отбрасывал пакет (`PJSIP syntax error` на `To`, колонка 5), каналы оставались в `Queue`/`AppQueue`. После исправления сценария те же 150 вызовов завершились, и `core show channels` вернулся к 0. Утечка каналов в этом прогоне воспроизводилась битым BYE генератора, не штатным завершением.

Один адрес `127.0.0.1`, 80 запросов `GET /api/callcenter/agent/me` сразу после входа: первые 20 ответили `200` за 110 мс на всю пачку, следующие 60 — `429`. Дальше пачка упирается в лимит около 20 запросов в минуту на IP.

## Браузеры

Страница `/login` → `/callcenter/agent` в headless Chromium. Первое место открылось за 11.3 с (холодный Vite), следующие успешные — за 3.5–5.7 с. На каждое открытие пришлось около 80 ответов `/api/` со статусом `200`, один `201` (вход в смену) и один `500`.

`500` на каждом месте — `GET` пропущенных вызовов. Sequelize на PostgreSQL выполняет:

```sql
ORDER BY lastAttemptAt DESC
```

алиас в выборке создан как `"lastAttemptAt"`, а некавыченный `ORDER BY` PostgreSQL приводит к `lastattemptat`. Колонки нет, `CallCenterService.getMissedCallsGrouped` падает. Место в коде: `literal('lastAttemptAt')` в `getMissedCallsGrouped`.

С седьмого места в ответах страницы появился `429`, панель при этом всё ещё дорисовывалась. Успешно дорисованы 10 панелей из попытки открыть 50. На ~10 окнах процессы Chromium занимали около 5.4 ГБ RSS, свободно оставалось около 0.5 ГБ, и набор дальше не наращивался: 50 полноценных Chromium на этой VM не помещаются. Оценка по факту — порядка 500–600 МБ на одно открытое место вместе с обвязкой браузера.

Открытая панель `op01` показала смену «Ожидает звонка», карточки операторов 01–06 и очередь 8000 с 50 свободными. В консоли страницы — предупреждения React о повторяющемся `key` в `Primitive.label` и `Primitive.button`.

Медиа 150 звонков шло через лабораторные SIP-агенты. `res_pjsip_transport_websocket.so` на Asterisk 20.6 не загрузился, в `http.conf` опция `websocket_enabled` проигнорирована. Браузерный софтфон в эти разговоры не входил.

## Что ещё всплыло при старте

- `ModulesRegistryService`: `ALTER TABLE hub_modules MODIFY COLUMN ...` — синтаксис MySQL, на PostgreSQL предупреждение `syntax error at or near "MODIFY"`. Следующий `CREATE TABLE` в том же `try` не выполняется.
- Модель VAD не найдена (`models/silero_vad.onnx`), голосовые роботы без VAD. На этот прогон не влияло.
- Глобальный throttler в коде объявлен как 60 запросов / 60 с (`pbx-core.composition.ts`), модуль auth — 20 / 60 с. Наблюдаемый потолок с одного IP — 20 успешных запросов, дальше `429`. `trust proxy` не включён, поэтому адрес клиента за Vite/nginx для лимитера один на всех.

## Ограничения

Certified Asterisk 22 и PostgreSQL 17 в этой VM не ставились. Запись разговоров, транскодинг и WebRTC-медиа не входили в 150 мостов: кодеки `alaw`/`ulaw`, мост Asterisk, без записи. 50 отдельных Chromium не достигнуты из-за памяти гостя. CPU-профиль ядра Asterisk на пике отдельно не снимался; о живом event loop говорит health 1–3 мс в то же окно.
