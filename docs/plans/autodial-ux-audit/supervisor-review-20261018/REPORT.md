# Супервизорский аудит автообзвона Krasterisk

Это исходный аудиторский срез до реализации. Последующее поручение пользователя на выполнение PLANr2 активно; текущие результаты, оставшиеся gates и границы проверки — в [VERIFICATION](VERIFICATION.md) и [EXECUTION](../EXECUTION.md). Исторические находки ниже не означают, что они остаются без исправления в новой сборке.

18 октября 2026. Проверяемый продукт: **4.7.1.1, 427a5059724f3884e131da4b7bfa09c772f5a2aa, схема 0048**.

Статус: **аудит выполнен с замечаниями**. Зафиксировано 40 пунктов U01–U40, подготовлены рекомендации, предлагаемый план и интерактивный макет. Продуктовый код в этом аудите не менялся. Живые результаты и границы проверки приведены ниже; изолированный LAN-стенд очищен, очистка прежних собственных объектов на недоступном ipbx остаётся pending. Предыдущие реализация и выпуск 4.7.1.1 остаются исторически закрытыми.

## Вывод для руководителя

Рабочее ядро есть: кампания создаётся через мастер, клиентские поля участвуют в озвучивании, preflight проверяет инфраструктуру, обычный звонок сохраняет DTMF и бизнес-исход, отчёты выгружаются. Но интерфейс пока требует понимания внутреннего устройства диалера. Супервизору недостаточно быстро отвечать на пять вопросов: **кого сейчас набираем, почему темп такой, кто требует вмешательства, какой результат получили от клиента и что делать дальше**.

Самые существенные проблемы — противоречащие друг другу редакторы TTS, потеря производной речевой ссылки при переименовании поля, скрытые ошибки озвучивания/сбора ввода, сломанное создание повторной кампании с расписанием и смешение технического «успеха» с бизнес-результатом. Сохранённый клиент не всегда сразу появляется в таблице, основная детализация не показывает клиента, монитор прячет текущую работу под большими карточками. Одинаковые панели и блоки текста имеют примерно одинаковый визуальный вес, хотя их операционная важность различается.

Перестройку предлагаю вокруг **рабочего места супервизора, отдельного рабочего места базы и кампании с понятной целью**. Существующие API, мастера, FSD и shared-компоненты следует сохранить и развить.

## Что именно проверялось

Первый вход выполнен обычным пользователем уровня «супервизор», без подстановки JWT в браузер. На ipbx проверялся `/v4/autodial` — корень сайта обслуживает другое приложение. Создавались только помеченные `SV-AUDIT-20261018` сущности и синтетические клиенты. Вызовы направлялись только на собственные внутренние loopback-номера.

После появления 504 пользователь перенёс оставшиеся проверки на **192.168.2.201**. Существующий экземпляр на порту 3010 имеет версию 4.7.1.0/schema0047, поэтому для сопоставимости подготовлен отдельный экземпляр точного пакета 427a, с отдельными БД и Asterisk, без изменения чужих контейнеров. Ресурсы согласованы с параллельной задачей «CDR отчёт»: автообзвон — префикс `sv-autodial-20261018`, HTTP3181; CDR — отдельный namespace/3182. После экспорта доказательств собственные 9 контейнеров, сеть, runtime-каталог, приватные данные, ключи и локальные помощники удалены;3181/15013 освобождены.

Метод: проход по интерфейсу, реальные запросы и SIP-звонки, сверка результата с данными API/AMI, чтение актуального архитектурного канона и исходников проверяемого релиза. Это экспертная проверка одного оценщика, не исследование на выборке пользователей и не нагрузочная аттестация крупного колл-центра.

Обозначения: **UI/live** — воспроизведено в приложении; **source** — подтверждено устройством кода, но соответствующий отрицательный сценарий ещё не пройден живьём; **рекомендация** — предлагаемое развитие продукта. P1 — мешает верному запуску/операционному решению; P2 — заметная потеря времени и ясности; P3 — последующая полировка.

## Что уже сделано хорошо

- Есть последовательный мастер, черновик и отдельное подтверждение запуска; новая база не стирает уже введённое название кампании.
- Схема базы **уже открывается отдельным модальным окном**, а не редактируется внутри строк клиентов. Проблема смешения теперь в навигации, выборе базы и устройстве самой формы.
- Поддерживаются money/date/enum/boolean, несколько телефонов, нормализация, схема и её ревизия. Есть предпросмотр влияния изменения схемы; его следует развить визуально, а не обходить.
- Предпрослушивание произносит значения клиента, сумма формируется по-русски с валютой. Тестовый звонок ограничен внутренним номером вошедшего пользователя и явно предупреждает о пропущенных переводах/роботах.
- Технический исход и бизнес-исход **хранятся отдельно**. В проверенном звонке `payment_promised` не потерялся из-за короткого разговора.
- Есть серверный preflight, диагностика причины отсутствия набора, SSE, журнал, разрезы, создание базы/черновика из выборки. Запись доступна через разрезы, настройка колонок тоже уже есть в этом представлении — эти функции нужно сделать ближе к основному пути.
- Динамический импорт через API **уже реализован**. Нет оснований планировать второй API с теми же задачами.

## Как должен выглядеть рабочий путь

### Первое открытие `/autodial`

Вверху — выбранная смена/период и часовой пояс. Далее 3KPI: работающие кампании, требующие внимания, результат целей. Один компактный блок проблем с конкретными действиями. Затем список кампаний с целью, состоянием, главным ограничением, клиентами/номерами, текущими линиями, результатом и следующим шагом. Черновик предлагает «Продолжить настройку», исчерпанный тур — «Посмотреть итоги», отсутствие агентов — переход к очереди.

Отдельный «Монитор» отвечает на оперативные вопросы: текущие вызовы, готовность операторов, лимиты и отставание потока. История/долгосрочная эффективность остаются в отчётах; показатели между страницами используют общие определения.

### Рабочее место базы

`Список баз → конкретная база → Клиенты / Поля / Импорты / Интеграции / Стоп-лист`.

Список баз больше не отнимает постоянные 20rem у данных. В заголовке базы — описание, количество клиентов/телефонов, версия схемы, связанные кампании и качество данных. Клиенты — на своей вкладке. Поля — на своей, свёрнутыми карточками с примером значения. Нажатие поля открывает редактор, где первым видны название и смысловой тип; key и переменная автоматически предложены и доступны в дополнительной секции.

Изменение типа/удаление/новая обязательность проходит уже существующий анализ влияния: сколько записей и кампаний затронуто, какие значения не конвертируются, нужен ли default и новая ревизия. Активные вызовы и исторические результаты не должны молча менять смысл.

### Кампания по бизнес-цели

Начальный выбор: «Напомнить о платеже», «Подтвердить приём», «Соединить с оператором», «Опрос» или «Свой сценарий». Шаблон связывает аудиторию, сообщение, ответы клиента, правила следующей попытки и отчётные цели. Технический режим доступен, но человеку объясняется его влияние на нагрузку операторов и риск ожидания.

Нужен сквозной путь: **цель → аудитория → разговор → правила набора → проверка и запуск**. Вложенные модальные окна и одновременное редактирование организационных настроек убрать из этого пути. Черновик можно сохранить на любом шаге; запуск требует полной актуальной сводки.

В сценарии слева расположены шаги и ответвления, справа — выбранный клиент, фактическая фраза и тест. Для узкого экрана это последовательные панели с быстрым переключением. Технический режим диалплана остаётся доступен инженеру.

## Дизайн и вёрстка

Канон: [frontend ARCHITECTURE](../../../../packages/frontend/.idea/ARCHITECTURE.md), [backend ARCHITECTURE](../../../../packages/backend/.idea/ARCHITECTURE.md). Палитра берётся из `design-system.scss → globals.css --color-*`: в тёмной теме графитовые поверхности и cyan-primary, в светлой — её действующие поверхности и indigo-accent; foreground, muted, success/warning/destructive семантические. Токены текущей темы обязательны: отдельную палитру автообзвона и жёстко заданные цвета не вводить.

**Иерархия.** Один PageHeader и один набор основных действий. Числа и главный диагноз видны раньше вспомогательных подсказок. Понятные заголовки секций, короткий контекст под ними. Не строить экран из десятка одинаково крупных Card с абзацами одной важности.

**Объём и акценты.** Использовать уже принятый wash около 5%, тонкую рамку, мягкую тень,3px рейку состояния, числовую табличную сетку и иконку в компактном боксе. Цвет несёт смысл состояния, не украшает каждую строку. Hover на всю активируемую карточку/строку; движение только на подходящем устройстве и с respect reduced-motion. Большие glow на каждой панели только усилят визуальный шум.

**Плотность.** Отступы и радиусы берутся из системы; сокращаются лишние уровни обёрток. Таблица рабочих данных имеет компактный и обычный режим, единый toolbar, закреплённые ключевые колонки. Массовое выделение не создаёт второй конкурирующий баннер. Основные данные не должны зависеть от горизонтального скролла на обычном рабочем экране.

**Формы.** `FormDialogContent`, `ModalBody`, фиксированные header/footer, прокрутка только тела. Повторяющиеся сущности — свёрнутые `ModalSection`/канонические карточки. Дополнительные параметры раскрываются по смыслу. Одинаковые переключатели сохраняются согласно существующему контракту: draft-поле вместе с формой; самостоятельная настройка — optimistic mutation с undo и явной областью действия.

**Адаптивность.** KPI3→2 при 1024→1 при 640; таблицы на телефоне показывают полезные карточки строк. Весь основной экран не должен прокручиваться горизонтально; локальная прокрутка сложной таблицы допускается и заметна. Проверять 320/390/768/1024/1440px, короткое окно по высоте,200%масштаб, клавиатуру, RU/EN и обе темы. Цель — не только отсутствие overflow, но и доступность рабочего действия без длинного обхода списка.

Видимость фокуса при sticky-панелях и достаточные цели нажатия проверять по [W3C: Focus Not Obscured](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum) и [Target Size](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum). Измеренные 16×16 кнопки закрытия сами по себе ещё не доказывают нарушение: стандарт учитывает исключения и интервалы. Для удобства нужен больший интерактивный бокс, не увеличение одной иконки.

Отчётные периоды, активный тур и бизнес-категории должны быть видимыми: [Genesys, Campaigns dashboard](https://help.genesys.cloud/?p=34340) также явно различает период метрик текущего запуска и бизнес-результаты. Это ориентир для терминологии; Krasterisk нужны собственные однозначные определения на своих данных.
