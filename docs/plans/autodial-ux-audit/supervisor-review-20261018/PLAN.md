## Границы и принятые решения

- Развивать существующие FSD/React/RTK/SCSS/shared UI, серверный preflight, версионирование схем, dialplan-editor, импорт и CRM API. Не создавать параллельный API или отдельную визуальную систему.
- Сохранять стабильные UID, машинные коды исходов, значения полей, старые кампании и историю. Внедрять изменение терминологии/метрик явно, с определениями и совместимостью экспорта.
- База — самостоятельное рабочее место. Список клиентов и схема полей — разные вкладки. Общие настройки организации отделены от кампании.
- Основная форма кампании — «цель → аудитория → разговор → правила → проверка». Progressive/Power/Predictive остаются доступны; сложность раскрывается по задаче.
- Безопасный внутренний тест, предпрослушивание, обычный контрольный прогон и запуск всей аудитории имеют разные названия и границы.
- Общие `dialplan-apps`, UI tokens, DTO/контракты/manifest имеют одного назначенного владельца записи. Уже изменённые чужими задачами файлы не перезаписывать. Номер новой миграции согласовать с владельцем schema; 0049/0050 принадлежат CDR и не присваиваются этим планом автоматически.
- Макет — иллюстрация компоновки. Производственная реализация должна использовать действующие shared-компоненты, доступность, локализацию, реальные контракты и состояния.

## S3. Кампания, правила набора и осознанный запуск

**UX12 / U17/U18.** Цель и сквозные шаблоны: должники/приём/уведомление/оператор/опрос. Импортировать существующую кампанию в редактор без изменения сценария. Для общих операторов показывать конкурирующие кампании/распределение, не обещать изоляцию 1:1, которой конфигурация не обеспечивает.

Расписание — зона, дни, календарь и следующая разрешённая попытка в двух временах: кампании и клиента. Сделать 24×7 явным выбором. Учесть ночной переход, DST для IANA зон, пустое окно, просроченное уведомление и DNC.

**UX14 / U08/U09.** Маршрут/CallerID — понятные подписи, статус/ёмкость, источники и fallback, пример для выбранного клиента. Перед запуском показать аудиторию, исключения, maxchannels/темп, операторов, расписание, retry, фразу, цель, ревизию и выполненные тесты. Любое существенное изменение инвалидирует прошлую проверку. Ошибка проверки ведёт к конкретному месту формы.

**UX15 / U09/U24.** Первый запуск отделить от продолжения/повторного тура. Для redial — доступные исходы с количеством затронутых клиентов/номеров, что не перезапустится, какие счётчики сохранятся. Пауза/остановка объясняют судьбу текущих звонков. Список кампаний получает рабочие фильтры, компактную таблицу, сохранённые виды, цель и главное ограничение.

Исходящий маршрут нельзя выбрать случайным добавлением строки. Прерванный мастер восстанавливает свой draft. Неподготовленная/устаревшая конфигурация не запускается.

## S4. Сценарий и проверка разговора

**UX16 / U21.** Сообщение с дружелюбными токенами полей; сохраняется стабильный машинный контракт. Форматы доступны по типу. Денежная сумма, дата и обычный текст не подменяют друг друга. Пустые/неподходящие данные видны до синтеза; есть переход к клиенту/полю. Время HH:mm первоначально можно оставить существующей строкой; новый тип/оператор произношения требует отдельного согласованного backend/shared-контракта.

**UX17 / U22/U03.** Бизнес-исход имеет неизменный код, подпись, категорию и отношение к цели. DTMF-ветви видны в шаге ввода: совпадение, нет ввода, неверный ответ, повтор, следующий шаг. Имя технической переменной генерируется/доступно инженеру. Старые outcomeMap строки продолжают работать с fallback-подписью. Для изменения семантики нужны снимок ревизии/миграция, а не переименование прошлого результата.

**UX18 / U23.** Панель теста рядом: клиент, полученный текст, медиа, стадия звонка, прошедшие шаги, результат/ошибка TTS, DTMF, конец и ограничения. Показать лимит и оставшееся ожидание. Повтор запроса с тем же ключом не порождает второй вызов. Тест переводов/роботов нельзя отмечать успешным, если эти шаги пропущены безопасным внутренним тестом.

**UX19.** Библиотека проверенных разговоров: должники с согласованной проверкой нужного лица и нейтральной ветвью; запись с подтверждением/переносом и сроком актуальности; простое сообщение с событием окончания воспроизведения; оператор с корректным ожиданием/нет агентов. AMD/неизвестная классификация/ошибка синтеза/нет ввода должны иметь явное поведение. Не объявлять DTMF нажатием юридически достоверную идентификацию.

Приёмка: имя+15240.50RUB произносятся корректно; дата и время приёма не заменяются техническими строками;13 секундный звонок с business_outcome не исчезает из бизнес-воронки при пороге 20. Реальный обычный SIP-прогон подтверждает цепочку, которую safe test не проверяет. Изменение схемы поля не оставляет молча сломанный токен.

## S5. Обзор смены и монитор

**UX20 / U10/U17/U30.** Обзор `/autodial`: текущий период/зона,3KPI, приоритетные проблемы, компактные кампании. Монитор: актуальность/соединение, текущие вызовы и нагрузка, затем работающие кампании/причины ограничений. Все historical/stopped/draft карточки не должны занимать верх экрана. Подробность выбранной кампании раскрывается без дублирования всей таблицы.

**UX21 / U24.** Явная модель диагностики: основной blocker, дополнительные ограничения, применённая ревизия, свободные операторы/линии, pending/waiting/active, следующая попытка. Состояние «база обработана» не выглядит как неисправность/вечный набор. Данные SSE и polling согласуются по timestamp; offline/stale отличаются от 0.

**UX22.** Быстрые действия с контекстом: продолжить draft, открыть очередь, исправить TTS/маршрут, пополнить аудиторию, посмотреть итог. AI — вторичное контекстное объяснение на тех же фактах. Ошибка AI не скрывает исходную диагностику и не блокирует ручное управление.

Приёмка: при 50 кампаниях пользователь сразу видит проблемы и активные вызовы; за 10 секунд может определить причину нулевого темпа в подготовленных кейсах «нет операторов / вне окна / DNC / исчерпана база / лимит / ARIoffline». Это критерий приёмки на сценариях с пользователем, не уже измеренный результат текущего аудита.

## S6. Отчёт о клиентах и целях

**UX23 / U03/U26.** Реализовать словарь S0 в вычислениях и UI. Воронка: попытки→ответы→уникальные достигнутые клиенты→нужное лицо(если подтверждается)→цель. Техническое качество отдельно: короткие, ошибки, очередь/брошенные. Определения одинаковы в summary/live/export; период, зона, тур, размер выборки видны.

**UX24 / U04/U27.** Единый инспектор попытки из detail/графиков/клиента: клиентский ID, номер по правам, временная шкала, технический и бизнес-исходы, запись, DTMF, ревизия/данные звонка и следующий шаг. Использовать существующий recording endpoint и drilldown, не создавать второе хранилище аудио. Если записи нет — причина, а не кнопка с неизбежной непонятной ошибкой.

**UX25.** Разрезы и сохранённые представления: бизнес-исход, сегмент, попытка, час, оператор, транк/причина. Фильтры и выбранные колонки в URL/persistedview. «Сделать базу/кампанию по выборке» использует действующий preview_hash и явное подтверждение количества, создаёт только draft. В основной таблице доступны полезные клиентские колонки, не только технические.

**UX26 / U06/U27/U28.** Экспорт повторяет фильтры/зону/период, содержит отдельные client/external_id/attempt/talk/technical/businesscode/label/category поля и provenance. Ясно обозначить CSV«текущая страница» против серверного«весь результат». Ограничения/обрезание выдачи видны. Цвета фиксированы по смыслу исхода и общим tokens, а не по позиции pie.

Приёмка: число подтверждений/обещаний в выбранном периоде воспроизводится кликом до клиента и в выгрузке; прошлый период не смешивается с текущим туром; ошибка API не выглядит пустым отчётом; CSV/XLSX без полного JWT и случайного выхода за scope фильтра.

## S7. Дизайн, доступность и финальные проверки

**UX27.** Привести header/sections/KPI/forms/tables/spacing/statuses к канону. Повторно использовать Stack/Text/TableToolbar/FormDialogContent/ModalBody/ModalSection, feature SCSS modules. Страницы остаются тонкими. Не выносить domain-логику в shared UI ради визуальной унификации. Общие logo/launcher ошибки исправлять совместно с shell владельцем.

**UX28.** Проверить 1440×900/1024/768/390×844/320, короткую высоту,200%масштаб, светлую/тёмную тему, RU/EN, клавиатуру, focus trap/возвратфокуса, screen reader labels, inline errors, видимость sticky footer, scroll affordance, touch цели, reduced-motion. Сравнить с живыми CallCenterSupervisor/SpeechAnalytics и архитектурными эталонами. Скриншот на одном размере не заменяет эти проверки.

**UX29.** Выполнить целевые регрессии и обязательные `npm run lint`, `npm run test:backend`, `npm run test:frontend`, сборку и необходимые schema/API-контракты при их изменении. Отдельно записать unit/mock, integration, реальные SIP/voice, UI и release evidence. Независимую проверку может выполнить только другой разрешённый исполнитель/человек; собственный review не называть независимым.

Финальные живые кейсы: первый вход → правильный deep link; новая база → поле → клиент → CSV → тот же external_id через API; должники → TTS/DTMF → цель; приём → дата/время → подтверждение/перенос; занято/нет ответа → повтор; DNC → исключение; нет операторов → понятная причина блокировки; pause/resume/stop; короткий разговор с достигнутой целью; недоступный TTS/ARI/AMI; отозванный ключ/revision/idempotency; экспорт/запись; корректное завершение и очистка.

## Где выполнять изменения

Основные области: `features/autodial/ui/{BasesList,BaseFormModal,ContactsGrid,ContactFormModal,ImportWizard,CampaignCreationWizard,CampaignFormModal,CampaignWorkspace,MonitorBoard,ReportsView}` и `model/lib`; страницы `Autodial*Page`; `shared/api/endpoints/autodialApi.ts`; backend `modules/autodial`, `autodial-integration`, ограниченные providers/bridge adapters; sharedautodialcontracts.

Общие области с отдельным владельцем: `features/dialplan-apps`, shell/auth, tokens/shared UI, миграционный manifest. Перед каждым срезом сверить текущий dirty baseline. Существующие AI/CDR изменения не включать попутно в UX коммит. Тестовые стенды/контейнеры/номера должны быть изолированы и согласованы между задачами.

## Когда считать результат принятым

1. Все P1 имеют исправление и воспроизводимое доказательство; технический результат и цель клиента не путаются.
2. Супервизор может подготовить/импортировать базу, проверить разговор и запустить понятный объём без знания служебных UID/переменных и вычисления секунд/часовых смещений.
3. Монитор объясняет состояние и действие; отчёт позволяет найти клиента и подтвердить цифру выгрузкой/попыткой.
4. UI согласован с каноном на всех согласованных размерах и темах; общие компоненты не регрессировали в других модулях.
5. Automated/integration/live/release gates отмечены отдельно; неподтверждённые режимы не объявлены проверенными. Тестовые сущности/вызовы/секреты очищены, сохранены только нужные обезличенные evidence.

Начинать реализацию рекомендуется с **S0→S1→UX08/UX09**: это устраняет ложные сообщения и непосредственно решает замечание о смешении полей с клиентской базой. После этого можно последовательно принимать вертикальные сценарии S3–S6.
