# D6-LIVE contract — implementation planning, 2026-10-11

Coordinator: /root; codex-direct; assigned PLAN r2 / D6. This document is a read-only implementation contract, not another execution plan. No calls, deployments, external writes or source changes were made during this investigation. The coordinator assigns subsequent writers and gates.

## Isolation and actual dashboard

Use a separate Asterisk process with an alternate `-C` configuration and UUID-owned etc/run/log/spool directories. Bind AMI, ARI/HTTP, PJSIP and RTP to loopback with distinct ports. The existing production Asterisk, its realtime database, global CEL setting, dialplan and ARI applications remain outside the lab. The actual host capability report confirms the binary and alternate-config/foreground flags exist; CEL is currently disabled on the existing instance, whereas cdr_custom, cel_custom and core PJSIP/ARI modules are available. Missing chan_local/app_answer/app_wait files do not by themselves mean the built-in Local/Answer/Wait applications are unavailable.

The lab receives two numeric tenant IDs allocated only in a fresh test SQL database, never tenants copied from production. Endpoint names must follow existing protocol: `e101_<uid>`, `e102_<uid>`, optional `ew101_<uid>`, and a trunk-like peer `t_lab_<uid>`. Exact tenant contexts are `sip-in<uid>` / `sip-out<uid>` or suffixes beginning `-` / `_`. Set inherited `VPBX_USER_UID` plus the real CDR tenant field in the dialplan. Local helper contexts can carry tenant suffixes, but each visible logical call needs an actual PJSIP leg: current collector intentionally omits Local-only groups. Technical Local/ExternalMedia legs join only an unambiguous tenant+linkedid group.

Start a small Nest sidecar using the actual DashboardController, DashboardService, DashboardAccessService, DashboardGateway, DashboardCollectorService, DashboardProjectionService, DashboardReadStore and DashboardCacheService. Use actual AmiService against the isolated AMI; do not replace collector data or projection with fixtures. Build a narrow provider module rather than importing the full application graph, which can start unrelated telephony/worker services. AmiService's old gateway sink can be omitted from exposed namespaces; `/pbx-dashboard` must be the actual new authenticated gateway. The source requires Node ID alignment between collector, projection and persisted state.

Use fresh canonical SQL schema including migration0033. Register actual Sequelize models and actual ModulesRegistryService/ProductAccessService for catalog access. Seed test-owned users, roles, numbers, tenant bindings, hub modules/pages and grants. The fixture must supply numeric UserLevel (admin1, operator2, supervisor3, readonly5), users.uniqueid/sub and vpbx_user_uid, tenant.id distinct from tenant.vpbx_user_uid, plus timezone. Use an admin and two scoped users with overlapping extension visibility; a second tenant verifies isolation. Base dashboard/cdr/endpoints/trunks catalog pages must be active. Box settings and cloud tenant_modules require their actual pages and cabinet configuration.

HTTP must keep the actual JwtAuthGuard/JwtStrategy and Access.resolve database checks. A freshly signed test JWT can be issued by the harness; this is explicit fixture identity, not a tested production login. Socket token uses issuer `krasterisk-v4`, audience `krasterisk-v4-client`, and the same sidecar secret. Set `/api` prefix. Serve the actual frontend build and proxy API/socket on the same origin, without route interception or baked responses. Full login/authentication UI acceptance is a separate gate if the sidecar does not run the actual AuthController.

Cloud tariff/balance/limits can be test configuration rows in the isolated SQL; use actual tenant.id billing binding. Exporter is an actual host source and remains separately labelled from fixture cloud data. None of these fixture rows prove live billing or enforcement.

## Generated CDR/CEL ingestion contract

Enable real CDR/CEL in the isolated instance only and write UUID-owned cdr_custom/cel_custom CSV files. Tail complete CSV records and insert them idempotently into the sidecar SQL source tables; then let the ordinary background projection discover and classify them. Preserve raw files and hashes. An ingestion adapter may allocate surrogate integer IDs but must not fabricate timestamps, dispositions, linkedids, tenant attribution or AI playback evidence.

Required CDR columns: numeric monotonic `id`, `calldate`, `src`, `usrc`, `dst`, `dialednum`, `dcontext`, `channel`, `dstchannel`, `lastapp`, `lastdata`, `duration`, `billsec`, `disposition`, `uniqueid`, `linkedid`, `userfield`, `vpbx_user_uid`. `clid` and recording references are useful provenance. Empty linkedid stays empty; projection falls back to uniqueid. For naive dates explicitly configure DASHBOARD_CDR_TIMEZONE to the isolated Asterisk timezone; prefer UTC. Do not substitute ingestion time for call time.

Required CEL columns: numeric monotonic `id`, `eventtime`, `eventtype`, `uniqueid`, `linkedid`, `channame`. Preserve `cid_num`, `exten`, `context`, `appname`, `appdata` for diagnostic evidence. Capture ANSWER, BRIDGE_ENTER, BRIDGE_EXIT, APP_START/APP_END, HANGUP, CHAN_END and LINKEDID_END. Terminal proof needs uniqueid or exact channame matching an owned CDR leg; shared linkedid alone is deliberately insufficient. Source CSV rows, AMI events and source SQL rows must retain the same identifiers.

A finalized CDR leg is not logical completion. Persisted fresh complete calls snapshots or owned CEL LINKEDID_END finalize the logical call. During ongoing IVR/human/AI phases, projected outcomes remain active and history aggregates exclude them. After the last channel ends, ordinary pending replay must correct the same call without requiring another CDR. Test both CEL completion and delayed/absent CEL with fresh live absence; wait for normal scheduler/cache cadence, not handcrafted final markers. A stale or older live snapshot must leave an unproved result unknown.

## Actual SIP/media scenarios

The existing `harness/environment/asterisk.ts` Originate helper resolves when AMI accepts the action, not when a call answers. Existing realtime tests can return without asserting unavailable Asterisk; the new required gate must fail clearly when the configured lab cannot run. `sip-probe.cjs` is OPTIONS/auth reconnaissance and `sip-probe-srtp.cjs` stops after SDP offer/answer, with `srtpMediaDecrypted:false`; neither proves a completed conversation. The host has no sipp/pjsua, so the assigned minimal UDP UA runner must complete INVITE/180/200/ACK/BYE, handle retransmissions/CANCEL/OPTIONS, and exchange actual PCMU/PCMA RTP with packet evidence.

| Scenario | Actual call fixture | Dashboard evidence |
|---|---|---|
| Ringing inbound | t_lab caller to e101, delay its answer at least10s | one active/ringing logical call, no history finality |
| Human answer | e101 sends200, ACK and bidirectional RTP; hold at least10s | active/talking, then one accepted incoming; source CDR/CEL identifiers agree |
| Missed inbound | same trunk to e102, only180 until Dial timeout or caller CANCEL | missed/noAnswer after completion; zero accepted |
| IVR | trunk to Answer/Background or Playback/WaitExten without staff Dial | active waiting; completed missed/ivr, never accepted from IVR Answer |
| Voicemail | trunk to actual VoiceMail with a test mailbox and test-only spool | missed/voicemail; actual app/recording evidence |
| Transfer | actual bridge e101 to e102 via controlled redirect/transfer retaining linkedid | one logical call, accepted, both authorized participants; actual REFER transfer is a separate stronger gate if only dialplan transfer is used |
| Internal | e101 actually calls e102 | internal count once; do not prelabel as inbound with trunk/context metadata |
| Outbound | e101 dials t_lab remote UA | outgoing ringing before remote answer, then talking; timeout must not count originating caller ANSWER as successful destination answer |
| Autodial | actual outbound call in test autodial context plus userfield tag | origin autodial and direction out; this tests dashboard attribution, not full production campaign scheduler unless actual originator is included |
| AI negative | real Stasis/session with no successful speech playback, or unavailable provider | unknown/aiPlaybackUnconfirmed after completion; no fake accepted/talking |
| AI to human | actual legacy robot workflow transfers to e101, which answers with media | one logical call accepted by human; AI presence retained |

Capture each phase long enough for5s publication and30s channel reconciliation. Current collector does not consume AMI Newexten, so short technical application transitions may only appear in history/CEL unless real events expose a supported waiting state. This is a concrete source handling gap to assess with recorded events, not a reason to inject application fields into AMI.

## Confirmed runtime limits and targeted observations

- asterisk-manager lowercases header names and event-emitter names. Bulk source reports confirm EndpointList fields objectname/devicestate, ContactList endpoint/status/expirationtime/uri, and OutboundRegistrationDetail endpoint/status. Record active CoreShowChannel fields on the lab; the previous actual source check had zero active channels, so it cannot establish populated channel protocol compatibility.
- Classifier currently recognizes technical completion only from CDR lastapp (Playback/Background/Read/WaitExten/IVR/VoiceMail); evidenceBatch does not read CEL appname. Actual CDR final lastapp can be a later application. The lab must preserve raw lastapp and app event sequence and report any IVR/voicemail unknown instead of expected missed; a source correction should follow actual evidence.
- CEL human evidence currently accepts ANSWER or BRIDGE_ENTER on any tenant human e/ew channel. A genuine outgoing caller can answer before its remote destination. A missed outgoing test must determine whether caller-only ANSWER causes false accepted; accepted destination requires stronger evidence if this occurs. Do not avoid the case by omitting actual CEL ANSWER rows.
- Live origin is currently autodial only when the first selected PJSIP context includes autodial; history also recognizes ac_campaign/userfield. Record the actual originating runtime channel context rather than renaming it solely to obtain a green test.
- v2 AiVoiceModule supplies admission/configuration, with capabilities realtime:false/externalSip:false. AiVoiceService.admit persists an admitted session but does not run a live ARI/media loop or create played turns. Search of production backend confirms no writer of played_until_ms. SQL model correctly maps tenant_uid to vpbx_user_uid; there is no column mismatch. Pure turn coordinator/PSTN emulator cannot prove live AI acceptance.
- Legacy VoiceRobotsService does wire real ARI StasisStart/ExternalMedia and RTP/STT/TTS. Its recognized_text journal precedes actions, and ai_response can follow swallowed playback failures; dashboard correctly treats it as presence only. Real legacy speech can be verified by RTP/recording and provider evidence, but current dashboard cannot prove accepted AI from that journal. Accepted v2 AI gate needs an adjacent owner to supply an actual runtime producer of positive playback evidence; never seed played_until_ms for this live gate.
- Current legacy TTS factory supports Yandex, not arbitrary custom/local TTS. STT supports Yandex/custom HTTP. Existing provider credentials/model service availability is unverified in read-only host reports. Plain Playback or a deterministic mock transcription must not be called a tested working AI session.
