# Контакт-центр: аналитика, панели, отчётность — оценка и план

Статус: draft (анализ + план), решения R1–R8 приняты 2026-10-15 (раздел 6), открытых нет; не назначен исполнителю. Режим по умолчанию — `codex-direct`; перед стартом зарегистрировать в `docs/plans/EXECUTION-REGISTRY.md` у владельца реестра.

Точка зрения: руководитель / супервизор крупного контакт-центра (100–500 операторов, 10+ очередей, смены 24/7) и маркетолог, которому нужны лиды, источники и потери.

---

## 1. Что я хочу видеть (критерии)

| Роль | Главный вопрос | Горизонт |
|---|---|---|
| Супервизор смены | «Где горит прямо сейчас и что нажать?» | секунды |
| Руководитель КЦ | «Держим ли сервис и почему просели?» | интервал 15/30 мин, день, неделя |
| Тимлид | «Кто из моих операторов тянет вниз и чем помочь?» | день, неделя |
| Маркетолог | «Сколько обращений принёс каждый канал, сколько потеряли, сколько сконвертировали?» | день, неделя, месяц |
| Оператор | «Как я работаю относительно цели?» | смена |

Критерии:

1. **Цифры совпадают везде.** SLA на стене, в панели супервизора, в отчёте и в рассылке — одно число по одной формуле. Рестарт сервера не меняет цифры.
2. **Сначала исключения.** Не 200 карточек, а список «требует внимания» с действием в один клик.
3. **Время ожидания видно всегда.** Самый долгий ожидающий в очереди — главный показатель смены.
4. **Интервальный отчёт (15/30 мин)** — основа планирования, без него нет WFM.
5. **Имена, а не `PJSIP/e110_0`.** Длительности в `мм:сс`, заголовки на русском, часовой пояс тенанта.
6. **Drill-down до записи.** Цифра → список звонков → карточка → запись → оценка качества.
7. **Результат звонка — структурированный.** Без кодов результата нет ни маркетинга, ни конверсии.
8. **Сравнение периодов.** Каждое KPI показывает изменение к прошлому периоду и к той же неделе.

## 2. Оценка текущей реализации

| `/callcenter/supervisor` | 6/10 | Есть живые статусы, время в статусе, вмешательство (spy/whisper/barge, принудительная пауза, перевод, сброс), watchlist, фильтр очередей, KPI «сейчас / за день». Нет времени ожидания звонков, нет ленты исключений, нет команд, мало метрик по очередям. |

| Маркетинг | 1/10 | Нет источников (DID → канал), нет кодов результата, нет уникальных/повторных, нет «потерян → перезвонили → продали». |

### 2.2 Проблемы корректности данных (блокируют доверие к цифрам)

Это первое, что увидит руководитель: «на стене 85%, в отчёте 71%, после обеда стало 64%». Исправлять до любой новой визуализации.

| # | Проблема | Где | Эффект |
|---|---|---|---|
| D1 | Каждый RNA (оператор не взял) пишется в `cc_queue_calls` строкой `disposition='timeout'` с именем очереди. `restoreToday()` прогоняет все строки через `accumulateQueueRow`, а `timeout` считается abandoned. Живой путь RNA в offered не добавляет. | `callcenter-ami.service.ts` (~1062), `callcenter-metrics.service.ts` `restoreToday` / `isAbandonedDisposition` | После рестарта бэкенда «Поступило» и «Потеряно» в очередях завышаются, SLA проседает скачком. Алерты могут сработать ложно. |
| D2 | Личные/исходящие звонки пишутся с `queue_name='direct:<iface>'` и тоже попадают в очередные аккумуляторы при restore и в `queue-summary`. | `callcenter-ami.service.ts` (~1601), `callcenter-reports.service.ts` `getQueueSummary`, `callcenter-rollup.service.ts` | В отчёте по очередям появляются псевдо-очереди `direct:PJSIP/...`; `getTenantQueueMetrics` (алерты) видит их как очереди. |
| D3 | В отчёте `queue-summary` и rollup `totalCalls` считает все строки, включая RNA-попытки. | `getQueueSummary`, `recomputeDay` | Один звонок, который прозвонил 3 операторов, = 4 «поступивших». SLA и ASR занижены. |
| D4 | `transferred` в живых метриках — отвечен, в отчётах и rollup — нет. | `isAnsweredDisposition` против `disposition === 'answered'` | Расхождение отвечено/SLA между панелью и отчётом. |
| D5 | AHT: raw = (talk + wrapup) / answered, rollup = talk / answered; rollup SLA по фиксированным 20 с, а не по `servicelevel` очереди. | `callcenter-reports.service.ts`, `callcenter-rollup.service.ts` | Отчёт за 91+ день показывает другой AHT и SLA, чем за 90. |
| D6 | Часовой пояс: даты отчётов парсятся как UTC, `toDateOnly` и heatmap — по локали сервера, `PbxDashboard` — по timezone тенанта. | `parseAndClampPeriod`, `getHourlyHeatmap`, `toDateOnly` | Для UTC+7 «сегодня» в отчёте сдвинуто на 7 часов, heatmap по часам смещён. |
| D7 | Wallboard: SLA = простое среднее по очередям (пустая очередь = 0%), пороги `sla_critical_pct=70` захардкожены; у супервизора — взвешенный SLA и порог 80% из настроек. | `CallCenterWallboardPage.tsx` | На стене и у супервизора разные SLA и разные цвета. |
| D8 | `operator-stats`: `total_pause_time` / `total_idle_time` сессии суммируются целиком, без обрезки по периоду. | `aggregateSessionTime` | Пауза за «сегодня» включает вчерашнюю часть ночной смены. |
| D9 | `idleSeconds` не восстанавливается после рестарта → Occupancy врёт до конца дня. | `restoreToday` (комментарий в коде) | Occupancy в карточке оператора ненадёжен. |
| D10 | Короткие сбросы (абонент повесил трубку за 3–5 с) считаются потерянными. | метрики, отчёты | Abandon% завышен; в индустрии short abandon обычно исключают (настраивается). |
| D11 | Спарклайн «Агенты» рисует ряд свободных агентов. | `SupervisorKpiStrip.tsx` (`totalAgents.spark`) | Мелкий визуальный баг. |

### 2.3 UX-пробелы супервизора (`CallCenterSupervisorPage.tsx`)

- **Live Calls** — колонки `#`, абонент, очередь, статус, оператор, действия. **Нет времени ожидания / разговора**, нет сортировки по самому долгому ожиданию, нет признаков VIP / повторный звонок.
- **Очереди** — ожидают, говорят, агенты, SLA, отвечено, потеряно. Нет самого долгого ожидания (live), ASA, AHT, Abandon %, «нужно агентов». `avgWait/avgTalk` есть в `IQueueStats`, но не показаны.
- **Нет ленты исключений**: пауза дольше `max_duration` причины, затянутый wrap-up, серия RNA, разговор дольше 2×AHT, оператор выпал из очередей (`queuesDetached`) — всё это есть в данных, но не поднимается наверх.
- Алерты уходят только во внешние каналы (Telegram/email/webhook) раз в 30 с; в самой панели нет баннера и звука (`alert_sound_enabled` хранится, но не используется).
- Нет **команд/групп** с тимлидом — только личный watchlist. На 200 операторах сетка карточек неуправляема: нет компактного режима, группировки, сортировки по времени в статусе, поиска.
- Нет **внутридневного графика** (поступило / отвечено / потеряно по 15–30 мин + SLA нарастающим итогом) — главного инструмента «почему просели в 11:30».

### 2.4 UX-пробелы отчётов (`CallCenterReportsPage.tsx`)

- 7 отчётов как сырые таблицы; заголовки колонок приходят с бэкенда на английском; операторы — `agentInterface` и числовой `User ID`; секунды без форматирования.
- Фильтр оператора — **текстовое поле для ввода интерфейса** (`PJSIP/e110_0`); очередь — техническое имя.
- Нет графиков (кроме heatmap объёма), нет сравнения с прошлым периодом, нет интервалов 15/30 мин, нет пресетов периода.
- Нет drill-down: из строки очереди нельзя открыть звонки, из звонка — карточку и запись.
- Нет scorecard оператора (AHT, ACW, hold, occupancy, паузы по причинам, RNA, переводы, качество).
- Нет анализа потерь: в какую секунду бросают, на какой позиции, сколько потерянных перезвонили и как быстро.
- Записи разговоров доступны только в CDR и речевой аналитике; КЦ-история и отчёты их не открывают.

### 2.5 Что уже есть и на чём строить

- Таблицы: `cc_queue_calls` (direction, disposition, wait/talk/hold/wrapup, transfer_destination, position), `cc_agent_events`, `cc_agent_sessions`, `cc_missed_calls`, `cc_daily_queue_stats`, `cc_daily_agent_stats`, `cc_card_data` (JSON значений карточки по `call_uniqueid`), callback requests.
- In-memory движок метрик с формулами SLA/ASR/ASA/AHT/Abandon/Occupancy, бизнес-день (EOD) через `shift_policy`.
- SSE для панели и wallboard, display-токены для ТВ.
- Расписания отчётов с доставкой в каналы уведомлений.
- Речевая аналитика: оценки по шкалам, sentiment, темы, рейтинг операторов (но без связи с очередью и `call_uniqueid` в агрегатах).
- Автообзвон: contact rate, RPC, ASR, AHT, penetration.
- `PbxDashboard`: зрелый паттерн «карточка KPI → drill sheet → список звонков», выбор периода, timezone тенанта, источник данных и его свежесть. Переиспользовать этот паттерн для КЦ.

## 3. Целевая картина

### 3.1 Словарь метрик (один для всех экранов)

Хранить в `packages/shared` (тип + описание + формула), использовать в live-движке, отчётах, rollup, wallboard и подсказках UI.

| Метрика | Формула (по умолчанию, настраивается в тенанте) |
|---|---|
| Offered (поступило) | уникальные `call_uniqueid` в очереди; RNA-попытки не считаются |
| Handled (обслужено) | answered + transferred (после ответа) |
| Abandoned (потеряно) | caller abandon после `short_abandon_sec` |
| Short abandon | abandon ≤ `short_abandon_sec` (по умолчанию 5 с), показывается отдельно |
| SLA % | handled в пределах `servicelevel` очереди / (offered − short abandons) |
| ASA | Σ wait handled / handled |
| AHT | (talk + wrapup) / handled; `talk` уже включает удержание (hold — справочная доля, не прибавляется) |
| Longest wait (live) | max(now − enter_time) по ожидающим |
| Occupancy | (talk + wrapup) / (talk + wrapup + ready); `talk` включает hold |
| Utilization | (talk + wrapup) / logged-in |
| Shrinkage (факт) | pause / logged-in, с разбивкой оплачиваемые / нет |
| RNA rate | RNA-попытки / предложения оператору |
| Transfer rate | transferred / handled |
| Repeat contact (FCR-прокси) | тот же номер повторно в течение 24 ч / 72 ч / 7 дн |
| Callback recovery | потерянные, до которых дозвонились за 15 / 60 мин / день |
| Conversion | звонки с результатом `success=true` / handled |

### 3.2 Экраны

1. **Дашборд КЦ (`/callcenter/dashboard`)** — отдельный управленческий обзор за период: сервис, нагрузка, очереди, команды, потери, паузы, результаты, качество; вкладка «Маркетинг». Не путать с `PbxDashboard` (админ АТС).
2. **Супервизор (live cockpit)** — исключения + очереди + интервальный график + доска агентов.
3. **Отчёты 2.0** — каталог по вопросам, а не по таблицам; KPI-шапка, график, таблица, drill-down.
4. **Wallboard** — тот же словарь метрик, пороги из настроек, вариант на очередь/команду.
5. **Оператор** — личные KPI и цели.

Разделение ролей экранов:

| Экран | Вопрос | Горизонт | Действия |
|---|---|---|---|
| Дашборд КЦ | «Как работает КЦ и где просели?» | сегодня / вчера / неделя / месяц, сравнение | только переходы (drill-down) |
| Супервизор | «Что горит прямо сейчас?» | секунды | вмешательство: пауза, spy, перевод, сброс |
| Отчёты | «Почему и кто конкретно?» | любой период, интервалы | фильтры, экспорт, рассылки |
| Wallboard | «Общий статус для зала» | сейчас + день | нет |
| `PbxDashboard` (`/`) | «Жива ли АТС?» (админ) | сейчас + период | технический drill-down |

## 4. План реализации

Порядок жёсткий: фаза A — условие для всех остальных. B и C можно вести параллельно после A (разные владельцы файлов). E (дашборд КЦ) стартует после A и C1; его секции, зависящие от D, включаются по мере готовности D. F — после B/C.

### Фаза A — «Одна правда»: контракт метрик и исправление данных (P0)

Цель: любые два экрана показывают одинаковые числа; рестарт ничего не меняет.

| ID | Задача | Файлы (владелец записи — один исполнитель фазы) |
|---|---|---|
| A1 | Словарь метрик и чистые функции расчёта в `packages/shared` (тип `CcMetricId`, формулы, единицы, описание для tooltip). | `packages/shared/src/callcenter-metrics/*` (новый) |
| A2 | Разделить «звонок» и «попытку предложения»: RNA писать в отдельную таблицу `cc_agent_offers`, не в `cc_queue_calls`; `rebuildSinceLoginFromHistory` читает пропуски оттуда. Перенос старых строк не делается (R6). | `callcenter-ami.service.ts`, `callcenter-history-writer.service.ts`, `callcenter-metrics.service.ts`, миграция схемы (новая таблица), новая модель |
| A3 | Очередные агрегаты (live restore, reports, rollup, alerts) берут только `direction='inbound'` и настоящие очереди; `direct:*` — в отдельный поток «личные/исходящие». | `callcenter-metrics.service.ts`, `callcenter-reports.service.ts`, `callcenter-rollup.service.ts`, `callcenter-alert.service.ts` |
| A4 | Единые правила handled/abandoned/short abandon/SLA/AHT во всех трёх местах через функции из A1. Abandoned в знаменателе SLA (R1); настройка тенанта `short_abandon_sec`, по умолчанию 5 (R2). | те же + `cc-settings.model.ts`, `callcenter-settings.dto.ts`, `AlertThresholdsForm` |
| A5 | Часовой пояс тенанта во всех отчётах, heatmap, rollup (день = бизнес-день тенанта). | `callcenter-reports.service.ts`, `callcenter-rollup.service.ts`, `kpi-reporting-window.util.ts` |
| A6 | Rollup: per-queue `servicelevel`, сохранять суммы (не средние), добавить hold/wrapup, handled, short abandon; ночной пересчёт + пересчёт по запросу. | `callcenter-rollup.service.ts`, модели daily stats, миграция |
| A7 | Обрезка сессий/пауз по периоду; восстановление ready-времени из `cc_agent_events` для occupancy. | `aggregateSessionTime`, `restoreToday` |
| A8 | Wallboard и KPI strip супервизора на общих функциях; пороги из `cc_settings` передавать в display-token SSE (только пороги, без чувствительных настроек). Исправить спарклайн «Агенты». | `CallCenterWallboardPage.tsx`, `SupervisorKpiStrip.tsx`, `supervisorKpiRollup.ts`, `callcenter-wallboard.controller.ts` |

Приёмка:
- Golden-набор (фикстура `cc_queue_calls` + events на один день, включая RNA, transfer, short abandon, ночную смену, UTC+7) → одинаковые SLA/ASA/AHT/Abandon в live restore, `queue-summary` raw, rollup и wallboard. Unit-тесты на каждую формулу.
- Тест: «записали N звонков → restoreToday → метрики равны живым до рестарта».
- В `queue-summary` нет `direct:*`.

### Фаза B — Live cockpit супервизора (P1)

Цель: супервизор за 10 секунд видит, где проблема, и решает её в один клик.

| ID | Задача |
|---|---|
| B1 | **Лента «Требует внимания»** (правый/верхний rail, сортировка по критичности): звонок ждёт > `max_wait_sec`; пауза дольше `max_duration` причины; wrap-up > лимита; разговор > 2×AHT очереди; серия RNA ≥ N; `queuesDetached`; SLA очереди ниже порога; свободных < минимума. Каждая строка с действием: снять паузу, spy, написать в чат, добавить в очередь, перевести звонок. Бэкенд: события брешей в SSE (`ccAlert`) из `callcenter-alert.service.ts`, а не только во внешние каналы; звук по `alert_sound_enabled`. |
| B2 | **Очереди в виде плиток**: ожидают, **самое долгое ожидание (тикает)**, SLA сегодня, Abandon %, ASA, AHT, агенты ready/busy/paused, изменение SLA за последние 30 мин. Цвет по порогам тенанта. Клик = фильтр всей страницы. |
| B3 | **Live Calls**: колонки «ждёт / говорит» с таймером, позиция, повторный звонок сегодня (×N), VIP, число переводов; сортировка по ожиданию по умолчанию; подсветка превышения SL. |
| B4 | **Внутридневной график**: поступило / отвечено / потеряно по 15/30 мин + SLA нарастающим итогом; наложение «тот же день недели прошлой недели». Источник — серверный интервальный агрегат (C1), не браузерные сэмплы. |
| B5 | **Доска агентов для 100+**: компактный режим (плитка 1 строка), группировка по команде / очереди / статусу, сортировка по времени в статусе, поиск, счётчики по статусам сверху (кликабельны). Подсветка: пауза сверх лимита, RNA, долгий разговор. |
| B6 | **Команды**: сущность `cc_teams` (название, тимлид, участники); супервизор видит свои команды, руководитель — все; watchlist остаётся как личный фильтр. Права через существующий access scope. |
| B7 | Wallboard: варианты по очереди / команде (параметр токена), плитка longest wait, без локального графика (берёт C1). |

Приёмка: сценарий «в очереди 1 SLA упал» → супервизор видит алерт, открывает очередь, видит оператора в паузе 25 мин при лимите 10, снимает паузу — без перехода на другие страницы. Проверка на 300 мок-агентах: без лагов (виртуализация списка, мемо-рендер как в текущем `AgentStatusElapsed`).

Приёмка: отчёт «Сервис» за вчера по 30 мин совпадает с B4 за вчера; scorecard оператора совпадает с суммой его звонков в call-detail; из любой цифры за ≤ 3 клика открывается запись.

### Фаза D — Результаты звонков и маркетинг (P2)

Цель: маркетолог видит, сколько обращений принёс каждый канал, сколько потеряно и сколько стало продажами.

| ID | Задача |
|---|---|
| D1 | **Коды результата**: справочник «Тема → Результат» с флагом `success` (конверсия) и `requires_callback`; выбор в WrapupBar / карточке, обязательность — настройка очереди `outcome_required`, по умолчанию выключена (R3). Хранение в структурированной таблице `cc_call_outcomes` (`call_uniqueid`, `topic_code`, `outcome_code`, `success`, `agent_user_uid`, `queue_name`), не только в JSON карточки. |
| D2 | **Источники и бюджеты**: справочник `cc_number_sources` (DID / входящий номер → канал, кампания, период действия) и `cc_source_budgets` (источник, период с / по, сумма в копейках, валюта тенанта; несколько периодов на источник, без пересечений). Бюджет за произвольный отчётный период распределяется пропорционально дням пересечения (R5). Редактирует ADMIN (R8). Проставлять `source` в `cc_queue_calls` при входе в очередь; для звонков мимо очереди — из CDR по DID. |

| D4 | **Вкладка «Маркетинг» дашборда КЦ (E7)**: обращения по источникам (всего / уникальные / новые), потерянные лиды по источникам и часам, восстановленные перезвоном, конверсия по источнику и теме, **стоимость лида**: бюджет / обращения, / уникальные, / новые, / конверсии (CPL, CPA) с дельтой к прошлому периоду; для источника без бюджета — «бюджет не указан», а не 0; топ причин обращений (D1 + темы речевой аналитики). |
| D5 | Речевая аналитика: при ingest сохранять `call_uniqueid`, `queue_name`, `agent_user_uid`; агрегаты тем / sentiment / оценок по очереди и оператору для C4 и D4. |

Приёмка: по тестовому дню с 3 источниками дашборд показывает обращения, потери, восстановление и конверсию, совпадающие с выборкой звонков; CPL / CPA совпадают с ручным расчётом, включая бюджет месяца, частично попавший в период; результат обязателен там, где включено, и wrap-up без него не завершается.

### Фаза E — Отдельный дашборд КЦ `/callcenter/dashboard` (P1–P2)

Цель: руководитель КЦ открывает одну страницу и за минуту понимает, как прошёл день / неделя, где просели и куда идти разбираться. `PbxDashboard` (`/`) не трогаем — это дашборд администратора АТС.

Структура страницы (сверху вниз):

1. **Шапка**: пресеты периода (сегодня, вчера, 7 дн, 30 дн, свой), «сравнить с прошлым периодом», фильтр очередей и команд, часовой пояс тенанта, свежесть данных (паттерн `DashboardSource`). Состояние в URL.
2. **Сейчас** (только для «сегодня»): ждут, самое долгое ожидание, агенты ready / busy / paused / offline, SLA за последние 30 мин. Клик → `/callcenter/supervisor` с фильтром очереди.
3. **Сервис за период**: поступило, обслужено, SLA %, Abandon % (+ короткие сбросы отдельно), ASA, AHT. Каждая карточка — значение, дельта к прошлому периоду, спарклайн. Клик → отчёт «Сервис» с теми же фильтрами.
4. **Интервальный график**: поступило / обслужено / потеряно по 15–30 мин (день) или по дням (неделя / месяц) + линия SLA, наложение прошлого периода. Клик по интервалу → список звонков.
5. **Очереди**: компактная таблица, отсортированная по худшему SLA: поступило, SLA, Abandon %, ASA, AHT, тренд.
6. **Команды и отклонения**: таблица команд (обслужено, AHT, occupancy, доля пауз, оценка качества); список операторов-отклонений (AHT > 1,5× медианы, пауза сверх нормы, серия RNA, много коротких разговоров) со ссылкой на scorecard (C4). Это взгляд руководителя; R4 касается только экрана оператора.
7. **Потери и перезвоны**: потеряно, ещё не перезвонили (ссылка на рабочий список), recovery за 15 / 60 мин, распределение времени до сброса.
8. **Паузы**: доля пауз по причинам, оплачиваемые / неоплачиваемые.
9. **Результаты и причины** (после D1): топ тем, конверсия по очередям. **Качество** (после D5): средняя оценка, доля негативных разговоров.
10. **Вкладка «Маркетинг»** (после D2–D4): обращения по источникам, уникальные / новые, потерянные лиды, восстановленные, конверсия.

Секции, для которых нет данных или не настроен модуль, показывают состояние «не настроено» со ссылкой на настройку, а не нули.

| ID | Задача | Файлы |
|---|---|---|
| E1 | Контракт `CcDashboardOverview` в `packages/shared`: секции с собственным `source` (ok / stale / notConfigured / error), значения + значения прошлого периода, серии для графика. | `packages/shared/src/callcenter-dashboard/*` (новый) |
| E2 | Бэкенд: `GET /callcenter/dashboard/overview?period|from&to&compare&queues&teams` — один запрос, агрегирует из интервальных агрегатов C1, live-состояния и функций A1; tenant из JWT; scope супервизора (очереди / команды) из access scope. Drill — через существующий call-detail с фильтрами. | `packages/backend/src/modules/callcenter/dashboard/*` (новый) |

## 5. Приоритеты и оценка трудоёмкости

| Фаза | Ценность | Риск | Оценка |
|---|---|---|---|
| A. Одна правда | критичная: без неё остальное вредно | средний (смена схемы записи, без миграции истории — R6) | 1–1,5 нед |
| B. Live cockpit | высокая для смены | низкий | 2–3 нед |

| G. WFM-lite | высокая для крупных КЦ | высокий | 2–3 нед |

## 6. Решения владельца продукта (2026-10-15)

| # | Вопрос | Решение |
|---|---|---|
| R1 | Abandoned в знаменателе SLA | **Да.** SLA = handled в пределах `servicelevel` / (offered − short abandons). |
| R2 | Порог short abandon | **5 с** по умолчанию (`short_abandon_sec`, настраивается в тенанте). |
| R3 | Обязательность результата звонка | **Опционально:** настройка очереди `outcome_required`, по умолчанию выключена. |
| R4 | Рейтинг операторов среди коллег | **Опционально:** настройка тенанта `agent_leaderboard_enabled`, по умолчанию выключена. |
| R5 | Стоимость лида в первой версии маркетинга | **Да, в v1.** Бюджет источника по периодам (D2), стоимость обращения / уникального / нового / конверсии на вкладке «Маркетинг» (D4). |
| R6 | Перенос старой истории | **Не нужен:** проект новый. Миграции данных и пометки старых периодов нет; меняются только запись и расчёт. |
| R7 | Где дашборд КЦ | **Отдельная страница `/callcenter/dashboard`** в модуле КЦ. `PbxDashboard` остаётся дашбордом администратора и не меняется. |
| R8 | Доступ маркетолога | **Отдельную роль / право пока не делаем.** Вкладка «Маркетинг» и справочник источников доступны SUPERVISOR и ADMIN (бюджеты редактирует ADMIN). |
