## Отклонения от PLAN (фиксируются здесь)

1. **AHT = talk + wrapup, без `hold`.** В PLAN §3 формула с `hold`; но `talk_time` считается от answer до end и уже включает удержание
   (AMI: `talk_time = end − answer`; `hold_time` — справочная доля). Добавление `hold` считало бы его дважды. Словарь метрик (A1) фиксирует `talk + wrapup`.
2. **RNA — отдельная таблица `cc_agent_offers`** (как в PLAN A2). Дополнительное обоснование: уникальный индекс
   `uq_cc_queue_call_tenant_id (vpbx_user_uid, call_uniqueid)` (миграция 0003) конфликтует, если RNA-строка и итоговая строка звонка делят `call_uniqueid`.
   Маркер `call_type='rna'` не решил бы конфликт.
3. Схема меняется через версионированный SQL (`database/migrations/0036-*`), а не новым `migrate-callcenter-*.ts` (те — maintenance-only по DB-02-A).
4. Часовой пояс тенанта: `tenants.timezone` → `PBX_DEFAULT_TIMEZONE` → `UTC` (как `DashboardCloudService.timezone`), с кэшем и безопасным fallback, если таблицы `tenants` нет.
5. **Агентская RNA-метрика**: пропуски очереди берутся только из `cc_agent_offers`; `cc_missed_calls` (personal) дедуплицируется по `call_uniqueid` с историей (D12 — двойной счёт исправлен).
6. **Реконсилер**: `created_at` строки истории = время окончания звонка (звонок относится к дню завершения); затронутые дни — по ключу даты в TZ тенанта.
7. **Журналы звонков** дополняются RNA-попытками (синтетические строки `callType='rna'`, uid < 0) через `mergeJournalOffers`.
8. **Occupancy (A7)**: после рестарта READY-время восстанавливается из `cc_agent_sessions`/`cc_agent_events` (`callcenter-agent-timeline.util`), ночные смены режутся по границе отчётного дня; открытая сессия продолжает живой READY-трек.
9. **Известное ограничение**: строки, которые реконсилер добавляет за *текущий* день, попадают в живую память только при следующем `restoreToday`.

AMI стенда подключается через несколько секунд после старта backend (сначала в логе «AMI not connected» — это гонка при старте, не отказ); после этого: 8 очередей. Результат (прогон из 4 звонков, все проверки зелёные; сценарий прогнан 3 раза, итоговый — на исправленном backend):

Участник регистрировался в состоянии как «LiveAgent», дублировался с настоящим ключом `Local/agent@…` (на плитке «Свободны 1 + В разговоре 1» при одном участнике) и после `QueueRemove` оставался в состоянии навсегда (событие удаления приходит по устройству). Ключ теперь `interface || location || name`; 3 теста в `callcenter-ami.service.spec.ts`; живая проверка: ровно один агент, после удаления состояние чистое. Платформа сама участников с `MemberName` не создаёт — дефект проявляется на очередях, настроенных вручную или внешними инструментами.
51. **Не проверено**: реальные оператор-сессии (вход с панели, паузы, RNA) и звонки с живым SIP-телефоном — нужен зарегистрированный софтфон; секция «Операторы» на живых звонках пуста (участник без сессии, < 5 звонков), её логика проверена на реальных данных за июль–август и модульными тестами.
