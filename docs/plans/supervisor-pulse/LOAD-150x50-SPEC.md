# Техническое задание: 150 одновременных звонков и 50 операторских панелей

**Идентификатор:** CC-LOAD-150x50 · **Редакция:** 1.0 · **Дата:** 28.10.2026, Красноярск, UTC+7.

**Статус:** ТЗ подготовлено для согласования и последующего исполнения. Новые нагрузочные прогоны по этому ТЗ ещё не выполнены.

**Координатор подготовки:** `/root`, codex-direct, назначение A14 в [PLAN](PLAN.md), состояние в [EXECUTION](EXECUTION.md).

## 1. Цель и результат

Проверить совместную работу АТС, backend, БД, транспорта событий и настоящих браузерных панелей при 150 одновременных звонках и 50 активных операторских местах. На одинаковой нагрузке сравнить SSE и WebSocket, определить ограничения каждого варианта, найти подтверждённые узкие места и подготовить проверяемый план оптимизации. По измерениям построить карту и расчётную модель CPU, RAM, сети, диска и соединений для разных нагрузок.

Заказчик уточнил: «50 реальных операторов» — **50 отдельных учётных записей с настоящими браузерными панелями**, а не обязательное участие 50 сотрудников. HTTP-клиенты, 50 токенов или фиктивное заполнение Redux не заменяют эти места.

Обязательные результаты задания:

## 3. Модель нагрузки и термины

### 3.1. Пользователи, панели и роли

Основная популяция: **50 операторов + 2 супервизора = 52 одновременно открытые панели**. Супервизоры добавляются сверх 50 операторов, чтобы не уменьшать проверяемое число рабочих мест. Любое другое соотношение указывается как отдельный профиль, с точными фактическими числами.

Для каждого оператора обязательны собственные учётная запись, cookie/storage browser context, открытая смена, отдельный внутренний номер и настоящий SIP- либо WebRTC-сеанс. Вход через штатный UI/API, включая действующие проверки доступности устройства. Панели показывают данные реального backend, принимают реальные события и выполняют штатные команды. Супервизорские права не выдаются операторам для упрощения теста.

Два супервизора работают независимо: первый на `/callcenter/supervisor`, второй переключается между текущими звонками, очередями, командой и журналами. У операторов открыт `/callcenter/agent`; вкладка «Текущие звонки» основная, остальные вкладки регулярно используются по сценарию.

### 3.2. Что считать звонком

Раздельно считать:

- `C_connected`: соединённые разговоры, включая удержание; `C_talking` и `C_hold` внутри него непересекаются;
- `C_waiting`: клиенты в очереди, включая воспроизведение MOH;
- `C_ringing`: звонки на стадии вызова оператора;
- `C_total = C_connected + C_waiting + C_ringing` в согласованной модели состояний;
- SIP-диалоги, RTP-потоки, Asterisk channels, bridges и логические звонки. Это разные величины;
- `C_rec`: одновременно записываемые разговоры; `X`: одновременно транскодируемые медиасессии с указанной единицей.

Идентификатор логического звонка связывается с callId/linkedid/uniqueid и всеми его ногами, включая перевод. Количество каналов не подменяет число звонков; схема с Local-каналами может иметь больше двух каналов на один разговор. CDR и queue_log сверяются с исходной последовательностью событий, а не используются как единственный счётчик текущей одновременности.

### 3.3. Два обязательных сценария 150 звонков

| Профиль | Состав плато | Что доказывает |
|---|---|---|
| Q150 | 50 соединённых с операторами +100 ожидающих; отклонения во время смены звонка фиксируются | Работа колл-центра 50 мест при перегруженной очереди, MOH, FIFO, подхвате и изменении KPI |
| M150 | 150 соединённых:50 с операторами и 100 с отдельными техническими автоответчиками | Медианагрузка 150 соединений и обработка соответствующего состояния панелями |

Один оператор в штатном однолинейном сценарии не ведёт три независимых разговора одновременно. Для M150 нужны 100 дополнительных технических отвечающих абонентов/участников тестовых очередей. Они помечаются как технические, не считаются дополнительными людьми или браузерными местами и не смешиваются с операторскими KPI. Если их звонки не входят в модель call-center, это отдельный PBX-only профиль и не доказательство отображения 150 строк звонков в панели.

В Q150 низкий SLA и длительное ожидание могут быть ожидаемым следствием 50 занятых операторов. Проверяется правильность расчёта и отображения SLA, а не обязательное достижение бизнес-SLA при заведомой перегрузке очереди.

### 3.4. Устройства и медиа

Обязательны S50 —50 SIP-телефонов с 50 панелями и MIX40/10 —40 SIP +10 браузерных WebRTC. Для заявления о поддержке 50 WebRTC-мест дополнительно обязателен W50; результаты S50 на него не экстраполируются.

Оба направления реального RTP/SRTP должны передавать проверяемый тестовый аудиосигнал. Для WebRTC допускается синтетический микрофон браузера, но сохраняется полный путь SIP over WSS, ICE/DTLS/SRTP и фактическое медиа; это не проверка человеческой разборчивости речи. Снимать `getStats()` для каждого WebRTC-места. Работоспособность только SIP-генератора не закрывает WebRTC gate.

Базовый кодек — один согласованный G.711 без транскодинга, packetization20 ms; точный codec/ptime подтверждается фактически. Opus↔G.711, TURN и другой codec/ptime — отдельные профили. Прямое медиа, обходящее Asterisk, отключено либо явно выделено в самостоятельный сценарий. Запись включена по целевой политике; для capacity с записью обязателен замер 100%соединённых разговоров. Профиль без записи нужен отдельно для оценки её стоимости. AI/ASR/TTS не входят в основной расчёт и требуют отдельных коэффициентов/прогонов.

## 4. Стенд и неизменяемый manifest

### 4.1. Разделение ресурсов

Исходный кандидат SUT из контекста задачи — тестовый стенд `192.168.2.201`. Его фактический состав и соответствие целевой коробке проверяются перед исполнением. Адреса отдельных браузерных машин/генераторов, порты и изолированный кабинет записываются в manifest; прежнее совместное размещение браузеров на этом сервере не переносится в новый capacity-прогон.

Нагрузочные браузеры и генераторы SIP/RTP размещаются **вне сервера приложения/АТС/БД**. Учитываются отдельно четыре группы: SUT (тестируемая система), браузерные машины, генераторы телефонии и сбор телеметрии. Допускается совместное размещение backend/БД/Asterisk как у заказчика, но нагрузочные клиенты туда не добавляются.

Для клиентских машин сначала снять idle/loaded расход одного и десяти мест и выбрать число машин с запасом. Указать число процессов Chromium, contexts и pages; не считать 50API-клиентов или 10 дорисованных окон 50 панелями. У групп клиентов должно оставаться не менее 30%CPU и 25%RAM; запланированные действия не должны замедляться вслед за SUT. При нехватке ресурсов генератора результат маркируется как ограниченный генератором, а не предел приложения.

Браузерные профили: одинаковый viewport, версии, локаль, шрифты, масштаб и режим кеша для обеих сторон. Основной desktop viewport1440×900. Профили с другими размерами сохраняются отдельно. Записывать реальную `visibilityState`; базовый worst case —52 видимые отрисовываемые страницы. Обычные скрытые вкладки проверяются отдельно, без принудительного отключения их штатного throttling.

### 4.2. Manifest до каждого прогона

Зафиксировать runId, сценарий, seed и порядок A/B; время UTC и ISO8601 с UTC+7; Git SHA frontend/backend/shared/harness, dirty diff или чистое дерево, image digests, schema/migrations; production build и параметры флагов измерения; версии Node/Chromium/Asterisk/модулей/СУБД/Redis/ORM/драйверов; конфиги очередей, codecs/ptime, record/MOH/qualify, auth/throttler, cache/proxy/TLS/HTTP/compression/keepalive/WS ping.

Описать CPU модель/частоту/число vCPU, NUMA при наличии, RAM, диск/FS, NIC, VM/cgroup quotas, swap, steal time, ОС/kernel, топологию и фоновые службы. Версии Asterisk certified22.8 и PostgreSQL17 из предыдущего плана — кандидаты целевой коробки, которые необходимо подтвердить; лабораторные Asterisk16/20, другая БД и dev Vite не заменяют release gate целевой конфигурации.

Основная матрица выполняется на выбранном целевом стеке. Если capacity заявляется одновременно для PostgreSQL и MySQL, для каждого нужны отдельные функциональные проверки и основной парный прогон; результаты одной СУБД не переносятся на другую.

## 5. Данные и предварительные проверки

Использовать изолированный тестовый кабинет и полностью синтетические данные. Обязательный состав:50 операторов,2 супервизора,6 очередей с пересекающимся членством и одна общая очередь для Q150; технические абоненты M150 отдельно помечены. Внешний кабинет с повторяющимися внутренними номерами нужен для проверки изоляции, но не входит в рабочую нагрузку.

Базовый объём:100000 записей истории,1000 пропущенных/заказанных обращений разных состояний, записи разговоров, достаточные для проверки чтения и удержания записей. Seed, распределение по датам/пользователям/очередям, индексы и статистика БД одинаковы для SSE/WS. Отдельный профиль 1000000 исторических записей проверяет чувствительность к росту БД, не смешиваясь с основным сравнением. Во время звонков история пополняется настоящими событиями этих тестовых вызовов; прежний синтетический корпус ими не называется.

До нагрузки должны пройти:

1. Штатный вход, начало/восстановление/завершение смены; только подходящие зарегистрированные и доступные устройства, корректные подписи/i18n.
2. Один вызов через очередь на SIP и WebRTC, двустороннее медиа, запись, корректный BYE и возврат к 0 каналов; первый qualify после REGISTER без ручного обхода проверки доступности.
3. Пропущенные и история без 500, включая группировку/сортировку на целевой БД; старт приложения без ошибки runtimeDDL.
4. Изоляция tenant/user/queue, права супервизора, корректное истечение/обновление токена.
5. Политика лимитов: фактический ключ, обработчик, пользователь/IP, ответные заголовки и порядок guards; отсутствие двойного непреднамеренного учёта. Эффективные лимиты записать, не угадывать из одного из двух config.
6. Парковка: успешное чтение пустой/непустой парковки, корректный вызов «повторить», отсутствие чередования visible/error при нормальных ответах.
7. Снимок исходного состояния, reserved IDs/PID/контейнеров, остановка по deadline и процедура очистки только собственных объектов.

Блокирующий функциональный дефект сначала фиксируется отдельным результатом. После исправления формируется новый **общий** baseline для обеих сторон. Ни молчаливое снятие лимитов, ни 50 разных исходящих IP вместо проверки NAT не считаются исправлением продукта.

## 6. Правила честного сравнения SSE и WebSocket

| Матрица | SSE | WebSocket | Интерпретация |
|---|---|---|---|
| T1, существующий HTTP/1.1 путь | SSE по HTTP/1.1 | WS по HTTP/1.1 Upgrade | Прямое сравнение на одинаковом текущем сетевом стеке |
| T2, целевой TLS/proxy путь | SSE по фактически согласованному HTTP/2 | WSS через поддерживаемый proxy путь | Сравнение целевых схем доставки; фактический протокол каждого соединения обязателен |

HTTP/2 на стороне браузера не означает HTTP/2 между proxy/backend и не гарантирует WebSocket overHTTP/2. T1 и T2 не объединять в одну статистику; невозможность T2 фиксировать как непроверенную альтернативу, а не проигрыш SSE в любых условиях. Ограничение числа HTTP/1.1 соединений одного браузера относится к browser/origin;50 разных браузерных contexts и 6 вкладок одного пользователя — разные испытания. См. [описание SSE и ограничений браузера](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events).

Внутри каждой парной ячейки одинаковы SHA, payload/schema, видимость/права событий, компрессия/буферизация, настройки heartbeat/reconnect, начальные данные, количество реальных открытых страниц, API периодика, media/record/transcode, CPU/RAM бюджеты, логические входные действия и длительность. Различаться должен исследуемый транспорт; неизбежные различия auth/handshake документируются. Решение открыть вторую вкладку не создаёт второй UA на тот же номер, если продукт этого не допускает.

Генератор задаёт одинаковую последовательность логических входов с seed, абсолютным расписанием и корреляцией; Asterisk присвоит новые uniqueid в каждом прогоне, поэтому требовать одинаковых физических ID между A/B нельзя. Сверять семантическую нагрузку и фактически достигнутую одновременность. Снижение рассылки только на одной стороне — уже сравнение оптимизаций, а не транспортов.

На каждую основную ячейку — минимум 3 пары запусков, с чередованием AB/BA и зафиксированным seed порядка. Между запусками: завершить свои звонки, закрыть браузерные targets, проверить 0 каналов, восстановить начальные данные/счётчики/статистику выбранным способом, одинаково прогреть кеши. Новые вызовы одного запуска не переходят в другой. Все окна сохраняются, включая неудачные; выбирать лучший p95 из нескольких попыток запрещено.

Сначала измеряется общая версия без оптимизаций между A/B; затем допустим новый общий baseline после оптимизации и повтор той же матрицы. Крупные CPU/React traces собираются в отдельных диагностических повторах. Лёгкая инструментация должна быть одинаковой, ограниченной по памяти и проверенной контрольным запуском: её накладные расходы на throughput/CPU/latency желательно≤5%; превышение требует уменьшения частоты или отдельной пометки результата.

## 7. Сценарии, расписание и длительность

### 7.1. Общий порядок

Предавторизация по действующей политике → регистрация устройств и проверка доступности → открытие всех 52 панелей → готовность каждой панели → минимум 5 минут прогрева → измеряемое окно → завершение звонков/команд → итоговая сверка состояния → очистка. Холодный старт измеряется отдельно, не включается в steady-state p95.

Плато 150 не подменяется кратким пиком. Для удержания одновременности использовать заранее заданные времена жизни; краткие провалы/всплески при замене соединений учитывать как call-seconds deficit/excess. Не менее 99%секунд измеряемого основного окна должно соответствовать целевой популяции в пределах±2 звонка; каждый недостаток записывается. Задержки реальных звонков и фактический offered/accepted rate не скрывать поддержанием замкнутой модели.

Дополнительно обязателен открытый поток поступления: новые попытки запускаются по расписанию независимо от завершения предыдущих. Сохранять scheduled/started/completed/dropped и отставание генератора. Это защищает от ситуации, когда при торможении системы сам тест незаметно снижает нагрузку; см. [открытую и закрытую модели k6](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/open-vs-closed/).

Q150 не считается стабильной системой обслуживания с хорошим SLA: это специально ограниченная очередь. В открытой модели λ выбирается по измеренному AHT/ACW и требуемой загрузке, затем повышается ступенями до границы SLO. Опциональный ramp выше 150 или 50 мест — отдельное назначение с собственными пределами; он не требуется для объявления результата на 150.

MORNING разделяет два вывода: security-негативный тест обязан показать срабатывание действующего лимита; бизнес-сценарий 50 легитимных входов за 60 с должен получить оценку доступности. Если текущая IP политика блокирует этот бизнес-сценарий, фиксировать fail политики и предложить безопасное изменение отдельно. Нельзя одновременно требовать прежний общий лимит 10 входов/минуту на NAT и 50 успешных входов за ту же минуту. Не подменять проверку входа выдачей готовых токенов; предавторизация разрешена только для отдельного steady-state теста.

### 7.3. Действия в панелях

В steady-state по seed расписать на каждого оператора в среднем одно действие раз в 30 с: смена вкладки/поиск/история/«К работе»/очереди. На всю популяцию дополнительно: pause/resume одного свободного оператора каждые 30 с; переключение членства в очереди раз в 60 с;1 перевод/мин,1 парковка-возврат/мин,1 исходящий и 1 обратный звонок/мин; сценарии меняют разные звонки и не должны случайно конфликтовать.

В Q150 все 50 операторов могут быть заняты. Для pause/resume планировать короткое свободное окно при ротации разговора, в пределах допуска ±2 звонка; не выполнять запрещённую команду над занятым оператором. Дополнительные исходящие/парковки занимают предусмотренные слоты общей нагрузки, а не незаметно увеличивают её. Неисполненные по guard действия и отставание расписания фиксируются отдельно; снижение фактической интенсивности не скрывается.

Для супервизоров: изменение сортировки/фильтра раз в 30 с, открытие карточки/очередей раз в 60 с, управление оператором раз в 60 с; наблюдение/подключение при разрешённом праве — отдельный помеченный эпизод с учётом дополнительного media leg. Оператор должен видеть разрешённые вызовы очереди и коллег, подхватывать ожидающего; тест не разрешает оптимизировать поток до «только свои звонки», если это убирает эти возможности.

Отдельные коррелируемые проверки: входящий→ответ→удержание→возврат→завершение; FIFO и позиция ожидающего; клиент сам перезвонил и снял пропущенное; согласованность счётчиков вкладок/карточек/истории; pause/resume и очереди без рассинхронизации; переход на другую страницу во время реального разговора с сохранением общего софтфона. Измерять подтверждённый результат команды на backend/АТС, а не только мгновенный optimistic UI.

Polling в продукте, включая парковку, одинаков для A/B и соответствует текущей версии. Не добавлять 50 внешних probe-клиентов к тому же rate-limit ключу. Доступность парковки оценивать по штатным запросам и состоянию её кнопки; искусственные error/visible переключения отмечать как функциональный fail. Отсутствие припаркованного вызова — штатное состояние, ошибка проверки — другое состояние.

## 8. Измерения и корреляция

### 8.1. Цепочка задержки

Каждое контрольное изменение имеет runId, logicalCallId, actualUniqueid/linkedid, semanticEventId, entityKey, ожидаемых получателей и source sequence. Для каждого получателя фиксировать:

| Время | Граница |
|---|---|
| `t_plan` | Запланированное время действия генератора |
| `t0` | Первое наблюдение соответствующего AMI/бизнес-события на входе backend |
| `t1` | Обновление состояния приложения |
| `t2` | Передача сериализованного события в транспорт/очередь отправки конкретному получателю |
| `t3` | Получение и разбор события в браузере |
| `t4` | Первое появление соответствующего состояния в реальном DOM |
| `t5` | Следующий animation frame, если измеряется |

Считать отдельно `t0-t_plan` (инжекция/телефония), `t1-t0`, `t2-t1`, `t3-t2`, `t4-t3`, `t4-t0`. `t0` — наблюдение AMI на входе, не доказанное время физической отправки Asterisk. `t5` не называть физическим paint. Если нужен paint, использовать отдельный браузерный trace с явно указанной методикой.

На всех машинах синхронизировать часы; сохранять измеренный offset и неопределённость до/после каждого окна. Для cross-host one-way метрик желательна неопределённость≤2 ms, обязательна≤5 ms. Иначе не публиковать точные one-way перцентили как проверенные; локальные monotonic интервалы и RTT остаются действительными. Преобразование `performance.now()` через timeOrigin документируется; UTCepoch и monotonic clocks напрямую не вычитаются.

Видимые строки проверяются на реальном DOM. Невидимые/виртуализированные строки получают отдельную метрику store-freshness; скролл к ним должен показать актуальное состояние без ожидания нового события. Не считать отсутствие DOM невидимой строки потерей события. Входящие/контрольные состояния для nominalDOM замера держать≥1 с; для EVENTS40 ms собирать также долю визуально объединённых промежуточных состояний. Coalescing допускается для представления текущего состояния, но не для потери завершения звонка, результата команды или корректности истории.

Node инструментацию строить на совместимых с фактической версией API [eventLoopUtilization/monitorEventLoopDelay](https://nodejs.org/api/perf_hooks.html); единицы histogram корректно переводить в ms. WebRTC медиа подтверждается статистикой [RTCPeerConnection/getStats](https://www.w3.org/TR/webrtc-stats/).

Серверные метрики собирать с шагом 1 с; накопительные counters сохранять до/после и дельтами. Браузерные события/команды — точечными timestamps, heartbeat/периодические receipts не реже 1 с с оценкой накладных расходов. Тяжёлые полные snapshots/traces не запрашивать с 50 мест каждую секунду ради измерения. Для media доступны per-call counters и агрегаты 1 с, содержимое аудио хранить только для ограниченной синтетической выборки.

HTTP 200 после получения заголовков, за которым чтение body прервано, — не успешный запрос. Не смешивать клиентские abort, ответ 502, backend exception и rate-limit 429. Для каждой ошибки сохранять route, этап, пользователя/роль без секретов, время, корреляцию, факт попадания на proxy/backend и наличие штатной отмены при navigation.

Не делать вывод о DB pool, media CPU или производительности бизнес-API только по быстрому `/health`: это liveness. Проверять типичные чтения панели, запись команды и запросы к БД в том же окне. Дополнительные probes считаются отдельной нагрузкой и не должны исчерпывать лимит публичного health.

### 8.3. Анализ статистики

Для каждого сценария/транспорта/запуска/роли и критического маршрута вывести count, p50, p95, p99, max, ошибки и pending; показать худший клиент и распределение по всем 50 операторам/2 супервизорам. При недостаточном объёме данных p99 помечать ненадёжным, не заменять максимумом без маркировки. Для основных перцентилей стремиться к≥1000 семантических наблюдений на роль/ячейку; для редких команд показывать все значения и число эпизодов.

Перцентили запусков не усреднять арифметически. Сохранять исходные samples/гистограммы, результаты каждой пары и 95% интервалы разности по независимым парным запускам; временную зависимость учитывать блоками, а не миллионами независимых пакетов. Три пары дают ограниченную уверенность: если интервалы перекрывают практически значимый эффект, расширить выборку или оставить вывод неопределённым.

Считать четыре покрытия: ожидалось источником; подлежало доставке по правам на момент события; реально получено; отражено DOM/store. Повторы выделяются отдельно. Глобальный eventId может иметь пропуски из-за фильтра прав; это само по себе не потеря. Промежуточные визуально объединённые статусы и потерянные доставки имеют разные счётчики. Сравнение только успешно отрисованных быстрых событий без покрытия и длинных хвостов недопустимо.

## 9. Критерии приёмки

Ниже — **заданные инженерные цели**, а не уже измеренные возможности. Любое изменение порога согласуется и фиксируется до нового запуска. Основной SLO оценивается в steady-state на целевом стеке при исправном генераторе и нормальной сети; WAN, stress и аварии имеют отдельные результаты. Для базовой LAN дополнительно измеряется RTT; его нельзя молча вычесть из пользовательской задержки.

| Gate | Порог для основного Q150/M150 профиля |
|---|---|
| Популяция | Все 50 операторов и 2 супервизора готовы; целевая одновременность по §7.1, не единичный пик |
| Событие→видимый DOM | Для контролируемых состояний≥1 с: p95≤250 ms,p99≤500 ms, отдельно по роли; max и coverage обязательны |
| Свежесть итогового состояния | После окончания номинального изменения все разрешённые панели сходятся≤2 с; после сбоя транспорта≤10 с от восстановления сети |
| Сохранность | 0 потерянных обязательных событий вне заданного outage; нет неправильных звонков/KPI/команд или повторного выполнения; при outage полный корректный resync |

Пороги loss/jitter для LAN не доказывают MOS или качество WAN. Запись дополнительно проверяется на наличие файла, длительность/формат, оба направления, отсутствие обрыва и связь с завершённым звонком. Queue KPI/пропущенные сверяются с контрольными событиями, reporting window/timezone, slaThreshold и short-abandon правилами.

Нулевые ошибки на конечной выборке не доказывают нулевую вероятность ошибки: в отчёте указывать экспозицию/число запросов/звонков. Stress может не пройти nominal SLO, но обязан завершаться контролируемо, без потери итоговой корректности и с отмеченной границей деградации. Транспорт не признаётся «рабочим на 150», если прошёл только wire connectivity, а nominal SLO или API доступность не выполнены. Если оба варианта fail, итог — «ни один не принят», с приоритетом дальнейших исправлений.

## 10. Поиск слабых мест и план оптимизации

Необходимая диагностика:

1. **HTTP/NAT:** фактический handler/tracker key, ожидание HTTP-слотов, буферизация proxy/HTTP2, повторы маршрутов и порядок auth/global guards. Не предполагать общий бюджет 20 на все 80 разных запросов.
2. **FullSnapshot:** причина каждого снимка, начальная подписка против broadcast при входе в смену, reconnect; рост стоимости при 10/25/50 входах. 1263 снимка в прежнем отчёте требуют объяснения, но не доказывают reconnect storm.
3. **Fan-out:** исходные события против доставок, одинаковые agent/queue payloads, JSON и CPU подписчиков; зависимость от операторов/очередей/супервизоров и прав.
4. **Открытие UI:** HAR/waterfall с окном наблюдения, уникальные routes/повторы/polling, RTK subscriptions/invalidation, production против dev StrictMode. Сначала найти дубли, затем обосновать lazy loading/cache/bootstrap.
5. **Основной поток backend:** reconcile/AMI/JSON/GC/синхронные циклы, event loop delay, отдельные profiles. Добавление vCPU не устраняет автоматически блокировку одного JS-потока.
6. **БД:** конкретные query plan/lock/acquire/fsync/WAL, объём истории, диалект SQL. Не увеличивать pool без измерений ожидания и ресурсов БД.
7. **React/браузер:** повторный render строк/таблиц/KPI, selectors, таймеры, длинные задачи, видимые/скрытые страницы; profiler отдельно от A/B.
8. **Телефония:** REGISTER→qualify→ready, AMI backlog, стоимость RTP/записи/транскодинга/TURN, причины ошибок BYE. Дефект SIPp не считать утечкой Asterisk.

Исполнитель составляет OPTIMIZATION-PLAN: findingId, компонент, severity, воспроизведение, baseline/runId и locator доказательств, причина или гипотеза и уверенность, предлагаемый срез, owned paths/зависимости, прогноз измеряемого эффекта, риски для прав/управления/звонков, targeted regressions, критерий повторного A/B, rollback. Приоритет: блокирующие дефекты → дубликаты/fullSnapshot → подписки/coalescing → БД/клиент → масштабирование после измерений.

План не должен заранее назначать SSE или WS победителем, повышать throttle без политики, отключать права/запись/медиа для улучшения цифр или убирать функции очередей/коллег. Реализация оптимизаций — последующее ограниченное назначение; после неё новый SHA и повтор общих ячеек с проверкой корректности.

## 11. Карта и формула расчёта ресурсов

### 11.1. Входы модели

Модель рассчитывает ресурсы для заданного профиля, а не «сервер на 50 пользователей вообще». Все нагрузки задаются одновременно; один и тот же C_total при разном числе разговоров/ожидающих имеет разную стоимость.

| Обозначение | Единица и смысл |
|---|---|
| `A`, `G` | Число операторов и супервизоров с открытыми панелями |
| `S`, `S_op`, `S_sup` | Число именно call-center соединений событий: всего и по ролям, с учётом вкладок/общих подписок; другие namespaces отдельно |
| `V` | Число видимых/отрисовываемых панелей; скрытые считаются отдельно |
| `C_m`, `C_w`, `C_r` | Соединённые медиазвонки, ожидающие с MOH и дозванивающиеся |
| `C_rec`, `C_web`, `X` | Одновременные записи, WebRTC медиасессии, транскодируемые сессии с зафиксированным codec pair |
| `lambda_call`, `lambda_login` | Попытки звонков/с и входы/с, отдельно accepted/answered/rejected |
| `R_api`, `R_db`, `R_checkout` | HTTP запросы/с, DB операции/с и выдачи соединений из pool/с; это разные счётчики |
| `E_k`, `F_k`, `D_k` | Исходные события типа k/с, число получателей, доставки/с |
| `N_devices`, `N_agents_state`, `Q_entities` | Число зарегистрированных устройств, хранимых состояний операторов/технических участников и очередей |
| `T_ser` | Реально сериализованные JSON bytes/с, включая снимки; не приравнивать автоматически к доставленным bytes/с |
| `K_snap`, `B_snap` | Фактические доставляемые снимки/с и средний/пиковый размер снимка в bytes |
| `H_rec_day`, `T_ret`, `b_rec` | Суммарные часы записи/день, хранение в днях, bytes/с одной записи |
| `codec`, `ptime`, `TLS`, `TURN`, `DBsize`, `recordFormat` | Категориальные параметры; значения должны соответствовать калибровке |

Нагрузку рассылки считать отдельно от звонков:

```text
D_k [messages/s] = E_k [events/s] * F_k [recipients/event]
D = sum_k(D_k)
S = S_op + S_sup
F_k = S_op * visibility_operator_k + S_sup * visibility_supervisor_k
```

Доли visibility берутся из прав и фактических подписок. При одной вкладке на пользователя S_op=A и S_sup=G; при дополнительных вкладках это равенство проверяется заново. Если JSON сериализуется каждому получателю, стоимость зависит от D и размера payload; при общем готовом JSON число сериализаций меньше числа доставок. Сохранять фактический T_ser. Snapshot/heartbeat/сжатие учитываются отдельно. Массовый login с общим broadcast может давать квадратичный рост: последовательное присоединение 50 мест — сумма 1+…+50=1275, а 50 broadcast на открытые 50 потоков —2500. Это примеры механизма, не реконструкция прежнего отчёта.

### 11.2. CPU

Для каждого компонента i (backend, Asterisk, БД, Redis, proxy, jobs) измерять **CPU-seconds/second**, то есть эквивалент занятых ядер: 100% одного ядра = 1 CPU-second/second. Калибруемая первая аппроксимация:

```text
cpu_i = b0_i + bm_i*C_m + bw_i*C_w + br_i*C_r
              + brec_i*C_rec + bweb_i*C_web + bx_i*X
              + bcall_i*lambda_call + blogin_i*lambda_login
              + bapi_i*R_api + bdb_i*R_db
              + bevent_i*sum(E_k) + bdelivery_i*D + bserialize_i*T_ser
              + bdevice_i*N_devices

vCPU_i_required = ceil(cpu_i_upper / U_cpu)
U_cpu = 0.60
```

Единицы `bm_i` — CPU-seconds/(second·call), `bapi_i` — CPU-seconds/request. `cpu_i_upper` — верхняя оценка спроса на CPU с учётом пиков по интервалам 1 с и неопределённости модели, а не только среднего за 30 минут. Коэффициенты получают на одной аппаратной платформе, отдельно для SSE/WS, записи и транскодинга. Включать только факторы, которые можно независимо оценить. Если есть взаимодействия или насыщение, использовать проверенную кусочную модель, а не линейную экстраполяцию за пределы измерений.

При совместном размещении компонентов считать их суммарное потребление на одной временной шкале и резерв ОС без двойного счёта. Для раздельных серверов нужен отдельный расчёт каждого узла. Сумма ядер нескольких машин не означает, что одна машина с таким числом ядер даст ту же производительность.

Для одного Node worker дополнительно должны проходить ограничения основного потока, event loop и задержек. Свободные ядра хоста не компенсируют блокировку этого потока. Масштабирование backend несколькими процессами допустимо только после проверки общего состояния, подписок, очередей, сессий и балансировщика. Модель CPU, частота, steal time и cgroup throttling входят в границы применимости формулы.

### 11.3. RAM

```text
M_working = M_OS + M_DB_shared_once + sum(M_process_private)
            + M_required_cache + M_bounded_buffers + M_burst

M_process_i ~= m0_i + mc_i*C_m + mw_i*C_w + ms_i*S
                   + ma_i*N_agents_state + mqueue_i*Q_entities

RAM_required = round_up_supported(M_working_upper / 0.75)
```

RAM выражается в bytes/GiB, коэффициенты — в bytes на сущность. Учитывать прогретые кеши, входы/снимки, пики GC и буферов. `Q_entities` — число очередей, не число ожидающих звонков; `N_agents_state` включает технических участников M150, хотя человеческих операторских мест остаётся 50. Для затрат регистрации/OPTIONS измерять actual rate; изменение qualify_frequency выводит профиль за прежнюю калибровку.

Общие страницы памяти нельзя многократно суммировать по RSS. Описать непересекающийся учёт через PSS, cgroup memory.stat и shared buffers БД. При использовании агрегата cgroup memory.current не добавлять заново уже включённые процессы и page cache. Вывести число сокетов, размер буферов и их настроенные пределы.

Браузеры и генераторы рассчитываются отдельно. Эвристика «500 MB на место» из другого стенда не является универсальным коэффициентом: расход зависит от процессов, contexts, pages, WebRTC, кешей и видимости. Для клиентских машин нужен запас 25% RAM и проверка фактической готовности всех мест; их память не входит в серверную конфигурацию.

В SOAK показать рост памяти после прогрева и возврат после завершения нагрузки. Разрешённые кеши должны иметь описанный предел/TTL. Неограниченный рост памяти или очередей отправки нельзя компенсировать рекомендацией добавить RAM.

### 11.4. Сеть и число пакетов

Для одного направления одной RTP-ноги:

```text
payload_bytes = codec_bitrate_bits_s * ptime_s / 8
packets_s = 1 / ptime_s
leg_direction_bits_s = (payload_bytes + H_packet_bytes) * 8 * packets_s

NIC_TX = sum(actual_TX_flows) + UI_TX + HTTP_TX + remoteDB_TX + backup_TX
NIC_RX = sum(actual_RX_flows) + UI_RX + HTTP_RX + remoteDB_RX + backup_RX
NIC_line_rate_required >= max(NIC_TX, NIC_RX) / U_net
U_net = 0.60
```

`H_packet_bytes` включает IP/UDP/RTP/SRTP/L2 на выбранном уровне счёта. IPv4/IPv6, Ethernet/VLAN, RTCP, SRTP, TURN, ACK, TCP/TLS и сжатие UI учитывать по фактическому пути. Если байты уже измерены сетевым счётчиком, повторно overhead не добавлять. Для TURN составить схему потоков по интерфейсам, не применять универсальный множитель 2.

**Расчётный пример, не результат прогона:** G.711 64 kbit/s, ptime 20 ms, RTP/UDP/IPv4 без options: 160 B payload + 12 B RTP + 8 B UDP + 20 B IP = 200 B × 50 pps = 80 kbit/s в одном направлении одной ноги. Для двух полных ног через PBX один разговор даёт 160 kbit/s TX и 160 kbit/s RX. Для 150 разговоров — **24 Mbit/s TX + 24 Mbit/s RX**, суммарно 48 Mbit/s на L3 и 30 000 packets/s. При бюджете сети 60% только эта медиачасть требует не менее 40 Mbit/s полосы в каждом направлении; UI, RTCP, SRTP, L2 и backup ещё не включены. Считать 48 Mbit/s требованием к каждому направлению было бы двойным счётом.

У ожидающего с MOH обычно одна клиентская нога; её потоки измеряются отдельно. Сценарий «50 разговоров + 100 ожидающих» не равен 150 двухногим разговорам. Описание RTP/RTCP и базового заголовка: [RFC 3550](https://www.rfc-editor.org/rfc/rfc3550).

```text
UI_TX_bytes_s = sum_k(D_k * wire_bytes_k)
                + K_snap * B_snap_wire + heartbeat_bytes_s + HTTP_response_bytes_s
```

Доставки `D_k` в этой сумме исключают отдельно добавленные snapshots и heartbeat. Полезный JSON и все байты на проводе сохранять раздельно. Проверить pps, softirq, drops, retransmits, conntrack и FD: достаточность Mbit/s не снимает ограничение обработки пакетов/сокетов. Для номинального профиля NIC и packet processing должны иметь резерв.

### 11.5. Записи, объём и производительность диска

```text
record_bytes_s = sample_rate_hz * bits_per_sample/8 * channels
V_record_day = H_rec_day * 3600 * record_bytes_s
V_record_retained = V_record_day * T_ret_days * local_copies

V_disk_required = (V_record_retained + V_DB_data_indexes + V_WAL_retention
                   + V_logs + V_temp_peak + V_upgrade_backup) / (1 - free_fraction)
free_fraction = 0.25

disk_write_bytes_s = C_rec * record_bytes_s + DB_data_write + WAL_write
                     + measured_background_write
```

Для сжатого формата скорость записи берётся из фактического распределения размеров, а не PCM-формулы. `local_copies` включает только настоящие локальные копии; внешний backup считается отдельно как хранилище и сетевой поток. Если продукт создаёт один смешанный файл на звонок, не умножать его на число ног или строк CDR. Индексы, WAL/redo, ротация, удаление по retention и временные файлы учитываются без повторного счёта.

**Пример:** PCM16LE, 8 kHz, mono = 16 000 B/s, 57.6 MB на час записи, где MB/GB/TB десятичные. При среднем числе 50 записываемых разговоров в течение 10 часов в день получается 500 call-hours: 28.8 GB/день и 864 GB за 30 дней. Для 150 таких разговоров — 86.4 GB/день и 2.592 TB за 30 дней. Это только аудио, без 25% свободного места, БД и копий. Stereo удваивает объём. Формат настоящего файла MixMonitor подтверждается измерением.

150 одновременных mono-записей этого формата дают 2.4 MB/s последовательной записи аудио. Этого числа недостаточно для выбора диска: дополнительно измерить IOPS, смесь чтения/записи, p95/p99 I/O и fsync, БД/WAL, ротацию и одновременно работающий backup/проигрывание записей. Рекомендация по диску должна пройти бизнес-SLO с запасом, а не только сравнение с паспортным MB/s.

### 11.6. БД, connection pool и интенсивность звонков

Начальная оценка числа занятых соединений по среднему времени их удержания:

```text
L_DB = R_checkout * mean_connection_hold_seconds
pool_candidate = ceil(L_DB / 0.70) + measured_job_reserve

sum(all_backend_pools + ODBC + jobs + admin_reserve) <= safe_DB_connection_budget
```

Это оценка средней конкурентности, не гарантия p99. R_checkout — число выдач соединений в секунду; транзакция с десятью SQL-командами может удерживать одно соединение, поэтому число SQL-запросов сюда автоматически не подставляется. Кандидат проверяется по acquire latency, очередям, CPU/I/O БД и бизнес-SLO. Учитывать длительные транзакции, jobs и все экземпляры backend. Большой pool способен перегрузить БД; прежнее значение 5 само по себе не доказывает ни достаточность, ни необходимость увеличения.

Для стационарного потока применимы соотношения:

```text
mean_calls_in_system = arrival_rate_calls_s * mean_time_in_system_s
mean_talking = answered_rate_calls_s * mean_talk_seconds
lambda_operator_target = occupancy * A / (AHT_seconds + ACW_seconds)
```

Здесь AHT явно обозначает время разговора без ACW; не подставлять показатель, уже включающий ACW. Все средние относятся к одному окну и одной популяции, включая правила учёта abandonment. Начальная волна 150 INVITE не является стационарным потоком.

**Пример:** 50 операторов, 180 с разговора + 20 с ACW, занятость 80% → 0.2 обработанных вызова/с, 720/час; среднее число разговаривающих 36, а не 150. Ожидающие, повторные звонки и отказы учитываются дополнительно. Формулы не заменяют модель очереди и расчёт необходимого персонала по бизнес-SLA.

### 11.7. Калибровка, карта и предел применимости

1. Снять не менее трёх уровней существенного фактора, меняя его независимо от остальных. Только пропорциональные точки «10 мест/30 звонков, 25/75, 50/150» не разделяют стоимость панелей и медиа.
2. Использовать достаточно независимых точек для выбранного числа коэффициентов. Показать fit, остатки, взаимодействия и 95% prediction interval. При недостатке данных коэффициент остаётся unknown; при насыщении модель разделяется на режимы.
3. Не менее трёх точек/повторов сохранить для holdout, включая 50 операторов/150 звонков. Относительная ошибка прогноза CPU/RAM на валидных отложенных точках должна быть не более 20%. Иначе использовать локальную таблицу измерений, не выдавать формулу за проверенный прогноз.
4. Для рекомендуемой конфигурации повторить основные SLO, запись и SOAK. Хороший fit при плохой задержке панели не является capacity acceptance.
5. Привязать рекомендации к аппаратному классу, версиям, БД, объёму данных, codec/ptime, записи и retention. За диапазоном измерений ставить extrapolated/unverified. Отдельно рассчитать single-host и раздельные PBX/DB/backend; N+1 подтверждается только отдельным failover-тестом.

Обязательная карта заполняется после измерений. Сейчас в ней нет выдуманных vCPU/RAM:

| Точка | Операторы / супервизоры | Соединённые / ожидающие | Особенности | vCPU / RAM / диск / сеть | Основание |
|---|---:|---:|---|---|---|
| L10 | 10 / 1 | 10 / 20 | Параметры профиля | Заполнить из замера | CAL / holdout |
| L25 | 25 / 1 | 25 / 50 | Параметры профиля | Заполнить из замера | CAL / holdout |
| L50-Q | 50 / 2 | 50 / 100 | S50 и MIX40/10 отдельно | Заполнить из замера | Q150 / SOAK |
| L50-M | 50 / 2 | 150 / 0 | 100 технических отвечающих абонентов | Заполнить из замера | M150 / SOAK |
| L50-W | 50 / 2 | 50 / 100 | W50, запись включена | Только после W50 | W50 / SOAK |
| За диапазоном | Любые | Например 300 суммарно | Явный профиль | Оценка без гарантии | Отдельный прогон |

Калькулятор принимает параметры §11.1 и выводит нагрузки по компонентам/узлам, рекомендуемые cores/GiB, GB записей в день/срок хранения, дисковую скорость и IOPS-ограничения, TX/RX/pps, бюджет DB pool, клиентские ресурсы отдельно, резерв и интервал достоверности. Формулы, единицы и источник каждого коэффициента открыты.

Обязательные выходы: `capacity-model.json` с версией, коэффициентами, единицами, runIds и диапазоном; `capacity.csv` с картой; `CAPACITY.md` с объяснениями и проверенными примерами. Табличный или CLI-калькулятор может дополнять эти машинно-читаемые выходы.

При фиксированных остальных входах:

```text
C_max = min(C_cpu, C_ram, C_net, C_disk, C_DB, C_latency_and_correctness)
```

Каждое слагаемое — граница для того же состава нагрузки. Если fan-out зависит от A*C, решать модель при заданном A, а не умножать два независимо найденных предела. `C_latency_and_correctness` может ограничивать систему при небольшом среднем CPU. Без успешного прогона соответствующая строка карты имеет статус not-accepted.

## 12. Управление прогоном и остановка

Перед запуском записать владельца, runId, target hosts/tenant, IDs созданных объектов, максимальные concurrency/rates/duration и deadline очистки. Тестовая телефония не выходит в PSTN. Чужие контейнеры, кабинеты и учётные записи не изменять; прежние артефакты не переписывать.

Остановить наращивание нагрузки и сохранить failure window при CPU >95% дольше 60 с, RAM >90% лимита 30 с или активном swapping, неограниченном backlog, 5xx/timeout >1% за 30 с, нарушении состояния/изоляции кабинетов. OOM, crash и потеря управления немедленно останавливают инжекцию. Это защитные пороги стенда; они не заменяют более строгие SLO. Stress выполняется только до назначенного предела.

Насыщение генератора, некалиброванные часы, незагруженные панели или несовпадающий baseline делают ячейку недействительной для соответствующего сравнения. Логи сохраняются. Продуктовый fail является действительным результатом fail и не выбрасывается ради повторений до успеха.

После запуска завершить свои звонки, park/hold/bridges, проверить 0 собственных SIP-диалогов, каналов и строк активных звонков; закрыть свои contexts/подписки, завершить свои смены после итогового сценария, сверить память/FD/сокеты/restarts. Постоянные тестовые данные оставлять только по принятой политике. Убрать временную измерительную сборку, проверить обычный UI/health, сохранить rollback. Receipt должна подтверждать фактическую очистку, а не только отправку SIGTERM.

## 13. Передаваемые материалы и порядок приёмки

| Материал | Обязательное содержание |
|---|---|
| RUN-MANIFEST | Версии/SHA/digests, матрица/seed, топология, ресурсы, политики, часы, происхождение данных |
| REPORT | Каждая ячейка/повтор, pass/fail/pending, задержки с покрытием и ошибками, ресурсы, SSE/WS и обоснование решения |
| BOTTLENECKS | Доказанные причины и гипотезы, корреляция, отдельные traces, воспроизведение |
| OPTIMIZATION-PLAN | Поля §10, зависимости, владельцы, риски, проверка, ожидаемый эффект без придуманных измерений |
| CAPACITY + JSON/CSV | Модель §11, holdout/погрешность, проверенные конфигурации, ограничения и клиентские ресурсы |
| HAR / receipts / metrics / media proof | Сырые события/задержки, исходы body, RTP/getStats, скриншоты настоящих панелей, все неудачи |
| CLEANUP / verification | Очистка своих звонков/сессий/подписок, здоровый runtime, снятие измерительной сборки, rollback/оставленные данные |

Поддерживаемые сценарии хранить в `harness/callcenter/` с README, версиями, явными входами/выходами, без секретов. В Git — ТЗ, назначенный execution plan, краткие принятые результаты и проверенные синтетические fixtures. Новые сырые результаты, записи, архивы, HAR и traces — во внешнем `ARTIFACTS_ROOT/runs/<initiative>/<run-id>/` через [artifact paths](../../../tools/artifacts/README.md). Итоговый документ содержит locator, hash/размер, команду, baseline, результат и ограничения. Пароли, JWT, SIP secrets и частные CDR не публиковать; query token SSE удалять из HAR/URL перед экспортом.

Порядок приёмки: (1) валидность стенда и популяции; (2) телефония/медиа/данные; (3) HTTP/event/DOM и команды; (4) SLO/повторяемость; (5) доказательства узких мест/плана; (6) калибровка ресурсов; (7) очистка. Каждый gate имеет свой статус. Открытие 52 соединений не заменяет пункты 3–6.

Для подготовки этого ТЗ достаточно проверки ссылок, размерностей/примеров и внутренней согласованности. При будущих изменениях кода обязательны `npm run lint`, `npm run test:backend`, `npm run test:frontend` и targeted/integration/live gates назначенного плана. Ошибка среды не считается test pass. Самопроверка исполнителя не называется независимым review.

## 14. Открытые входы перед исполнением

Подтверждены 50 отдельных операторских учётных записей с настоящими панелями. Два супервизора сверх них — явный параметр этого ТЗ; Q150 и M150 разделены.

Перед запуском заполнить manifest: конкретные hosts/owner/scope, целевые версии Asterisk/БД, доступные клиентские машины, codec/формат записи/retention, TURN/proxy/HTTP2, безопасную бизнес-политику auth, технических абонентов M150 и бюджет прогонов. Незаполненный параметр ограничивает соответствующий capacity claim. Допущения отмечаются явно и не подменяются выдуманными замерами.
