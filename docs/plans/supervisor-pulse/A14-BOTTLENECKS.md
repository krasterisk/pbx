# A14 — узкие места, подтверждённые прогоном `a14-cloud-20261028`

Уверенность отделена от гипотез. Предыдущий отчёт `707d803b` здесь только фон: каждый пункт ниже заново увиден 28 октября 2026 на сборке `f646e20a72a0`.

## Установлено

1. **Групповые пропущенные на PostgreSQL отвечают 500.** `GET /api/callcenter/agent/missed/grouped` вернул 500, в логе — `column "lastattemptat" does not exist`. Плоский `GET /api/callcenter/missed-calls` при этом 200. Каждая из шести открытых панелей получила ровно один 500. Причина та же, что уже локализована в коде: неквотированный `ORDER BY` алиаса, который PostgreSQL приводит к нижнему регистру. Уверенность высокая.

2. **Лимит входа — 10 запросов за 60 с на IP.** Пятьдесят логинов за 58,8 с с `127.0.0.1`: 7×200 и 43×429, `Retry-After: 60`, в заголовке успеха `limit=10`. Это явный `@Throttle` на логине. Общий модульный лимит 20 и композиция 60 на этот сценарий не сработали. Для NAT, где все операторы видны как один адрес, утренний сценарий ТЗ не проходит. Уверенность высокая.

3. **Чтения панели делят тот же IP-бюджет.** При разнесении логинов на 7 с страницы `op03`–`op06` всё равно получили 429 (всего 119 на шесть страниц) при сотнях успешных 200. Открытие одной панели делает порядка 80–90 запросов. Уверенность высокая по факту 429; какой именно guard из двух глобальных счётчиков отрезал каждый запрос, по заголовкам ответов 429 не видно (на 429 полей limit не было). Это уже граница наблюдения, не догадка о другом продукте.

4. **Шесть Vite-страниц не помещаются в запас RAM этой VM.** После `op06` доступная память была 3,5 ГБ при правиле остановки 4 ГБ. RSS headless Chromium — 7,7 ГБ на шесть страниц. Дальше cgroup OOM убил процессы Chrome. Backend при этом оставался в 526–560 МБ RSS. Предел здесь клиентский и совмещённый с сервером. Уверенность высокая для этого dev-стенда; переносить 1,3 ГБ на production-страницу нельзя.

5. **Ожидание в очереди этого стенда обрывается через 300 с.** В `queue_log` 101 событие `EXITWITHTIMEOUT` при 150 `ENTERQUEUE` и 49 `CONNECT`. Dialplan лабораторный: `Queue(q8000_2,t,,,300)`. Это ограничение сценария стенда, не измеренный продуктный таймаут очереди клиента. Уверенность высокая.

6. **Набор 150 вызовов на 4 ядрах на короткое время занимает весь CPU хоста, удержание уже нет.** В окне 20:22–20:27 KRAT p50 CPU 27%, p95 100%, выше 95% только 49 срезов из 248. Генератор RTP, Asterisk и браузеры сидят на тех же ядрах, поэтому 27% и 100% нельзя разложить по компонентам. Уверенность в цифрах хоста высокая, в доле приложения — низкая.

## Гипотезы

- Поле `W:0` при заголовке `has 101 calls` — особенность строки `queue show` этой сборки Asterisk 20.6, а не ноль ожидающих. Бейдж панелей и `EXITWITHTIMEOUT` показывают около 100 ожидающих. Причину поля `W` отдельным разбором исходников Asterisk этот прогон не закрыл.
- Длинный обход DOM (секунды на шесть страниц) может быть и перегрузкой страницы, и ценой Playwright под нехваткой RAM. Без меток `t0`–`t4` это не доказывает медленный SSE.
- `qualify_frequency=10` уже стояло в БД с прошлого лабораторного прогона. Быстрый переход в `Avail` не доказывает штатные 60 с.

## Что этим прогоном не доказано

Нет профиля event loop Node, нет разложения fan-out SSE по типам событий на 50 потоках, нет сравнения с WebSocket, нет стоимости записи и транскодинга, нет отдельной машины клиентов. Полные снимки и их число, которые обсуждались в прошлом отчёте, здесь заново не посчитаны: инструментация потоков на шести страницах не сохранилась, процесс браузера был убит по OOM до сброса счётчиков.
