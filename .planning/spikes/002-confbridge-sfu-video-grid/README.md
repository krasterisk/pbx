# Spike 002: ConfBridge SFU video grid

## What This Validates

Сетка видео — обязательная часть v1 (**D-22**, **D-24**). Спайк проверяет, даёт ли её нативный
`video_mode=sfu` с браузерными клиентами на стеке, который уже есть в продукте (`sip.js@0.21.2`
из Phase 10), и что для этого требуется от эндпоинта, от клиента и от способа хранения настроек.

## Research

Перед сборкой — документация Asterisk и разбор исходников `sip.js`. Четыре факта определили конструкцию:

| Источник | Факт | Следствие для спайка |
|----------|------|----------------------|
| asterisk.org (Multi-stream Media and SFU) | Эндпоинту нужен `max_video_streams` > 1 (обычно 10–15), потолок bundled pjproject — 16 потоков суммарно | эндпоинты заводятся с `max_video_streams=10` |
| community.asterisk.org | Asterisk — B2BUA и не наращивает сессию надёжно; клиент обязан объявить все нужные m-lines в первом оффере | в peer connection заранее добавляются recvonly-видеотрансиверы |
| community.asterisk.org | `bundlePolicy` по умолчанию (`balanced`) заставляет Chrome отдать только одну пару дорожек | принудительно `max-bundle` |
| исходник `sip.js` (`session-description-handler.js`) | `setRemoteTrack` при каждом новом видеотреке **останавливает и выбрасывает** предыдущий | агрегированный `remoteMediaStream` непригоден для сетки; рендер идёт из `ontrack` напрямую |

Дополнительно из исходника: `addTrack` переиспользует трансивер только в состоянии `recvonly`/`inactive`,
а `updateDirection` в `stable` отображает `recvonly` сам в себя. Поэтому все слоты создаются
`recvonly` — камера сама занимает первый и переводит его в `sendrecv`.

## How to Run

```bash
node .planning/spikes/002-confbridge-sfu-video-grid/check-schema.js     # realtime схема: есть ли max_video_streams
node .planning/spikes/002-confbridge-sfu-video-grid/provision.js        # комната + два WebRTC-эндпоинта
node .planning/spikes/002-confbridge-sfu-video-grid/static-profile-test.js      # статический SFU-профиль → комната 9002
node .planning/spikes/002-confbridge-sfu-video-grid/probe-dynamic-vs-template.js # комнаты 9003 и 9004
node .planning/spikes/002-confbridge-sfu-video-grid/serve.js            # клиент на localhost
```

Затем открыть две-три вкладки и войти в комнату:

```
http://localhost:9002/?user=spike002a&fake=1&target=9004
http://localhost:9002/?user=spike002b&fake=1&target=9004
```

`fake=1` подставляет синтетический источник (канва с именем и часами + тон) вместо камеры —
так сетку можно проверить без вебкамер и с любым числом вкладок. Без параметра берётся камера.

Комнаты: **9001** — динамический `video_mode` (не работает), **9002** — статический профиль,
**9003** — динамический `max_members=1`, **9004** — динамический `template` поверх статического профиля.

Диагностика: `peek.js` (состояние Asterisk), `watch-events.js` (поток событий AMI),
кнопка «Выгрузить лог» в клиенте (события, SDP, полный SIP-обмен → `results/`).

Откат: `node .planning/spikes/002-confbridge-sfu-video-grid/teardown.js`.

## What to Expect

В журнале клиента — `m-lines: offer=7, answer=7`, затем плитки по одной на каждый входящий
видеопоток. В `confbridge list` — комната с участниками. В `getStats()` — `inbound-rtp video`
с растущим `framesDecoded`.

## Observability

Три независимых свидетеля, и они понадобились все:

1. **Перехват WebSocket** в клиенте (`window.__sipTrace`) — полные SIP-сообщения. Единственное,
   что вскрыло настоящую причину первого провала.
2. **`watch-events.js`** — события AMI. Показал отсутствие канала, чем отделил «Asterisk отказал»
   от «Asterisk не увидел».
3. **`peek.js`** — состояние сервера: каналы, комнаты, контакты, согласованные форматы.

## Investigation Trail

**Итерация 1 — тишина.** Первый INVITE не получил вообще никакого ответа, сессия умерла по
таймауту `408`. Событий AMI — ноль, канал не создавался. Гипотеза «отказ по правам» отпала:
ни одного события безопасности, и выяснилось, что AMI-пользователю не выдан класс `security`
(есть `call`, поэтому отсутствие `Newchannel` — надёжное свидетельство).

Попутно всплыл собственный баг: `registerer.register()` резолвится по **отправке** запроса, а не
по приёму `200 OK`, поэтому INVITE уходил раньше регистрации. Исправлено ожиданием состояния
`Registered`. На симптом это не повлияло — значит причина была в другом.

**Итерация 2 — провод.** Перехват WebSocket показал: `REGISTER` → `401` → `REGISTER` → `200 OK`,
Asterisk даже шлёт `OPTIONS` на наш контакт. Регистрация исправна. А INVITE несёт
**`Content-Length: 36994`** — 37 КБ. Шесть видео-m-lines, в каждой полный список из ~42 кодеков
со всей обвязкой. PJSIP отбрасывает слишком большие сообщения **молча**: ни ответа, ни лога, ни события.

**Итерация 3 — сужение кодеков.** `setCodecPreferences` на каждый видеотрансивер (VP8 + rtx) и на
аудио (opus/PCMU) ужал INVITE до 10 494 байт. Asterisk ответил `100 Trying` → `200 OK`,
`offer=7, answer=7` — все шесть видеопотоков согласованы, ICE подключён. Комната `conf9001_0`
поднялась, тенантное имя по схеме **D-06** принято без нареканий.

**Итерация 4 — звук есть, видео нет.** Оба участника **отправляют** видео (292 КБ / 224 кадра и
583 КБ / 482 кадра), звук ходит в обе стороны, а входящего видео нет ни у кого. При этом на
канале `NativeFormats: (opus|vp8)` и присутствуют потоки `softbridge_dest_*`, то есть микшер
видео знает. Зацепка: `confbridge list` показывал **`default_bridge`**, у которого из спайка 001
известно `Video Mode: no video`.

**Итерация 5 — решающий A/B.** Тот же клиент, те же кодеки, отличается только источник профиля.
Статический профиль в `confbridge.conf` (`video_mode=sfu`, применён `module reload app_confbridge.so`)
→ **видео пошло**: `inbound-rtp video`, 163 КБ, 140 декодированных кадров. Динамический
`Set(CONFBRIDGE(bridge,video_mode)=sfu)` → ноль. Причина найдена.

**Итерация 6 — насколько это фатально для D-02.** Два разделяющих опыта:

- комната 9003 с `Set(CONFBRIDGE(bridge,max_members)=1)`: второй участник получил `200 OK`,
  подключился и через две секунды получил `BYE` — **динамические опции работают**;
- комната 9004 с `Set(CONFBRIDGE(bridge,template)=spike_sfu_bridge)`: **видео пошло**
  (165 КБ, 131 кадр) — динамический профиль наследует `video_mode` от статического шаблона.

Значит сломана не динамика вообще, а конкретно `video_mode` как динамически задаваемая опция.

**Итерация 7 — видео идёт, но экран чёрный.** `getStats()` рапортует растущий `framesDecoded`
на `mid=video-7`, а `<video>` этой плитки показывает `videoWidth=2`, `currentTime=0`. Трек в
элементе — тот самый, что у приёмника (сверено по `id`), но у него `readyState: "ended"`.
Декодер считает кадры, приёмник их получает, а сток мёртв.

Виновник был выписан ещё в Research, но недооценён: `setRemoteTrack` не просто «выбрасывает»
прошлый видеотрек — он вызывает у него `stop()` (строки 592–601), и делает это **до** вызова
делегата (строка 886 против 888). То есть рендер из `ontrack` сам по себе не спасает: к моменту,
когда обработчик получает управление, все прежние видеотреки уже убиты библиотекой. В снимке
состояния это выглядело однозначно — `live` ровно один трек, последний пришедший, остальные
девять `ended`.

Лечится подменой метода на экземпляре SDH: `remoteMediaStream` продукту не нужен, сетка рендерится
из трансиверов. После подмены живыми остаются все десять треков.

**Итерация 8 — мёртвые каналы душат живых.** Отдельно от библиотеки: перезагрузка вкладки не шлёт
`BYE`, канал остаётся участником конференции и продолжает занимать слот SFU. Накопилось 11 таких —
и живые участники перестали получать видео вовсе. После `hangup-stale.js` видео пошло в ту же
секунду, без единого изменения в конфигурации. В клиент добавлен `pagehide` → `bye()`.

## Results

**Вердикт: VALIDATED.** Нативный SFU раздаёт видео браузерным участникам, все шесть слотов
согласуются в одной сессии, `sip.js@0.21.2` для этого пригоден. Внешний SFU **не нужен** —
запасной вариант из D-22 не задействуется.

Сетка подтверждена картинкой с обеих сторон: у каждого участника своя плитка соседа, VP8 640×480,
часы на удалённой плитке отстают от локальных примерно на 60 мс. Доказательства —
`results/grid-verified.json`.

### Поправка к D-02 (важное)

`video_mode` **нельзя** задать динамически. Рабочая схема — гибрид:

- платформа держит **маленький набор статических bridge-профилей** в `confbridge.conf`
  (по сути один: `video_mode=sfu` + `enable_events=yes`), они не тенантные и почти не меняются;
- тенантные настройки комнаты (лимиты, PIN, меню, поведение модератора, запись) едут
  **динамикой** поверх через `Set(CONFBRIDGE(bridge,template)=<профиль>)` — это проверено и работает.

Практическое следствие для планирования: к диалплан-генерации добавляется **разовая операционная
задача** — завести статический профиль и перезагружать его через `module reload app_confbridge.so`,
а не `dialplan reload`. Ловушка про `confbridge.conf`, снятая на discuss, возвращается — но в
сильно урезанном виде: файл платформенный, не тенантный, и пишется один раз.

### Жёсткое ограничение: размер INVITE

Наивная сетка **ломает SIP-сообщение**. Данные с этой сборки: **37 КБ — молча отброшен**,
**10.5 КБ — принят**. Отсюда для фазы:

- каждый видео-слот обязан нести **один кодек** (`setCodecPreferences`), иначе оффер не влезет —
  это прямо связывает **D-25** («единый видеокодек фиксирует платформа») с работоспособностью, а не
  только с совместимостью: единый кодек здесь **условие того, что звонок вообще состоится**;
- число слотов — это бюджет размера сообщения, а не только нагрузки; 6 слотов на VP8 ≈ 10.5 КБ;
- отладочная ловушка: превышение не даёт ни ошибки, ни лога. Любой будущий баг «звонок в комнату
  не проходит и в логах пусто» надо в первую очередь проверять на размер INVITE.

### Стоковый `sip.js` сетку не отдаёт — и молча

Библиотека рассчитана на звонок один-на-один и держит ровно один удалённый видеотрек: каждый
новый `ontrack` останавливает предыдущий, до того как приложение что-либо увидит. Для фазы это
означает **обязательный собственный SessionDescriptionHandler** (или подмену `setRemoteTrack`),
иначе сетка невозможна в принципе — сколько бы слотов ни согласовалось.

Коварство в том, как это выглядит: сессия установлена, кодеки согласованы, `framesDecoded` растёт,
статистика здоровая — а плитки чёрные. Ни ошибки, ни предупреждения. Признак, по которому это
опознаётся: у приёмника `track.readyState === 'ended'` при живом `inbound-rtp`.

### Мёртвые участники отнимают слоты у живых

Канал без `BYE` остаётся в конференции и держит слот SFU. Накопление таких каналов **полностью
лишает живых участников входящего видео** — раньше, чем упрётся в `max_members`. Для фазы это
две задачи: слать `BYE` при закрытии вкладки на клиенте и подчищать зависшие каналы на сервере
(по событиям `ConfbridgeLeave`/таймауту, а не вручную).

### Что это значит для ворот ресёрча

- **R-VIDEO — закрыт.** Нативный `video_mode=sfu`, кодек **VP8** (проверен в бою; H.264 доступен
  как альтернатива, `res_format_attr_vp9` в сборке нет). Сетка получается, внешний SFU не нужен.
- **R-ENGINE — сильно сдвинут в сторону ConfBridge.** Он раздаёт видео сеткой из коробки, а
  собственный ARI-бридж потребовал бы воспроизводить это вручную. Окончательное сравнение — спайк 004.
- **R-CAPACITY** — появился первый ориентир: ~10 fps VP8 на участника в тесте, при 2 ГБ RAM на сервере.

### Побочные подтверждения

- **D-06:** имя `conf9001_0` Asterisk принимает, в `confbridge list` читается нормально.
- **D-21:** участник сверх лимита получает `200 OK`, слышит объявление и затем `BYE` — то есть
  «отказ с объяснением» реализуем штатными средствами, без доработок.
- **D-02 (в части диалплана):** генерация контекста через `CreateConfig`/`UpdateConfig` +
  `dialplan reload` отработала ровно как в `DialplanApplyService`, без сюрпризов.
- Сегодняшний профиль `NAT_PROFILES.webrtc` в `endpoints.service.ts` **не годится** для видео:
  в нём нет ни `max_video_streams`, ни видеокодеков в `allow`. Расширение этого профиля — задача фазы.

### Открытое (не входило в вопрос спайка)

Проверка велась на двух участниках: сетка доказана как механизм и подтверждена картинкой, но
поведение на **многих** плитках сразу — нет. Открытыми остались вопросы масштаба, а не
принципа: сколько плиток тянет сервер с 2 ГБ RAM, как ведёт себя раскладка при входе и выходе
участников на ходу, и что происходит, когда отправителей больше, чем заготовленных слотов
(Asterisk добавляет свои m-lines через re-INVITE — второй участник приехал на `video-7`, а не
на заготовленный `2`). Это материал для спайка по ёмкости (R-CAPACITY), а не для этого.
