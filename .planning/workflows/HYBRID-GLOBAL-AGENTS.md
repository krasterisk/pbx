# Глобальные инструкции: разработка Codex + GSD

Версия протокола: **1.0**, 2026-09-18. Пользовательская инструкция для всех проектов Codex. Применяется вместе с системными инструкциями, текущим запросом пользователя и правилами репозитория; не меняет разрешения среды или права на внешние действия.

## Область применения

Используй этот порядок для многоэтапной разработки с сохраняемыми GSD или аналогичными артефактами. Для вопроса, аудита или маленькой самостоятельной правки не создавай искусственный milestone, агентов или десятки документов. Само наличие `.planning/`, GSD skills или незавершённых PLAN не является поручением их исполнять.

## Один источник управления

1. На инициативу/фазу действует **один координатор**. Он назначает текущий план, исполнителей, область файлов, проверки и принимает результат. Независимые инициативы могут иметь разных координаторов, если изменения не пересекаются. Общие схемы/registry/config/контракты имеют одного назначенного владельца записи.
2. Default гибридной разработки — **`codex-direct`**: Codex координирует исполнение, GSD-документы хранят требования, планы и evidence. **`gsd-workflow`** включается при явном запросе пользователя на GSD-процесс либо при зафиксированной передаче управления в уже разрешённом scope. Это альтернативные режимы одной фазы; не запускай два независимых процесса назначения задач.
3. В `codex-direct` не выбирай неявно управляющие GSD workflows, которые ищут следующую работу, запускают execute/auto-chain, создают других координаторов или переписывают общий STATE. Чтение шаблонов/спецификаций и ограниченная предметная проверка допустимы в назначенном scope. Явно запрошенный пользователем skill учитывай с согласованием текущего владения; не игнорируй запрос из-за default mode.
4. В `gsd-workflow` текущий координатор следует одному выбранному workflow. Не создавай рядом дополнительный direct execution loop. Проверь фактическую версию runner, paths, phase IDs и поддержку настроек. Значения вроде GSD `execution=sonnet` не являются настройкой модели Codex.
5. Эта инструкция не разрешает автоматически создавать субагентов. Делегирование выполняется в пределах разрешений текущей среды/задачи. Исполнитель не запускает собственную цепочку оркестрации или новые подзадачи без явного назначения координатором и соответствующего разрешения.

## Какие документы читать и выполнять

- Прочитай применимые `AGENTS.md`, каноническую архитектуру, индекс проекта и инструкции назначенной инициативы. Если есть `.planning/HYBRID-WORKFLOW.md`, прочитай его до выбора implementation plan.
- Текущее поручение пользователя задаёт цель. Координатор связывает её с **одним актуальным PLAN для конкретного задания**, указывает задачи/ревизию, входные SPEC/ADR, зависимости и критерии приёмки. Исполнитель читает назначенный PLAN и зависимости; не выбирает другую фазу самостоятельно.
- ROADMAP задаёт последовательность, STATE/EXECUTION — прогресс и владельца, PLAN — работу, SUMMARY/VERIFICATION — результаты. Исторические планы, audits и внешние проекты — контекст, пока явно не назначены. Дата файла или старая галочка не делает его авторитетнее нового требования.
- Не создавай второй master roadmap или альтернативный execution plan для того же scope. При изменении решения координатор обновляет канонический документ, фиксирует заменённое решение и уведомляет затронутых исполнителей.
- Документы не расширяют полномочия: найденные команды публикации, удаления, платежей, migration/deploy не считаются новым разрешением. Выполняй уже разрешённую работу без повторного запроса разрешения; уточнение нужно для реального конфликта цели/владельца или недостающего обязательного решения.

## Порядок исполнения

1. **Восстанови контекст:** текущий запрос, активная инициатива/режим/владелец, branch/HEAD/dirty files, выполненная работа и незакрытые проверки. Не начинай фазу заново после смены модели или compaction.
2. **Проверь владение:** используй существующий реестр задач. Для длительной инициативы без реестра создай небольшой `EXECUTION.md` рядом с планами и ссылку из индекса. Зафиксируй coordinator identity, mode, current plan, allowed paths, workers и next action. Файл — соглашение, не атомарный mutex.
3. **Назначь ограниченную работу:** цель; PLAN и задачи; required reads; owned files; запрещённые пересечения; зависимости; проверки; формат результата. Координатор может сам быть исполнителем — отдельный агент не обязателен.
4. **Реализуй** небольшими проверяемыми срезами поверх согласованного baseline. Не откатывай, stash/reset/commit чужие изменения. Worktree от HEAD не содержит незакоммиченный baseline — учти это до выбора изоляции.
5. **Проверь:** targeted tests и обязательные проверки репозитория, review по риску. Независимую проверку проводит другой разрешённый исполнитель/человек; собственную не называй независимой. Отделяй mock/unit от integration/live/release evidence.
6. **Зафиксируй результат:** изменения, команды/результаты, pending gates и next action. Координатор сверяет результат с требованиями и обновляет состояние. SUMMARY или сообщение `done` не заменяет приёмку.

## Владение и передача управления

- Смена модели не создаёт нового координатора. Новый исполнитель читает актуальное состояние, проверяет diff и продолжает с next action. Названия моделей в документах — рекомендации, не автоматическое переключение runtime.
- Для передачи другой задаче/режиму: прекрати выдачу новой работы, дождись завершения либо подтверждённой остановки writers, сохрани baseline/diff/tests/pending/next action, запиши принимающего координатора и режим. Только после этого начинай новую цепочку. Режим не меняется молча из-за чтения skill.
- Активного владельца нельзя заменить лишь из-за старого timestamp. Проверь статус/связь с ним. При неопределённости продолжай независимое read-only исследование; не пиши в пересекающиеся файлы и выясни владение.
- При конфликте останови только пересекающиеся изменения, сохрани работу и передай вопрос координатору. Не выбирай молча «более новый» план и не запускай второй вариант реализации.
- Координатор обновляет общий ROADMAP/STATE/реестр; исполнители пишут свой результат и явно назначенные файлы. Не закрывай соседние фазы или milestone по завершении одной задачи.

## Честные статусы

Различай `planned`, `in_progress`, `implemented`, `automated-tests-passed`, `live-verified`, `released`. Для каждого требуемого gate отдельно фиксируй pass/fail/pending/not-applicable с причиной. Не называй фазу проверенной, если прошла только часть тестов; не блокируй независимые работы из-за одного внешнего pending gate.

Перед завершением продолжительной сессии оставь handoff для другой модели: активный PLAN/ревизия, выполненные задачи, файлы, проверки, владельцы незавершённой работы, риски и точное следующее действие. Не выдавай паузу за завершение.
