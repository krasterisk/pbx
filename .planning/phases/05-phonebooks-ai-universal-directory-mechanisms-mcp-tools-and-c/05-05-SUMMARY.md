# Phase 05 Plan 05: Phonebook Bindings Backend Foundation Summary

**Per-binding dialplan pipeline (`pb_bind_{uid}_{vpbx}`) wired end-to-end: `route_phonebook_bindings` table + Sequelize model, bindings CRUD on routes with replace-all + tenant validation, 7 behavior-preset dialplan generation, `RouteApplyService` two-phase apply (bindings then route context, single reload), var-key/binding/delete regen triggers, and a tenant-checked `lookup-test` endpoint.**

## Performance

- **Tasks:** 3/3 completed
- **Files modified/created:** 20 (7 created, 13 modified)
- **Completed:** 2026-07-14

## Accomplishments
- Phonebooks are now pure data (`entries` only); `invert`/`actions` fields removed from model, shared types, and DB (idempotent migration drop)
- `route_phonebook_bindings` table + `RoutePhonebookBinding` model connect a route to a phonebook with `position`, `match_mode`, `behavior_type`, `behavior_params`, `actions`
- Routes' create/update accept a `bindings[]` array persisted with replace-all semantics; GET returns bindings sorted by `position` ASC; foreign-tenant `phonebook_uid` references are rejected
- `generateBindingDialplan` renders a `pb_bind_{uid}_{vpbx}` Asterisk context per binding: CURL lookup → match/no-match branch → `Set(PB_*)` vars → one of 7 behavior presets (set_name, set_number, blacklist, whitelist, redirect×2, custom, vars_only)
- `RouteApplyService.applyContext` writes binding categories to `krasterisk/phonebooks/pb_{vpbx}.conf` (no reload) before writing/reloading the route context — closing the runtime gap where dialplan generation was never invoked
- Var-key set changes, binding changes, and phonebook deletion all trigger re-apply of every affected route context; delete additionally `DelCat`s orphaned `pb_bind_*` categories
- `POST /api/phonebooks/:id/lookup-test` returns `{ matched, vars }`, gated by a tenant-scoped `findOne` before the actual lookup

## Decisions Made
- Bindings CRUD tests live in `routes.service.spec.ts` (not `phonebooks.service.spec.ts` as the plan's task-2 behavior section suggested) since bindings are owned by `RoutesService`; lookup-test tests live in a new `phonebooks.controller.spec.ts` since that's where the endpoint and its tenant guard actually run. This keeps each spec file testing the unit that owns the behavior.
- Module wiring avoided `forwardRef` between `PhonebooksModule` and `RoutesModule` by registering the shared models (`RoutePhonebookBinding`, `RoutePhonebook`, `PhonebookEntry`) via `SequelizeModule.forFeature` in both modules, and by extracting `generateBindingDialplan`/`collectAllVarKeys` into a standalone util file consumed by both `PhonebooksService` and `RouteApplyService` — this fully sidesteps a circular-dependency risk without runtime `forwardRef` indirection.
