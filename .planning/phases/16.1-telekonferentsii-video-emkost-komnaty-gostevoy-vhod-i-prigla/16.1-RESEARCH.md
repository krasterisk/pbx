### Locked Decisions

**Гостевой вход по ссылке**
- **D-10:** Чем является гость технически (эфемерный PJSIP-абонент на сессию против общего guest-абонента против канала, созданного через ARI) — решается ресёрчем вместе с R-ENGINE.
- **D-11:** Строгость входа — **настройка комнаты** с тремя уровнями: токен + имя; плюс PIN комнаты; плюс одобрение модератором (комната ожидания).
- **D-12:** Ссылки **двух видов одновременно**: общая ссылка комнаты с TTL и отзывом плюс именные приглашения (видно, кто вошёл, можно отозвать точечно). Прецеденты opaque-токена в проекте: `cc_display_tokens` + `DisplayTokenGuard` и `vm_access_tokens`.
- **D-13:** Поведение, когда гость пришёл раньше модератора, — **настройка комнаты**: ожидание модератора, свободный вход, а также завершение конференции при выходе модератора. В ConfBridge это `wait_marked` и `end_marked`.

**Ёмкость**
- **D-18:** Доступный максимум — **минимум из потолка тарифа и живого остатка сервера**. Тенант никогда не видит, какое из двух ограничений сработало.
- **D-19:** Набор метрик живой нагрузки и веса участника предлагает ресёрч (R-CAPACITY).
- **D-20:** Тенанту показывается **только число, формулировкой «Максимальное число участников: N»** — дословно по требованию пользователя, без слов «сейчас доступно» и без единого упоминания сервера. Следствие для планирования: число считается динамически и **может меняться между просмотрами**, поэтому окружающие тексты не должны обещать, что оно постоянно.
- **D-21:** Участник сверх лимита получает **отказ с объяснением** — голосовое объявление в трубку, понятная ошибка в вебе. Деградация «пустить без видео» отклонена.

**Видео**
- **D-22:** Видео — **обязательная часть v1**, вплоть до внешнего SFU, если нативного режима не хватит.
- **D-23:** Видео доступно **веб-участникам и аппаратным телефонам**, но веб в приоритете как управляемая среда. Аппарат получает видео **только если совпал видеокодек**, иначе участвует звуком. Важно: это штатное поведение ConfBridge, а не дополнительная работа — он **не MCU** и видео не транскодирует.
- **D-24:** Раскладка — **сетка всех участников**. Требует многопоточного режима; отсюда вес R-VIDEO.
- **D-25:** Единый видеокодек **фиксирует платформа**, тенант этой настройки не видит вообще. Конкретный кодек — по итогам R-VIDEO.

**Приглашения и имена**
- **D-38:** Механизм приглашения абонента в комнату (AMI `Originate` против ARI `createChannel` + `addChannelToBridge`) — **по итогам R-ENGINE**, должен совпасть с движком.
- **D-39:** Кто может приглашать внешний номер (это исходящий вызов за деньги тенанта) — **настройка комнаты**.
- **D-40:** Смена отображаемого имени: **гостю запоминается по токену**, своим — только на время встречи. Карточка абонента и справочники при этом **не перезаписываются** никогда.

**Закрытия ресёрча Phase 16, обязательные для 16.1 (не переоткрывать)**
- R-ENGINE закрыт: ConfBridge + AMI. D-10 и D-38 фиксируются на ConfBridge / AMI `Originate`.
- R-VIDEO закрыт: нативный `video_mode=sfu`, кодек VP8. Внешний SFU не нужен.
- R-CAPACITY закрыт: ёмкость — бюджет полосы N·(N−1) потоков ≈ 800 кбит/с; вес нового участника = `2n` новых потоков.

- D-06: тенантное имя комнаты — `conf{номер}_{uid}`.

## Summary

Phase 16 уже отгрузила комнату, тенантный диалплан, роли, SSE и подметальщик каналов. Таблица `conference_guest_tokens` и колонки `tariff_max_participants` / `invite_external_scope` существуют, но **не обслуживаются**: нет guard, join/leave, ephemeral PJSIP, пересчёта ёмкости, Originate-приглашения, ingest телеметрии. `NAT_PROFILES.webrtc` по-прежнему без `max_video_streams` и без VP8.

Гость обязан быть отдельным realtime-триплетом `ps_endpoints`/`ps_auths`/`ps_aors` с `context = krsk-conf-{room_uid}` — скомпрометированный SIP-креденшл физически не умеет ничего, кроме `exten => s` этой комнаты. Отзыв токена не может ограничиться `revoked_at`: синхронно `ConfbridgeKick` и `destroy` триплета. Ёмкость — чистая функция бюджета потоков плюс тариф комнаты; в REST наружу уходит одно число. Видео сеткой на backend — это провижининг `max_video_streams` + `allow` с VP8; клиентский SDH остаётся Phase 16.3.

**Primary recommendation:** не ставить новых npm-пакетов. Расширить `NAT_PROFILES.webrtc` + backfill `ew*`; отдельный `createEphemeralGuestEndpoint`; токены как `DisplayTokenGuard`/`vm_access_tokens`; ёмкость — `min(tariff, maxParticipantsForBudget)` + `AmiService.originate()` для приглашений.

### Pattern 3: Ёмкость как бюджет потоков (D-18…D-21)

Формула спайка 004 (не пересчитывать): N участников с видео = `N*(N-1)` потоков; вход при текущих `n` стоит `2n` новых потоков; ~800 кбит/с на поток. [CITED: .cursor/skills/spike-findings-krasterisk-v4/references/room-capacity.md]

```typescript
export const STREAM_KBPS = 800;
export function maxParticipantsForBudget(budgetStreams: number): number {
  if (budgetStreams < 0) return 0;
  return Math.floor((1 + Math.sqrt(1 + 4 * budgetStreams)) / 2);
}
export function streamsForParticipants(n: number): number {
  return n <= 1 ? 0 : n * (n - 1);
}
```

`effectiveMax(room) = min(tariff_max_participants ?? +∞, maxParticipantsForBudget(remainingStreams + streamsForParticipants(nThisRoom)))`

`tariff_max_participants` уже на комнате. [VERIFIED: packages/backend/src/modules/conferences/models/conference-room.model.ts:65-66] quote: `declare tariff_max_participants: number | null;`

Живой tally: `ConferenceStateService.getActiveRoomUids()` + `getSnapshot(uid).participants.length`. [VERIFIED: packages/backend/src/modules/conferences/conference-state.service.ts:192-196] quote: `return [...this.rooms.entries()].filter(([, members]) => members.size > 0)`

Не считать CBAnn в населении комнаты — state уже только участники Join.

Платформенная полоса: env `CONFERENCE_UPLINK_KBPS` (не `MANAGED_KEYS`: там только `records_base_path`, `records_base_url`, `webhook_secret`). [VERIFIED: packages/backend/src/modules/system-settings/system-settings.service.ts:11] quote: `export const MANAGED_KEYS = ['records_base_path', 'records_base_url', 'webhook_secret'] as const;`
Стартовый дефолт `100000` (= 100 Мбит/с → N≈12) — [ASSUMED] как рабочее значение со стенда, не продуктовый тариф.

Диалплан сегодня пишет `max_members` только из тарифа. [VERIFIED: packages/backend/src/modules/conferences/conference-dialplan.util.ts:93-96] quote: `const maxMembers = room.tariff_max_participants;` / `Set(CONFBRIDGE(bridge,max_members)=${Math.trunc(maxMembers)})`

**REST:** `GET /conferences/:uid/capacity` → `{ maxParticipants: number }` только. Считать на лету. Копирайт «Максимальное число участников: N» — фронт 16.3 / локали; backend не обещает константу.

**D-21 web:** до создания endpoint сравнить `n+1 > effectiveMax` → `409` `{ code: 'CONFERENCE_ROOM_FULL' }`. Без «без видео».

**D-21 SIP:** штатный `max_members`. Официально: после лимита комната **запирается**, пока кто-то не выйдет; **Admin всегда входит**. [CITED: https://docs.asterisk.org/Latest_API/API_Documentation/Module_Configuration/app_confbridge/] quote: `After the limit is reached, the conference will be locked until someone leaves. Note however that an Admin user will always be allowed to join the conference regardless if this limit is reached or not.`
Владелец/модератор с `admin=yes` обойдут лимит — это допустимо; гость и participant — нет.

## Common Pitfalls

### Pitfall 1: `max_video_streams` остаётся 1
**What goes wrong:** звук есть, сетки нет, ошибок нет.
**Why:** default Asterisk = 1; `NAT_PROFILES.webrtc` поле не ставит.
**How to avoid:** профиль + guest create + backfill `ew*`.
**Warning signs:** один inbound video track при 3+ участниках.

### Pitfall 2: Guest `context` = `from-internal{vpbx}`
**What goes wrong:** украденный SIP-пароль звонит по плану тенанта.
**Why:** копипаст `createCompanionTriple` (`context: primary.context`).
**How to avoid:** жёстко `krsk-conf-{uid}`; тест: в контексте нет `_X.`.
**Warning signs:** guest INVITE на 9XX уходит в маску.

### Pitfall 3: Admin обходит `max_members`
**What goes wrong:** модератор входит в «полную» комнату; гость — нет; цифры расходятся.
**Why:** официальный bypass Admin.
**How to avoid:** web-admission для всех не-admin; в UI не обещать, что owner получит 409.
**Warning signs:** owner в комнате при `n > maxParticipants`.

### Pitfall 4: Revoke без kick
**What goes wrong:** HTTP 401, а медиа живёт.
**Why:** SIP-сессия независима от строки БД.
**How to avoid:** одна транзакция revoke: stamp + kick + destroy.
**Warning signs:** отозванный гость остаётся в SSE snapshot.

### Pitfall 5: Guest `req.user.sub`
**What goes wrong:** гость проходит `assertLiveRoomAccess` / moderation.
**Why:** копипаст JWT payload.
**How to avoid:** как DisplayTokenGuard — без `sub`/`level`.
**Warning signs:** guest POST `:uid/moderators` = 200.

### Pitfall 6: Route `GET conferences/:uid` ест `guest`
**What goes wrong:** 400 ParseInt на `/conferences/guest/...`.
**Why:** class-level JWT + `:uid`.
**How to avoid:** отдельный controller `conferences/guest`, зарегистрировать первым.

### Pitfall 7: `EndpointsService.remove` на `gst*`
**What goes wrong:** 400 «Delete the primary».
**Why:** метод заточен под e/ew пару.
**How to avoid:** отдельный destroy.

### Pitfall 8: Глобальный throttler душит SSE/telemetry
**What goes wrong:** 429 на heartbeat.
**Why:** `ThrottlerModule.forRoot([{ name: 'global', ttl: 60000, limit: 60 }])`. [VERIFIED: packages/backend/src/app.module.ts:217-219]
**How to avoid:** `@SkipThrottle()` на SSE и telemetry; join оставить под лимитом.
