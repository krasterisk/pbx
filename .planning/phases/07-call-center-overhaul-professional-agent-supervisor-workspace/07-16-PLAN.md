<objective>
Заложить **AI-ready фундамент** модуля колл-центра: контракты и точки расширения, а НЕ полноценные AI-фичи. Плита состоит из четырёх скелетных элементов, переиспользующих уже существующие в репозитории паттерны (`phonebooks`, `voice-robots`, `ai-platform`, `cloud-admin/billing`):

1. **Типизированный CC event bus (D-41a)** — дискриминированный union `CcEventBusEvent` поверх существующего `CallCenterStateService` RxJS Subject; runtime не меняется, добавляется type-safe надстройка + slot `media.pcmFrame` для будущей транскрипции.
2. **`CallCenterAiAdapter` + MCP/AI-инструменты (D-41b)** — по эталону `PhonebooksAiAdapter`, самрегистрация через `AiAdapterRegistryService`; `vpbxUserUid` строго параметром handler (закрывает deferred gap backend ARCHITECTURE §6).
3. **Каркас ARI externalMedia (D-41c)** — «канал → PCM-поток» через переиспользование `RtpUdpServerService` + `AriHttpClientService` из `voice-robots`, БЕЗ STT: только эмит `media.pcmFrame` в event bus как точка подписки будущего платного модуля.
4. **License-gate платного AI-модуля (D-43)** — изоляция через уже существующий механизм `@RequiresModule` + `ModuleAccessGuard` + `ModulesRegistryService` (переиспользование billing-инфраструктуры), без резервирования полей в схеме КЦ (D-42/D-44).

Purpose: дать будущим платным AI-модулям (речевая аналитика, голосовые ассистенты — отдельные фазы) готовые точки подключения — подписку на типизированный поток событий, media-скелет и license-gate — не реализуя саму AI-логику в этой фазе (D-42, D-44).

Output: 1 новый типовой файл + 1 новый адаптер + 1 новый media-service + расширение `callcenter-state.service.ts`/`callcenter.module.ts` + 3 spec-файла. НИКАКИХ изменений схемы БД, НИКАКОГО STT, НИКАКОГО ai-agent-type.
</objective>
