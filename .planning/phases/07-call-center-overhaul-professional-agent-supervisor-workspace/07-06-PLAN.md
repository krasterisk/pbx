<objective>
Backend-слой конфигурируемых карточек звонка (Call Cards) — схема, миграции, CRUD и CRM-webhook при сохранении. Это фундамент, на котором Wave 3 (07-11) строит DnD-конструктор шаблонов и runtime-карточку у оператора.

Реализуется:
1. Три модели + миграция: `cc_card_templates` (шаблон + `auto_open_on` answer/ring/manual — D-12 + привязка к `notification_integration` для CRM-webhook — D-13), `cc_card_fields` (настраиваемые поля шаблона, набор типов v1 — D-11), `cc_card_data` (сохранённые значения карточки, привязка к `call_uniqueid`).
2. CRUD: `CallCenterCardsService` + `CallCenterCardsController` + DTO — шаблоны (мутации только для супервизора, `assertSupervisor`) и данные карточек (уровень оператора), всё tenant-scoped по `vpbx_user_uid`.
3. CRM-webhook при сохранении карточки (D-13): расширить `WebhookProvider.send` 4-м опциональным параметром `extraVars`, слить поля карточки в `vars` ДО `applyTemplate`; `CallCenterCardsService.saveCard` резолвит `notification_integration` через `NotificationsService.findByUidInternal`, строит `extraVars` из `field_values` и вызывает `webhookProvider.send(...)`. НЕ создавать отдельный credential store.

Purpose: без настраиваемых карточек оператор работает с захардкоженной формой v3 (проблема, зафиксированная в CC_CALL_CARD_CONCEPT.md); D-13 требует переиспользовать канал Phase 6, а не дублировать хранилище секретов CRM.
Output: рабочий, протестированный backend карточек + одна точечная правка `WebhookProvider` (расширение сигнатуры), готовые к потреблению фронтендом 07-11.

Distinct from `ClientCard`: существующий `ClientCard` (`features/callcenter/ui/ClientCard`) — read-only виджет контекста звонящего, НЕ трогается этим планом (Pitfall 4). Call Card — новая, настраиваемая сущность.
</objective>
