<objective>
Реализовать сущности настроек колл-центра (D-22, D-27): per-operator настройки `cc_operator_settings` и per-tenant singleton `cc_settings`, их миграции, CRUD-сервис/контроллер с корректным RBAC, и подключить два таба на страницу `/callcenter/settings` (shell из 07-02).

Реализуется:
1. Модель `cc_operator_settings` (per-operator: pickup permission D-18, auto-answer + zip tone D-16, wrap-up таймеры D-19, звуки/Browser-notifications/громкость D-20) и модель `cc_settings` (per-tenant singleton: default SLA-порог D-07, JSON-пороги алертов D-27) + standalone-миграция + регистрация моделей.
2. `CallCenterSettingsService` + `CallCenterSettingsController`: оператор читает/меняет ТОЛЬКО свои настройки (operator id из `req.user.id`), супервизор может читать/менять настройки любого оператора своего тенанта, tenant-singleton `cc_settings` пишется только супервизором/админом (`assertSupervisor`, level >= 3). Всё изолировано по `vpbx_user_uid`.
3. Фронтенд: RTK Query endpoints + таб «Настройки операторов» (per-operator форма) + таб «Пороги алертов» (tenant default SLA + пороги), встроенные в shell `/callcenter/settings` из 07-02.

Purpose: D-16/18/19/20 требуют per-operator гибкость (D-22), D-07/D-27 требуют tenant-level default SLA и настраиваемые пороги алертов — это данные-фундамент, который потребляют АРМ оператора (07-08), метрики (07-03) и wallboard (07-10/07-13).
Output: рабочие, протестированные сущности настроек КЦ с корректным RBAC/tenant-isolation и функциональными табами настроек.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Клиент (оператор level 2) → settings API | Аутентифицированный, но НЕ доверенный на изменение чужих настроек/tenant-параметров — потенциальный IDOR/эскалация |
| Клиент (супервизор/админ level 3+) → tenant settings API | Доверен на запись singleton, но должен быть ограничен своим тенантом |
| operator_user_id / :operatorId (вход) → строка настроек | Резолвинг «чьи настройки» — точка IDOR при доверии клиентскому значению |
| vpbx_user_uid (сессия) → все запросы к cc_operator_settings/cc_settings | Граница мультитенантной изоляции |

## STRIDE Threat Register (ASVS L1)

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-07-05-01 | Elevation of Privilege / Tampering (IDOR) | `PUT/GET /callcenter/settings/operator` | mitigate | operator id берётся ТОЛЬКО из `req.user.id`; `UpdateOperatorSettingsDto` не содержит operator_user_id/user_uid; оператор физически не может адресовать чужой ряд — Task 2 |
| T-07-05-02 | Elevation of Privilege | `PUT /callcenter/settings/tenant` (singleton) | mitigate | `assertSupervisor(req.user)` (level >= 3) — запись tenant cc_settings недоступна оператору level 2 (D-27) — Task 2 |
| T-07-05-03 | Information Disclosure / Tampering | Кросс-тенантный доступ к настройкам через `:operatorId` | mitigate | Все методы сервиса scoping по `user_uid = req.user.vpbx_user_uid`; супервизорский `:operatorId` резолвится только в пределах тенанта; UNIQUE (vpbx_user_uid, operator_user_id) и (vpbx_user_uid) — Task 1/2 |
| T-07-05-04 | Tampering (Input Validation) | `alert_thresholds` JSON в `UpdateCcSettingsDto` | mitigate | class-validator DTO + whitelist известных числовых ключей в сервисе (неизвестные ключи отбрасываются, значения кастуются к числам) — произвольный JSON не сохраняется — Task 2 |
