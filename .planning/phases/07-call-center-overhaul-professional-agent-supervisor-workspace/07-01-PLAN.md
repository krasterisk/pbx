<objective>
Заложить фундамент слоя исторической персистентности колл-центра (Wave 1, D-03) — то, от чего зависят все последующие волны (метрики, отчёты, wallboard sparklines, agent timeline).

Реализуется три вещи:
1. Модель `cc_queue_calls` (полная история звонка: enter/answer/end, wait/talk/hold/wrapup time, disposition) + standalone-миграция + регистрация модели.
2. `CallCenterHistoryWriterService` — batched-async writer: AMI-хендлеры кладут строку истории в in-memory буфер (`enqueue`, sync push, без `await`), отдельный `@Interval`-флаш пишет `bulkCreate` пачкой по интервалу/порогу; буфер имеет жёсткий cap (защита от DoS-флуда, threat T-07-01). Хендлеры `handleAgentConnect`/`handleAgentComplete`/`handleCallerJoin`/`handleCallerAbandon` проводятся через writer.
3. Действия по итогам экспертного аудита (D-02): фикс бага `agentTransfer` (использовать `call.callerChannel`, а не `call.callerIdNum` в AMI `Redirect`) + перезапуск `loadInitialState()`/полного QueueStatus-resync при reconnect AMI.

Purpose: без слоя истории отчёты/метрики нечем наполнять; без batched writer запись истории при пике 150 concurrent calls блокировала бы AMI hot path; аудит-баги (transfer channel, reconnect resync) — известные дефекты, чинятся в первой волне.
Output: рабочий, протестированный слой записи истории звонков поверх существующего `CallCenterAmiService`, без изменения контракта `CallCenterStateService`.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Asterisk AMI → backend event handlers | Поток AMI-событий неограничен по объёму (при пике/флуде 150+ concurrent calls) — недоверенный по частоте вход в hot path |
| AMI event handler → БД (write path) | Запись истории пересекает границу «дешёвый синхронный хендлер» → «медленный SQL round-trip» |
| queue name → tenant (vpbx_user_uid) | Резолвинг тенанта из имени очереди — точка мультитенантной изоляции записей истории |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-07-01 | Denial of Service | `CallCenterHistoryWriterService.buffer` (flush focus этого плана) | mitigate | Жёсткий cap буфера `MAX_BUFFER=5000`: при переполнении отбрасывать самые старые записи + `logger.warn`, буфер не растёт неограниченно ни при AMI-флуде, ни при систематической ошибке БД (flush не ретраит бесконечно) — Task 2 |
| T-07-02 | Denial of Service | Синхронная запись в БД внутри AMI hot path | mitigate | `enqueue()` — только sync push в массив; `flush()` — async fire-and-forget (`void`), никогда `await Model.create()` в хендлере (Pitfall 1) — Task 2 |
| T-07-03 | Information Disclosure / Tampering | Кросс-тенантная утечка строк `cc_queue_calls` | mitigate | Каждая строка несёт `user_uid` (vpbx_user_uid), резолвится через существующий `resolveQueueTenant`; хендлер уже делает `if (!userUid) return` до enqueue — строки без резолвнутого тенанта не пишутся — Task 2 |
| T-07-04 | Tampering | Blind transfer редиректит неверный канал (audit bug) | mitigate | Использовать `call.callerChannel` (имя канала), а не `call.callerIdNum`; guard на отсутствие канала; regression-тест — Task 3 |
