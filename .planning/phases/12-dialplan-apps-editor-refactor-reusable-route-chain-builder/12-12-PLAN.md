Одна миграция данных и одно удаление legacy: переписать `params` существующих цепочек на новую модель и убрать
типы, которых больше не будет.

Ordering: Wave 0 (12-01) → tracer (12-02) → expansion; этот план идёт **последним из содержательных** в ветке
данных, потому что читатель новой формы должен существовать раньше писателя (решение `dual-read`, принятое в
12-10). Обратный порядок оставил бы переписанные данные без кода, который их понимает.

Это единственная необратимая точка фазы: `params` переписываются на месте, три типа исчезают. Поэтому перед
работой стоит блокирующий `checkpoint:decision`, скрипт имеет `--dry-run` и резервную копию, а вся логика
преобразования вынесена в чистую функцию, которую можно протестировать без БД (`12-PATTERNS.md`: прецедента
тестирования SQL миграции в проекте нет, поэтому тестируется преобразование, а не SQL).

Purpose: без миграции пользователь после фазы увидит цепочки, наполовину состоящие из «неизвестных типов».
Output: `migrateAction`, скрипт `migrate-dialplan-actions-phase12.ts`, удалённые `tofax` / `asr` / `keywords`.

Standalone-скрипт, запускаемый `npx ts-node src/modules/routes/migrate-dialplan-actions-phase12.ts [--dry-run]`.
`npm run db:migrate` в репозитории **сломан** — на него не опираться.

Обязательная структура:
1. **Перечень целей** — массив `{ model, column }`, покрывающий все JSON-колонки с цепочками действий (6 колонок
   в 5 таблицах по данным RESEARCH; фактический перечень получить `grep`-ом и записать в SUMMARY). Пропущенная
   колонка = половина системы на старой модели, и обнаружится это на живом звонке.
2. **Резервная копия** — перед записью сохранить исходные значения затронутых строк в файл
   `.backup/phase12-actions-<timestamp>.json` (id строки + имя колонки + исходное значение). Без копии
   необратимость становится безвозвратностью.
3. **`--dry-run`** — прогон, печатающий счётчики (сколько строк затронуто, сколько действий преобразовано,
   сколько несопоставимых, с разбивкой по типам) и **не** пишущий в БД. Режим по умолчанию — именно запись,
   но в SUMMARY должен быть приведён вывод `--dry-run`, полученный до записи.
4. **Обход** — по каждой цели: чтение строк, `JSON.parse` при необходимости, применение `migrateAction` к каждому
   элементу цепочки, запись только если `changed` хотя бы у одного элемента. Обновление — в транзакции на
   таблицу, а не одной транзакцией на всё: одна гигантская транзакция на 5 таблицах при сбое оставляет неясное
   состояние и блокирует таблицы.
5. **Итог** — печать счётчиков и списка несопоставимых действий с идентификаторами строк, чтобы пользователь
   знал, где именно потребуется вмешательство; `process.exit(0)` / `exit(1)`.
6. **Идемпотентность** — повторный запуск не меняет ни одной строки (следствие идемпотентности `migrateAction`),
   что проверяется тем, что второй прогон печатает 0 изменённых строк.

Спек скрипта проверяет обход и счётчики на мокнутых моделях (SQL не тестируется — прецедента нет; тестируется
то, что скрипт вызывает `migrateAction` для каждого элемента каждой цепочки каждой цели и пишет только при
изменениях).
