## Phase Boundary

**ВАЖНО — граница фазы расширена в ходе discuss относительно исходного ROADMAP.**
Исходно фаза была FE-only рефакторингом редактора (`Scope (out): изменения backend / генерации dialplan`).
Пользователь явно включил бэкенд в scope («B и включаем бэкенд в scope, ничего страшного, делаем скурпулёзно,
качество и функционал — превыше всего») и добавил две крупные темы: полноценную типизацию/валидацию params
через весь стек и подсистему тенантных настроек. ROADMAP Phase 12 обновлён соответственно.

Фаза делает пять вещей:

1. **Рефакторинг редактора** — параметры шага уезжают из перегруженной inline-строки в Sheet, строка становится
   сканируемым summary, редактор получает типизированный контракт, конфигурируемость под host и операции продуктивности.
2. **Типизация params через весь стек** — discriminated union в `packages/shared` → DTO-валидация per-type на бэкенде →
   выравнивание всех действующих `ActionType` с генератором dialplan.
3. **Аудит и усиление dialplan-приложений** — исправление найденных багов генератора, тенант-скоупинг целей,
   расширение функциональности приложений до уровня конкурентных решений (FreePBX/Yeastar/3CX).
4. **Расширение условий шага** за пределы `DIALSTATUS` + UI редактора условий.
5. **Подсистема тенантных настроек** — глобальные (ADMIN-guard) + тенантные, не пересекающиеся; на ней стоят
   флаги видимости raw-dialplan и блок-схемы.

**Out of scope:**

- Граф-редактор / блок-схема dialplan с экспортом в PDF — **Phase 13**
- MCP-сервер + построение и редактирование маршрутов с помощью LLM — **Phase 13**
- ConfBridge как полноценный модуль (профили, PIN, admin/marked, запись, DTMF-меню) со своим UI — **отдельная фаза**
- MWI (индикатор нового сообщения на телефоне) и прослушивание голосовой почты с трубки — вне фазы
- Полный редизайн `RouteFormModal` целиком (только вкладки-потребители редактора)

## Implementation Decisions

### Surface редактирования шага (D-01…D-05)

- **D-01:** Параметры шага редактируются в **боковом `Sheet`** (справа; снизу на мобиле), **не** в `Dialog`.
  Причина: редактор уже вложен в модалки — `RoutePhonebooksTab` внутри `RouteFormModal`, `IvrMenuItemsEditor` внутри
  модалки IVR. Ещё один `Dialog` даёт стек оверлеев из трёх уровней.
- **D-02:** Изменения в Sheet применяются **live** в черновик — без пары «OK / Отмена» внутри Sheet.
  Сохранение/отмена остаётся на уровне host-формы.
- **D-03:** Sheet открывается **автоматически сразу после выбора типа действия** — новый шаг не остаётся пустым.
- **D-04:** Строка списка — **сканируемое summary одним предложением** (человекочитаемое, i18n), а не набор полей.
  Источник summary — реестр (`summarize(action)`).
- **D-05:** Условия шага показываются **badge-ом в строке**, редактируются **в том же Sheet**.

### Контракт редактора и типизация params (D-06…D-12)

- **D-06:** App-компонент получает **только свои `params` + `onChange(patch)`**. Уход от
  `onUpdate(id, field: string, value: any)` полностью. Это закрывает W1 и W2 (каскадные ре-рендеры).
- **D-07:** Схема полей — **гибрид**: декларативная схема (тип поля, обязательность, подсказка, опции) покрывает
  большинство приложений; для сложных остаётся возможность подставить кастомный компонент.
- **D-08:** `params` типизируются **discriminated union** в `packages/shared` по `ActionType`.
  В `route.types.ts` уже есть неиспользуемый union `DialplanAction` — он и становится основой, а не пишется заново.
- **D-09:** **Бэкенд в scope.** DTO валидирует `params` **per-type** через discriminated union вместо текущего
  свободного `Record<string, any>`. Все действующие `ActionType` выравниваются с генератором dialplan.
- **D-10:** Валидация **блокирует сохранение** (не warning): пустой `type` и незаполненные обязательные params
  не проходят.
- **D-11:** Ошибки поверхностятся **и на фронте** (per-step, в строке и в Sheet), **и с бэкенда** (ответ DTO-валидации
  маппится на конкретный шаг).
- **D-12:** Legacy-действия в существующих данных **миграются**, а не ломаются.

### Операции и переиспользуемость (D-13…D-15)

- **D-13:** Операции шага: **дублировать, включить/выключить, копировать/вставить, вставить между, undo удаления.**
- **D-14:** Props редактора: **`readOnly`, `labels` (i18n-namespace), `allowedTypes`, `density`, `maxSteps`.**
- **D-15:** Набор разрешённых типов действий задаётся **per-host**: маршрут, справочники маршрута и IVR-меню видят
  разные наборы.

### Raw dialplan и превью (D-16…D-18)

- **D-16:** Колонка `raw_dialplan` и её UI **остаются**. (Пользователь сначала просил убрать вместе с колонкой, затем
  передумал: «Короче, я передумал, оставляем raw-dialplan».) Видимость — через настройку системы.
- **D-17:** **Два флага** настроек: «показывать dialplan в маршруте» и «показывать блок-схему».
  Default для обоих — **включено**.
- **D-18:** Сама блок-схема (визуальное отображение + печать/экспорт в PDF) и MCP/LLM-построение маршрутов —
  **Phase 13**, не здесь. В Phase 12 делается только флаг.

### Подсистема тенантных настроек (D-19)

- **D-19:** В Phase 12 реализуется **полноценная подсистема тенантных настроек** (`full_in_12`): помимо существующих
  глобальных настроек с ADMIN-guard появляются **тенантные**, где пользователь кастомизирует под себя параметры,
  **не пересекающиеся** с глобальными. Флаги D-17 живут на ней.
  Существующие паттерны для опоры: `system_settings` (глобальные), `cc_settings` (тенантные),
  `cc_operator_settings` (оператор), `ai_chat_settings` (тенантные), `tenant_modules`,
  `role_start_defaults` (глобальные с тенантным override).

### Сквозные механики Asterisk (D-20…D-28)

- **D-20:** **Единый «источник значения»** для всех адресных действий вместо разрозненных флагов:
  `фиксированное` / `по маске маршрута (${EXTEN})` / `из переменной канала` / `из справочника`.
  Заменяет частный механизм `params.useExten` + сентинел `__USE_EXTEN__` у `toexten`.
- **D-21:** **Тенант-скоупинг цели обязателен и централизован.** `${EXTEN}` **никогда** не попадает в `Dial()` /
  `Queue()` / `Gosub()` напрямую — только через единую функцию нормализации в `dialplan.util`, по типу цели:
  очередь → `q{exten}_{uid}`, внутренний → `e{exten}_{uid}` (+ WebRTC-companion `ew{exten}_{uid}`),
  группа → `group_{exten}_{uid}`.
  **Обоснование (подтверждено кодом):** `queues.service.ts:68-71` строит имя очереди как `q{exten}_{vpbxUserUid}`,
  а генератор при пустом `params.queue` эмитит `Queue(${EXTEN})` — обращение к несуществующей очереди.
  Тот же дефект у `togroup`, `confbridge`, `voicemail`. Корректный образец — `pjsipDialTarget` у `toexten`.
- **D-22:** **Условия расширяются за пределы `DIALSTATUS`:** `QUEUESTATUS` (TIMEOUT / FULL / JOINEMPTY / LEAVEEMPTY /
  CONTINUE), `DEVICE_STATE`, произвольная переменная канала, результат `CURL` (`NOTIFY_RESULT`, `PB_RAW` уже пишутся,
  но использовать их сейчас нельзя). Без этого сценарий «очередь переполнена → следующее действие» невыразим,
  т.к. `Queue()` не выставляет `DIALSTATUS`.
- **D-23:** **UI условий: пресеты понятным языком + expert-режим.** Пресеты — «не ответили», «очередь переполнена»,
  «нет свободных операторов» и т.п.; expert — произвольное выражение.
- **D-24:** **Флаг `terminal` в реестре** для действий, не возвращающих управление (`toivr` → `Goto`, `toroute` → `Goto`,
  `hangup` → `Hangup`), и **предупреждение о недостижимых шагах** после них в редакторе.
- **D-25:** **Защита от петель** между маршрутами (счётчик переходов, напр. `Set(__KRSK_HOPS=…)` + guard):
  `toroute` A → B → A сейчас даёт бесконечный цикл в dialplan без страховки.
- **D-26:** **Манипуляция номером** (strip / prepend цифр) как общий блок параметров для действий, набирающих
  через транк. Сейчас отсутствует полностью.
- **D-27:** **Опции приложений — структурированные чекбоксы + expert-строка, одно значение с двусторонней
  синхронизацией.** Строка опций парсится в чекбоксы и обратно; **неизвестные и параметризованные флаги**
  (`U(...)`, `M(...)`, `L(x:y:z)`) сохраняются как есть и показываются в expert-строке, чтобы переключение режимов
  ничего не теряло. Правило показа expert: много опций либо наличие флагов с аргументами.
- **D-28:** **`sendmail`, `sendmailpeer`, `telegram` сливаются в `notify`** вместо переноса каждой PHP-ветки на CURL.
  `notify` уже умеет multi-channel через `CURL` → Nest (Phase 6, D-11/D-12).

### Legacy: удаление и перевод (D-29…D-31)

- **D-29:** `tofax`, `asr`, `keywords` — **hard remove** (не deprecate).
  Обоснование: `asr` и `keywords` эмитят идентичный `Record(...)` и никакого распознавания не делают;
  `tofax` ставит `Set(__faxmail=…)`, которую никто не читает.
- **D-30:** `text2speech` **переводится на внутренние TTS-движки** проекта вместо `AGI(say.php)`.
- **D-31:** Вызовы PHP через `SHELL()` / `System()` заменяются на **CURL → Nest endpoint**
  (паттерн `sendmail`/`notify` из Phase 6).

### Per-app улучшения (D-32…D-43)

Пользователь выбрал максимальный набор («Делаем всё по максимуму»).

- **D-32 `toqueue`:** добавить **`QUEUE_PRIO`** (VIP-обход хвоста очереди — `Set(QUEUE_PRIO=N)` перед `Queue()`)
  и **`announceoverride`** (4-я позиция `Queue()`, сейчас всегда пустая) — одна очередь звучит по-разному для разных
  DID. Очередь по маске — через нормализацию D-21.
- **D-33 Группы вызова — новое поле номера:** добавить `call_group.exten` и перевести контекст на
  **`group_{exten}_{uid}`** (симметрично очередям и внутренним). Причина: `ICallGroup` сейчас имеет только
  `uid` и `name`, контекст ключуется по `uid`, поэтому «группа по маске» без номера невозможна в принципе.
- **D-34 Группы — функциональность до уровня FreePBX Ring Groups:** **подтверждение вызова** для внешних участников
  (голосовая почта мобильного оператора иначе «поднимает» вызов и группа считает его отвеченным),
  **пропуск занятых** участников (через `${DEVICE_STATE()}` при сборке списка целей),
  **приветствие абоненту** перед обзвоном и **MOH вместо гудков**, **per-group опции Dial**
  (сейчас `DIAL_OPTS = 'tT'` захардкожен в `call-group-dialplan.util.ts:9`).
- **D-35 Группы — два фикса:** восстанавливать `CALLERID(name)` после `Return()` (сейчас `maybeCidPrefix` ставит
  префикс внутри контекста группы и не откатывает — следующие действия маршрута видят префиксованное имя);
  стратегия `random` → **настоящее перемешивание** (в коде помечена как упрощение v1: случаен только первый участник).
- **D-36 Карусель транков:** переписать с **O(n²) на линейный цикл** (сейчас для n транков эмитится n стартовых
  ветвей × n транков — 25 блоков `Dial` при 5 транках), добавить **per-trunk таймаут** (сейчас один на всю карусель)
  и **реальные режимы** вместо декоративного селектора (`mode` принудительно = `random_then_failover`).
- **D-37 `callerid`:** убрать **двойной вызов `SHELL()`** за звонок в режиме `setclid_list`
  (`dialplan.util.ts:367` — один раз в условии, второй в присваивании); подставлять **имя** из справочника
  в режиме `phonebook` (lookup его возвращает, но используется только номер); **анти-повтор** в карусели CID.
- **D-38 Медиа:** выставить в UI опции **`noanswer`/`n`, `skip`/`s`, `p`, `say`/`mix`** и штатные `langoverride` /
  `context` у `BackGround`.
  **Явный `Answer()` НЕ добавляем** — документация Asterisk 22: «The Playback application answers the channel if no
  options are specified», `noanswer` = «Playback without answering»; у `BackGround` то же через флаг `n`.
  То есть канал отвечается по умолчанию, и управлять надо противоположным.
  Инверсия имён `playprompt`/`playback` устраняется не переименованием, а **слиянием приложений** — см. D-51.
- **D-39 `toexten`:** флаг `webrtc` **оживить или убрать** — генератор его читает (`dialplan.util.ts:163`),
  но ни один компонент не пишет, форк на WebRTC-companion всегда включён; добавить **Mark Answered Elsewhere**
  (иначе на неотвеченных устройствах форкнутого звонка остаются ложные пропущенные);
  пустой `exten` больше не должен молча давать `dp = ''` (валидация по D-10).
- **D-40 [informational] `voicemail`:** ~~выбор приветствия busy/unavailable; тенантный контекст ящика — отдельная фаза~~
  **ОТМЕНЕНО и заменено на D-54…D-59:** приложение Asterisk `VoiceMail()` убирается целиком, вместо него
  кастомная голосовая почта. Тенантность решается по построению, отдельная фаза миграции ящиков из `@default`
  **не нужна**.
- **D-41 `confbridge`:** становится **отдельным модулем со своим UI** — отдельная фаза.
  В Phase 12 действие только переводится на схему параметров (D-07), профили / PIN / admin-marked / запись /
  DTMF-меню и тенант-скоупинг комнаты здесь **не** делаются.
  Риск зафиксирован: `ConfBridge(${EXTEN})` без тенанта означает, что два клиента с одинаковым номером комнаты
  попадают в одну конференцию.
- **D-42 Мелкое:** добавить **`Congestion()`** как тип действия (есть только `Busy()`); писать применение действия
  **`cmd`** в `action_logs` (произвольная строка попадает в конфиг Asterisk без следа); исправить **двойной суффикс
  контекста** в `toroute`.
- **D-43 Фиксы генератора из аудита:** `label` эмитит битое `NoOp())`; **условие в multi-line действиях
  применяется только к первой строке** — остальные выполняются безусловно (`totrunk`, `toexten`, `sendmail`,
  `notify`, `callerid`, `trunk_carousel`); отсутствует **time-group guard** в IVR- и phonebook-биндингах;
  `setclid_custom` / `setclid_list` **теряют часть params** из UI; `sendmailpeer` имеет недостижимые params.

### Единое приложение «Воспроизведение» (D-51…D-53)

Инициатива пользователя: «Playback, Background (и возможно другие сопутствующие apps астериска) объединить в одно
общее приложение, а уже исходя из его параметров — выбирать нужное приложение в dialplan asterisk.
Для пользователя — это просто параметры».

- **D-51:** Одно приложение «Воспроизведение» складывает **три** приложения Asterisk, генератор выбирает по режиму:
  - без прерывания → **`Playback`**
  - с перемоткой / паузой → **`ControlPlayback`**
  - с выходом по цифре в меню → **`BackGround`**

  **Не складываем:** `Read` (производит переменную — это D-49 «сбор ввода»), `MusicOnHold` (бесконечное удержание,
  другая семантика), семейство `Say*` (произносит значение, а не файл). Они отличаются не тем, *как* играют,
  а тем, *что* производят.
  **Миграция:** старый `playprompt` → режим без прерывания, старый `playback` → режим с прерыванием.
  Это устраняет инверсию имён из D-38 вместе с самим различием.
- **D-52:** Генератор берёт на себя расхождения, невидимые пользователю:
  - **язык** — у `BackGround` штатный аргумент `langoverride`, у `Playback` эквивалента нет,
    поэтому эмитится `Set(CHANNEL(language)=xx)` перед вызовом
  - **early media** — при выборе «не отвечать на вызов» (`noanswer` / `n`) эмитится `Progress()` перед
    воспроизведением, иначе звук может не пойти. Сейчас не эмитится ни то, ни другое.
- **D-53:** Режим «выход по цифре» **меняет поток управления**: при совпадении цифры с extension вызов уходит из
  цепочки и последующие шаги не выполняются, тогда как `Playback` / `ControlPlayback` всегда возвращают управление
  на следующий приоритет. Это **не косметический параметр** — режим маркируется тем же механизмом, что терминальные
  действия в D-24, с предупреждением о недостижимом хвосте цепочки.

### Кастомная голосовая почта вместо `VoiceMail()` (D-54…D-59)

> **Перенесено в Phase 12b при `/gsd-plan-phase 12` (2026-08-18).** Планировщик вернул
> `PHASE SPLIT RECOMMENDED`, независимо к тому же выводу пришёл research; пользователь подтвердил разделение,
> отменив тем самым своё более раннее решение `vm_phase: full_in_12`. Причины: голосовая почта зависит от
> типизации (D-08/D-09), `RECORD_STATUS` в условиях (D-22) и `notify` (D-28), то есть встаёт последней и не
> параллелится; это новый класс персональных данных со своей моделью угроз; два вопроса дизайна (чем триггерить
> STT/LLM, где числовой порог «вложение против ссылки») остались рекомендациями, а не решениями.
>
> **Текст решений остаётся здесь** и не дублируется в Phase 12b — она ссылается на этот файл, чтобы формулировки
> не разошлись. Все шесть помечены `[informational]` **для гейта покрытия Phase 12**: они не должны требовать
> плана в этой фазе. В Phase 12b они снова становятся отслеживаемыми требованиями.
> До выполнения Phase 12b старый тип действия `voicemail` остаётся в системе как есть.

Инициатива пользователя: «Voicemail asterisk — сложное приложение, на мой взгляд избыточное. Предлагаю его заменить
кастомным приложением: проигрывание начальной фразы (опционально), звук beep, запись сообщения, отправка уведомления
(с вложением или ссылкой на файл с записью). Возможно новую фичу использовать — расшифровка или саммаризация
с помощью LLM».

**Обоснование замены (подтверждено кодом):** обычный контраргумент — потеря MWI, папок, `VoiceMailMain` и
самозаписанных приветствий — здесь не применим, потому что **ничего из этого в проекте не подключено**.
Поля `mailboxes` и `incoming_mwi_mailbox` существуют только как пассивные колонки realtime-схемы PJSIP
(`ps-endpoint.model.ts:57`, `:345`, `ps-aor.model.ts:15`) и ни одним сервисом не заполняются; модуля голосовой почты
и провизионинга ящиков нет. То есть `VoiceMail(${exten}@default,u)` рассчитывает на `voicemail.conf`, заведённый
на хосте Asterisk вручную.

- **D-54 [informational]:** (Phase 12b) Кастомное приложение «Голосовая почта» **полностью заменяет** `VoiceMail()`.
  Старый тип `voicemail` — **hard remove** с миграцией существующих шагов на новое приложение.
  Состав шага: опциональное приветствие → запись → уведомление через `notify` → расшифровка / саммаризация.
  **Отдельный шаг beep не нужен** — `Record()` играет beep сам, подавляется опцией `q`.
- **D-55 [informational]:** (Phase 12b) **Опция `k` («Keep recorded file upon hangup») обязательна, а не опциональна.**
  Документация Asterisk 22 для `Record()`: «If the user hangs up during a recording, all data will be lost and the
  application will terminate». Абоненты голосовой почты в массе бросают трубку, а не жмут `#`, поэтому без `k`
  теряется почти каждое сообщение — и выглядит это как случайные пропажи, которые тяжело диагностировать.
  **Уточнено по итогам `/gsd-plan-phase 12` research (2026-08-18):** `k` спасает **файл**, но **не возвращает
  управление в цепочку** — канал всё равно завершается на отбое (`the application will terminate` — вторая половина
  той же фразы документации). Поэтому одной опции `k` недостаточно: перед `Record()` обязателен
  `Set(CHANNEL(hangup_handler_push)=<контекст завершения ВП>)`, иначе уведомление, запись в БД и
  расшифровка не запустятся **ровно в том сценарии, ради которого вводился `k`** — при отбое посреди записи.
  Порядок строк в генераторе (`hangup_handler_push` строго **до** `Record(`) — предмет отдельного обязательного
  теста, самого важного единичного теста фазы.
- **D-56 [informational]:** (Phase 12b) Родные возможности `Record()`, которые выносятся в UI: **`o`** («нажмите 0 для соединения с оператором»),
  **`x`** (писать до отбоя, игнорируя цифры), **`y`** (стоп по любой цифре), **`n`** / **`s`** для неотвеченных
  вызовов, лимит длительности, порог тишины, **`u`** (не обрезать тишину). `%d` в имени файла автоинкрементится.
  **`RECORD_STATUS`** подключается к расширенным условиям D-22 («сообщение не записано → другое действие»);
  **`RECORDED_FILE`** идёт в payload уведомления.
  **Уточнено по итогам research (2026-08-18):** значений у `RECORD_STATUS` **семь**, а не шесть —
  `DTMF` / `SILENCE` / `SKIP` / `TIMEOUT` / `HANGUP` / `ERROR` / **`OPERATOR`**. Последнее выставляется опцией `o`
  («нажмите 0 для соединения с оператором»), которая здесь же и включается. Без `OPERATOR` в наборе пресетов
  «нажал 0, чтобы позвать оператора» неотличимо от «нажал `#`, чтобы завершить запись» — то есть перевод на
  оператора молча превратится в обычное сохранение сообщения. Пресеты условий обязаны покрывать все семь.
- **D-57 [informational]:** (Phase 12b) ~~**Расшифровка и саммаризация — в Phase 12** (`full_in_12`)~~ —
  **переехало в Phase 12b вместе с остальной голосовой почтой.** Это интеграция, а не новая возможность:
  в проекте уже есть тенантный модуль **`stt-engines`** (`SttEngine` с `user_uid` + токеном, тот же паттерн, что
  `TtsEngines` из Phase 4), провайдеры `yandex-streaming-stt` и `custom-http-stt` за `stt-provider.interface.ts`,
  а для саммаризации — провайдеры из `ai-agents`.
- **D-58 [informational]:** (Phase 12b) **Доступ к сообщениям — вкладка/фильтр в CDR-отчёте**, а не отдельный раздел.
  Формулировка пользователя: подраздел или фильтр в CDR, отбирающий записи с оставленным голосовым сообщением,
  с кнопкой «Детализация», по которой открывается вся информация и плеер.
  Переиспользуется существующий механизм записей разговоров: `hasRecording` / `recordingUrl` в `cdr.service.ts`,
  стрим `GET cdr/recording/:uniqueid/play`, HTML-плеер, `findByUniqueid`, и **access-scope**

- **D-59 [informational]:** (Phase 12b) **Ссылка в уведомлении обязана быть аутентифицированной с истекающим токеном.**
  Уведомление уходит в Telegram / email, то есть ссылка живёт в чужой инфраструктуре — без токена голосовое
  сообщение клиента становится публичным URL. **Существующий `cdr-public.controller.ts` (стрим записей без JWT
