<objective>
Turn the architectural convention into a test that fails, so the agent's coverage cannot rot as the product grows.

Purpose: D-16 asks that every new module, service or feature ship with an AI adapter and a current skill, and D-17 says that promise is kept by a failing test rather than by a document. The reasoning is direct: a convention held only by review is a convention that lapses on the busy week, and the symptom is an agent that confidently says a tenant has no such feature because it cannot see the module someone added last quarter. This plan lands last because it needs every adapter from the phase to exist before it can be green — a rule written earlier would have been red for four waves and would have been switched off.

Output: the classification registry, the coverage test, the developer-facing skill, and the convention in the architecture document.
</objective>

<task type="tracer" tdd="true">
  <name>End-to-end "an unclassified module fails the build" (D-17)</name>
  <files>packages/backend/src/modules/ai-platform/module-coverage.registry.ts, packages/backend/src/modules/ai-platform/ai-adapter-completeness.spec.ts</files>
  <behavior>
    - Every module directory on disk appears in the classification, and a fixture directory absent from it fails with that directory named
    - Every module classified as covered has a registered adapter, and a fixture removing one fails with the domain named
    - Every classified domain that is not covered carries a non-empty reason string
    - Every registered adapter's domain appears in the classification
    - The suite reports all failures at once rather than stopping at the first
  </behavior>
  <action>
Create the classification registry as a single exported structure mapping each module directory to one of three classifications — covered, infrastructure, or excluded — with a reason string required for the two non-covered cases. The reason is the part that makes the mechanism honest: without it, classifying a domain as excluded is a one-word opt-out indistinguishable from an oversight, and the rule degrades into a list of things nobody wanted to do.

Write the coverage test with four independent assertions: the directory listing matches the classification both ways, covered domains have registered adapters, non-covered classifications have reasons, and every registered adapter's domain is classified. Read the directory listing from the filesystem rather than from a constant — the whole value of this test is catching the module someone added without thinking about the agent, and a hardcoded list cannot do that.

Report every failure in one run. A test that stops at the first missing domain makes a contributor who added three modules fix them one commit at a time, and that friction is what gets a rule disabled.

Follow the shape of the existing completeness test in this codebase that compares an enumeration against its own list, since that precedent is already understood here and it keeps the pattern recognisable.
  </action>
  <verify>
    <automated>npm run test -w @krasterisk/backend -- --testPathPattern="ai-adapter-completeness" --no-coverage</automated>
  </verify>
  <done>The rule is green against the phase's real state and red against fixtures for each of the four failure modes.</done>
</task>

<task type="auto" tdd="true">
  <name>Task 2: Skill currency as part of the rule (D-16, D-17)</name>
  <files>packages/backend/src/modules/ai-platform/ai-adapter-completeness.spec.ts, packages/backend/src/modules/ai-platform/module-coverage.registry.ts</files>
  <behavior>
    - Every covered domain resolves to a skill file, either its own or a declared shared one
    - A covered domain with neither its own nor a declared shared skill fails with the domain named
    - A skill file that fails frontmatter parsing fails the suite with the file named
    - A declared shared skill covering several domains satisfies the rule for all of them
    - Every tool name in the registry belongs to a domain that resolves to a skill
  </behavior>
  <action>
Extend the rule to skills. A covered domain resolves to a skill through the skill registry from 15-02, either by matching its own name or through an explicit shared-skill declaration in the classification. The shared declaration exists because two of this phase's batches legitimately share one skill — the speech engines and the four operational domains — and a rule that cannot express that gets satisfied with stub files, which is strictly worse than the exception since a stub teaches the model nothing while claiming coverage.

Assert that skill frontmatter parses. The registry hand-parses frontmatter because no parser library is present, so a malformed file fails softly at runtime by dropping out of the catalogue — the model simply never learns that skill exists, with no error anywhere. Making it a test failure is what converts a silent degradation into a build break.

Assert that every registered tool's domain resolves to a skill, closing the last gap: a tool can otherwise exist in a domain that is classified and adapter-covered but undocumented, which is the state where the model has capability without conventions and starts inventing them.
  </action>
  <verify>
    <automated>npm run test -w @krasterisk/backend -- --testPathPattern="ai-adapter-completeness|agent-skill-registry" --no-coverage</automated>
  </verify>
  <done>Skill presence, shared-skill declarations and frontmatter validity are all part of the rule, with a fixture per failure mode.</done>
</task>
