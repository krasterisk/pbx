<objective>
Stand up the skills subsystem: repository-hosted skill files, a catalog for the system prompt, and two platform tools that read one body on demand.

Purpose: D-10 requires progressive disclosure — the prompt gets names and one-line descriptions, bodies arrive through a tool. D-11 moves knowledge out of the gitignored documentation folder into the repository so it is versioned with the tools it describes. D-12 makes our conventions the thing skills carry, because general telephony theory the model already knows. Without the build asset rule the catalog is populated in development and empty in production, which degrades answers silently rather than failing.

Output: `AgentSkillRegistryService`, four seed skill files, the build asset rule, and a resolver test that proves the compiled path works.
</objective>

  <name>End-to-end "read one skill" — file on disk to tool result (D-10, D-11)</name>
  <files>packages/backend/src/modules/ai-platform/agent-skill-registry.service.ts, packages/backend/src/modules/ai-platform/agent-skill-registry.service.spec.ts, packages/backend/src/modules/ai-platform/ai-platform.module.ts, packages/backend/src/skills/developer-convention/SKILL.md</files>
  <behavior>
    - `getCatalog()` returns one entry per skill directory with `name` and `description` taken from frontmatter, and never the body
    - `readSkill('developer-convention')` returns the markdown body
    - An unknown skill name returns a structured not-found text rather than throwing
    - A body longer than the cap is truncated with a trailing note
  </behavior>
  <action>
Create `AgentSkillRegistryService` implementing `DomainAiAdapter` and `OnModuleInit` with `domain = 'skills'`, self-registering into `AiAdapterRegistryService` in `onModuleInit` exactly like the voicemail adapter does. Resolve the skills root once at construction by testing candidate directories in order: `path.resolve(__dirname, '../../skills')` — which yields the compiled `skills` folder when running from the build output and the source folder in development — then `path.resolve(process.cwd(), 'src/skills')` as a single fallback. Absence of the directory is a startup `logger.error`, not a silent empty catalog, because D-11 makes skills mandatory. Log the loaded skill count and names at startup.

Parse each `<dir>/SKILL.md` with a hand-written frontmatter reader: a leading fenced metadata block followed by the body, and inside that block exactly two single-line fields, `name` and `description`, extracted by anchored per-key regex with surrounding quotes trimmed. The repository has no YAML parser (`js-yaml`, `yaml` and `gray-matter` are all absent) and Phase 15 adds no dependency, so the format is deliberately flat — one line per field, no nesting, no lists. Fall back to the directory name when `name` is missing.

Expose `getCatalog(): { name: string; description: string }[]` and `readSkill(name: string): string`, capping a returned body at 8000 characters and appending a short truncation note past the cap. `getTools()` returns two definitions: `list_skills` with an empty schema returning the same catalog the prompt carries, and `read_skill` with a single `name` string property returning the body. Both are non-destructive with `entityType: 'skill'`; both handler signatures accept `vpbxUserUid` as the second parameter even though skills are tenant-independent, because the contract requires it (D-22).

Write `skills/developer-convention/SKILL.md`: the D-16 rule that any new module, service or feature ships with `<module>-ai.adapter.ts` next to the domain and `src/skills/<module>/SKILL.md`, that the completeness spec turns a missing pair red, that `vpbxUserUid` is a handler call parameter and never a closure or a schema property, that mutating tools return a proposal instead of writing, and that the skill frontmatter format is two single-line fields.

Register the service as a provider and export in `ai-platform.module.ts`.
  </action>
