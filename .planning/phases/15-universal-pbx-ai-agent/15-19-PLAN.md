<objective>
Give the agent evidence: live channels, recent events and the compiled dialplan — the three things it needs to explain a routing problem instead of guessing at one.

Purpose: D-12 names live switch state and diagnostic tools as first-class knowledge sources alongside skills, and D-13 requires the agent to be able to establish a cause rather than describe a possibility. Today the registry has no diagnostic tool at all, so every "why did this call go there" question is answered from configuration alone — which is exactly how an agent confidently blames the carrier for a tenant misconfiguration. The switch itself is shared across tenants, so this module's whole design problem is filtering: the data source has no tenant column, and the filter has to be built rather than assumed.

Output: a new diagnostics module with a tenant-filtering service, a read-only adapter, and the skill that teaches the evidence order.
</objective>

  <name>End-to-end "show me this tenant's live channels" — allow-listed command, tenant filter (D-12, D-22)</name>
  <files>packages/backend/src/modules/diagnostics/diagnostics.module.ts, packages/backend/src/modules/diagnostics/diagnostics.service.ts, packages/backend/src/modules/diagnostics/diagnostics.service.spec.ts, packages/backend/src/app.module.ts</files>
  <behavior>
    - The channel read issues only a command from the declared allow list
    - A command name not on the allow list is refused before reaching the switch interface
    - The result contains only channels whose context or endpoint belongs to the calling tenant
    - A fixture with channels from two tenants returns each tenant only its own
    - The result is capped at the documented channel count and the cap is reported when it truncates
  </behavior>
  <action>
Create the diagnostics module with a service exposing named read operations, each mapped to one fixed switch command from an explicit allow list. Never accept a command string from a caller, not even an internal one. The switch command interface is an unbounded capability — it can reload, hang up and originate — and a tool that takes a command name is a remote shell with extra steps regardless of what the model is instructed to send.

Filter results to the calling tenant inside the service, before anything is returned. The switch state is shared, so there is no tenant column to filter on and the filter has to be derived: match channels by the tenant's own contexts and endpoint names, resolved through the existing services. Cover the two-tenant fixture explicitly — this is the one domain in the phase where forgetting the filter yields another tenant's live calls rather than an empty list, so the absence of a test would be the absence of the guarantee.

Cap the result at a documented channel count and say so when it truncates. A busy tenant at peak can have more concurrent channels than a conversation can hold, and a silent truncation makes the agent conclude a call is absent when it was merely cut off.

Register the module in the application module. This is the phase's only new module, so it is also the only plan that needs that file in this wave.
  </action>

    - The dialplan read reports rules in their evaluation order, since order is what determines behaviour
    - The adapter declares three read tools and no mutating tool
  </behavior>
  <action>
Add the event history read over the existing event source, bounded by both a time window and a count, and the compiled dialplan read for a single named context. Refuse a context the tenant does not own — the compiled dialplan of another tenant's context is a full description of their routing.

Return dialplan rules in evaluation order and say in the result that the order is the evaluation order. Order is the whole semantics of a dialplan, and it is also what the precedence check in 15-05 refuses to break; a read that presents rules as an unordered set invites the model to reason about them as one.

Create the adapter declaring exactly the three reads, registering itself in the module's initialisation hook, taking the tenant as a handler parameter. Assert that no mutating tool is declared: the switch command interface is one method away from destructive operations, so the read-only boundary here is asserted rather than assumed.

Keep results compact. These three tools will be called in sequence during a single diagnostic turn, so their combined output has to leave room for the model to actually reason about it — which is the same context-budget argument as the state snapshot in 15-07.

  <action>
Write the diagnostics skill as the procedure the agent follows for a routing complaint, because this is the one skill whose value is sequencing rather than facts. State the order: identify the number or extension, read its resolved destination, read the schedule state at the reported time, read the compiled dialplan for the context, then read events or call records for the specific call — and only then state a cause.

Make explicit that a cause is stated from evidence, per D-13: name which tool output supports the conclusion. Also state the inverse, that an absent record is not a cause, so the model reports what it could not find rather than filling the gap. Both halves of that are what separates a useful diagnosis from a plausible story.

Note that results are capped and truncation is reported, so the model asks a narrower question rather than concluding from a truncated list. Keep the skill about this product's conventions and tools rather than general telephony theory, which the model already knows.
