<objective>
Extend universal reading to schedules, numbers and portal users — three domains the agent currently cannot see at all.

Purpose: D-15 draws reading wide and writing narrow, and the practical value of "knows everything" shows up in exactly these domains. A question like "why did the call go to voicemail at 19:10" needs the schedule; "where does this number land" needs the number's destination; "who changed this" needs the portal users. Without them the agent has to guess or ask, and guessing about a schedule is how it confidently explains the wrong cause. These are read-only by design: none of them is in the write boundary this phase opened.

Output: three read adapters, three domain skills, and a batch spec asserting they are read-only, secret-free and tenant-isolated.
</objective>

  <behavior>
    - The list tool returns the tenant's schedules with their intervals in a readable form
    - The evaluation tool answers whether a named schedule is currently inside or outside its intervals, and names the next boundary
    - Evaluation uses the tenant's configured time zone, not the server's
    - The adapter declares no mutating tool
    - A call as one tenant returns none of another tenant's schedules
  </behavior>
  <action>
Create the schedule adapter with a list tool and an evaluation tool. Evaluation is the tool that earns its place: a raw interval list makes the model do arithmetic across weekdays and time zones, and it will get that wrong in a way that reads as a confident wrong explanation. Answer the question directly — inside or outside, and when the state next changes — using the same evaluation the routing path itself uses rather than a second implementation.

Use the tenant's configured time zone. A schedule evaluated in the server's zone is right for one tenant and quietly wrong for the rest, and the resulting explanation is worse than no answer.

Declare no mutating tools and assert their absence in the batch spec. That assertion is the machine-checked form of the read-versus-write boundary in D-15: this batch reads, and a later contributor adding a write here has to change a test that says so out loud.

Write the schedule domain skill: what a schedule controls in this product, how intervals and holidays are expressed, that evaluation is time-zone sensitive, and which routing questions the schedule is the answer to.

  <action>
Create the number adapter with a list tool and a describe tool that resolves the number's current destination through the route lookup, passing the tenant as a parameter. Resolving the destination here is what collapses the most common diagnostic question into one tool call instead of three; without it the model has to list numbers, list routes, and match patterns itself, which costs steps and invites a matching mistake.

Report an unrouted number explicitly. Omitting it looks identical to the number not existing, and "the number is not routed anywhere" is usually the answer the user is looking for.

Write the number domain skill covering the number format convention in this product, what the statuses mean, how a number relates to an inbound route, and that the describe tool already resolves the destination so the model need not match patterns by hand.
