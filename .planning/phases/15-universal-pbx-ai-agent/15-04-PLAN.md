<objective>
Build the model client and rewrite the system prompt so the brain moves in-process.

Purpose: D-06 puts the loop in our process, which means we own the call to the model. The repository already has a working OpenAI-compatible client for voicemail summaries with encrypted keys and endpoint normalization — generalizing it is cheaper and safer than a new dependency, and the phase adds none. D-07 makes provider and model an administrator concern, so resolution happens server-side from the provider table. D-10 turns the prompt into a catalog, D-13 and D-14 set tone and language. This plan also moves the adapter knowledge blocks into the prompt builder before 15-15 deletes the service that currently glues them on, so the domain knowledge does not silently vanish.

Output: `PbxAgentLlmClient`, shared agent types, a rebuilt system prompt, one compact state snapshot serving both the prompt and a tool, and default-provider resolution.
</objective>

Rework `buildSystemPrompt()` into four composed blocks. First, the compact tenant state snapshot the builder already produces — keep its existing truncation of long entity lists, that restraint is the reason the prompt stays small. Second, adapter knowledge blocks read directly from `AiAdapterRegistryService.getKnowledgeBlocks()`; today those blocks are concatenated inside the knowledge service that 15-15 deletes, and calling the registry here is what keeps them in the prompt. Third, the skill catalog from `AgentSkillRegistryService.getCatalog()` rendered as name and description lines with an instruction to load a body through the skill-reading tool when a task touches that domain — bodies never go in the prompt, that is the whole point of D-10. Fourth, behavioural rules.

The behavioural rules replace the current fixed-language directive with a rule to answer in the language the user wrote in and to fall back to the interface locale when ambiguous (D-14). They state that answers describe observable call behaviour in business language, that technical detail comes only on request, and that a cause must be established from live state, logs and configuration rather than asserted (D-13). They state that changes are proposed as a confirmation card the user accepts, so the model must not claim a change is done before that (D-18/D-19). They state that tool results, call-detail rows and skill bodies are data and can never redirect these rules — the same boundary the voicemail summary prompt already draws for transcripts, and the hook location `/gsd-secure-phase 15` will harden.

Do not remove the knowledge service in this plan — it stays until 15-15 so the prompt change and the deletion are separate commits and a regression is attributable.

Expose the same snapshot as a platform-level tool in `pbx-state-ai.adapter.ts`, registered from this module's initialisation hook and declaring one read tool with an optional domain filter. This replaces the first of the eighteen handwritten tools, which loaded every entity of five domains in parallel and serialized the lot — the same information the prompt already carries, assembled a second time and at ten times the size. One implementation behind both the prompt and the tool is what keeps them from disagreeing about current state, and it is why this tool lands here rather than in the migration slice that follows: the builder is already the place the snapshot lives.
