<objective>
Make settings and messaging answerable without making them changeable, and keep every secret they contain out of the model's context.

Purpose: D-15 makes reading universal, and settings are where universal reading pays off most for diagnosis — a limit, a feature flag or a channel configuration explains behaviour that otherwise looks like a bug. But this phase's scope explicitly excludes writing tenant settings and switch parameters through the agent, so these adapters are read-only by decision rather than by convenience. They are also the domains densest in secret material: provider tokens, webhook secrets and encrypted values sit next to the harmless fields, and everything a tool returns is persisted in a conversation.

Output: four read adapters, two grouped domain skills, and a batch spec that proves read-only and secret-free against the declared output shapes.
</objective>

  <action>
Create the tenant settings adapter with a single read tool returning settings grouped by area. Build the output from an explicit field allow list. Deny-listing known secret names is the tempting shortcut and it breaks silently the first time a column is added, which in this domain means a provider token in a persisted conversation.

Declare no mutating tools and assert their absence. Writing tenant settings and switch parameters through the agent is explicitly outside this phase's scope, so the assertion is the boundary made mechanical rather than a comment.

Write the settings domain skill covering which settings affect call behaviour, how to read a limit or a flag when diagnosing, that secret-valued settings show only presence, and that the agent cannot change any of them and should route the user to the settings screen instead.

  <behavior>
    - The read tool returns only the platform settings that describe the calling tenant's own limits and capabilities
    - Platform-wide operational values, provider configuration and other tenants' allocations are absent from the result
    - The same call as two different tenants returns each tenant's own projection
    - The adapter declares no mutating tool
    - The projection is defined as an explicit list, and a new platform setting does not appear in it by default
  </behavior>
  <action>
Create the platform settings adapter as a deliberately narrow projection: the calling tenant's limits, enabled capabilities and quota-shaped values, and nothing else. Platform settings are not tenant-scoped data, so the usual tenant filter offers no protection here and the safety has to come from the projection itself.

Define the projection as an explicit list of settings with an explanation for each, and assert that a setting absent from the list does not appear in the output. Default-exclusion is the property that matters: a platform setting added next year is invisible to every tenant until someone decides otherwise, which is the opposite of what a pass-through would do.

Cover the two-tenant case even though there is no tenant column to filter on — the assertion is that each caller sees its own numbers, which is what makes this a projection rather than a leak with extra steps.
  </action>

    - Neither adapter declares a tool that sends a message

  </behavior>
  <action>
Create both messaging adapters with a configuration read and a delivery-history read. Report the channel as configured and enabled or not, never with its credential — a channel token in a conversation transcript is a durable credential leak with no audit trail attached to its use.

Exclude message bodies from delivery results by default and truncate to a documented preview only where the delivery question genuinely needs it. Delivery history contains customer-authored content, so the volume of personal data a single tool call can pull into a conversation is the thing to bound here.

Declare no send capability in either adapter, and assert it. Sending a message is an outward action with no undo and no confirmable diff worth the name — the recipient has already read it — so it does not belong in the write boundary this phase opened, and the assertion says so where the next contributor will see it.

Write the messaging domain skill covering both channels, what a delivery status means, that bodies are not exposed, and that the agent can explain a delivery failure but cannot send or resend.
