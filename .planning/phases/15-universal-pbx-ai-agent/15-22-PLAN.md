<objective>
Build the evaluation harness the design contract asks for: canned model turns replayed through the real loop, asserting what the agent did rather than how its answer read.

Purpose: the approved evaluation strategy names deterministic in-repository replay as the primary tool, and its critical dimensions — tenant boundary integrity, the confirmation gate, tool-use correctness, multi-step completion — are all properties of the sequence of actions, not of the prose. A unit test per service proves each piece works; only a replayed scenario proves the pieces compose into the right behaviour on a real question. Ten scenarios ship with this plan and the remaining ten are specified for the phase gate, matching the contract's timeline of starting during execution rather than after.

Output: the harness, the first ten scenarios, the guide for adding more, and a script to run them.
</objective>

  <behavior>
    - A scenario declaring an input, a tenant, canned model turns and an expected tool sequence passes against the real loop
    - The harness makes no outbound network request; the model client is replaced by the fixture, and nothing else is
    - A scenario whose actual tool sequence differs fails with both sequences printed
    - Every audit row produced during a scenario carries the scenario's tenant
    - The scenario file is data, so adding a scenario requires no change to the harness
  </behavior>
  <action>
Create the harness taking a scenario and the loop's real dependencies, substituting only the model client with one that returns the scenario's canned turns in order. Substituting only the model client is the property that gives the suite its value: the registry, the dispatch point, the argument sanitisation, the proposal service and the audit writer are all the real ones, so a regression in any of them fails a scenario. A harness that mocks the tool layer too would test the fixture.

Collect the stream events and assert the tool sequence against the scenario's expectation, printing both sequences on failure. The sequence is the assertion that matters — a correct answer reached by calling the wrong tool is a coincidence that will not survive the next question, and the contract's tool-use dimension is defined exactly this way.

Assert the tenant on every audit row produced during the run. That single assertion, applied to every scenario, is the cheapest continuous check on the phase's most important property, and it costs nothing to include once the audit writer is real.

Keep scenarios as data in the scenario file, with the harness reading them. A scenario expressed as code is a scenario nobody adds; the contract expects this set to keep growing from production samples.
  </action>

    - Three mutating scenarios pass, each asserting a pending proposal exists with the expected entity and that no row changed before confirmation
    - Two cross-tenant scenarios pass, one calling the same tool as two tenants and one supplying a forged tenant key in model arguments
    - One diagnostic scenario passes, asserting the agent reads before concluding
    - One step-budget scenario passes, asserting the loop stops at the ceiling and emits the ceiling outcome
  </behavior>
  <action>
Write ten scenarios spanning the dataset buckets the contract defines, weighted toward the critical dimensions. Add the assertion kinds each bucket needs to the harness: a pending-proposal matcher for the mutating bucket, a no-write matcher comparing entity counts before and after, a forged-argument matcher for the cross-tenant bucket, and a terminal-outcome matcher for the step-budget bucket.

Make the mutating scenarios assert both halves — that the proposal exists and that nothing was written. Asserting only the proposal would pass for an implementation that writes and also proposes, which is the exact failure the confirmation gate exists to prevent and the one most likely to be introduced by a well-meaning refactor.

Make the forged-argument scenario supply a tenant key inside the model's tool arguments and assert the affected tenant is unchanged. That is the model-side attack the argument sanitisation defends against, expressed as a behaviour rather than as a unit test on the sanitiser.

Give the diagnostic scenario canned turns that would let the model answer immediately, and assert it reads first. The scenario is checking the system prompt's tool discipline, which is otherwise unobservable.
  </action>
