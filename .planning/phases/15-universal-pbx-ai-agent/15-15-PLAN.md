<objective>
Finish the hard migration: delete the eighteen handwritten registrations, delete the two bypass paths, and close the tenant-header hole on the external entry.

Purpose: D-27 and D-28 are the reason this phase is a migration rather than an addition. Two sources of tools diverge — that is not a risk, it is a certainty, and the divergence shows up as an agent that can do something through one path that the confirmation gate blocks on another. Today there are three dispatch paths and the alternative controller is the one that makes the gate decorative. The external entry stays alive because third-party callers use it, but its tenant stops coming from a header under a service token, because a header a caller controls is not an authorisation.

Output: the deletions, the token-only external entry, corrected architecture documentation, and a widened narrow test command.
</objective>

<task type="auto" tdd="true">
  <name>Task 2: Token-only tenant on the external entry (D-28)</name>
  <files>packages/backend/src/modules/mcp/mcp.controller.ts, packages/backend/src/modules/mcp/mcp.controller.spec.ts</files>
  <behavior>
    - A request with a valid user token dispatches with that token's tenant
    - A request with a service token and a tenant header is rejected with an unauthorised response
    - A request with a valid user token plus a contradicting tenant header dispatches with the token's tenant and ignores the header
    - Tool listing over the external entry returns the same set as the internal path, with no tool the internal path lacks
    - A session established by one tenant cannot be resumed with another tenant's token
  </behavior>
  <action>
Put the standard authentication guard on the external entry and take the tenant from the authenticated principal only. Remove the service-token branch and the tenant-header read entirely — not deprecate them. A header naming the tenant, accepted under a shared token, means any holder of that token is every tenant, and the migration to adapters does nothing about that on its own.

Ignore the tenant header if present rather than erroring on it, and cover that case explicitly. A third-party caller that keeps sending the header after repointing at a user token should keep working with its own tenant, and an error there would look like the migration broke them when it did not.

Bind the session to the tenant that established it and reject a resume under a different tenant. The session layer keeps state across requests, so a session identifier that outlives a token is the same header hole in a different costume.

Assert that the external entry and the internal path expose the identical tool set. They both read the same registry, so a divergence would mean something re-introduced a second source — which is the failure mode this whole plan exists to remove.
  </action>

  </verify>
  <done>The external entry authenticates every caller, derives the tenant only from the token, ignores the header, and matches the internal tool set.</done>
