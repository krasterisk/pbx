<objective>
Fill the panel's rail slot with real conversations, so a user can come back to what the agent did instead of losing it on reload.

Purpose: D-26 exists because today the conversation lives in a client-side store and dies with the page, while the tool calls it made are recorded in the audit log — the record of consequences outlives the record of intent. Persisting conversations by tenant and user makes "what did the agent do here" answerable, which is a precondition for trusting it with changes at all. This plan consumes the persistence added in 15-03 and the rail slot added in 15-06.

Output: conversation queries, the rail component with all four states and a guarded delete, and the panel wiring that lifts selection.
</objective>

<task type="auto" tdd="true">
  <name>Task 2: Rail states and guarded deletion (D-26, design contract)</name>
  <files>packages/frontend/src/features/ai-chat/ui/ThreadList/ThreadList.tsx, packages/frontend/src/features/ai-chat/ui/ThreadList/ThreadList.module.scss, packages/frontend/src/features/ai-chat/ui/ThreadList/ThreadList.test.tsx, packages/frontend/src/features/ai-chat/model/slice/aiChatSlice.ts</files>
  <behavior>
    - While the list query is pending the rail shows skeleton rows and no empty-state copy
    - With no conversations the rail shows the empty-state copy and the new-conversation action
    - With a failed list query the rail shows the error copy and a retry that refires the query
    - Deleting a conversation opens a confirmation whose dismissing action keeps the conversation, and confirming removes it from the rail
    - Deleting the selected conversation clears the selection and shows the empty conversation column
  </behavior>
  <action>
Implement the four rail states explicitly. A single "no items" branch that covers both loading and empty is the standard way a slow list looks broken, and the design contract calls for distinguishing them.

Wire deletion to a confirmation dialog using the exact copy from the design contract, where the dismissing action is phrased as keeping the conversation rather than as a generic cancel. Phrasing the safe action affirmatively matters here because the destructive action removes a record of changes the agent made, which is the opposite of what a user reaching for tidiness expects.

Handle deletion of the currently selected conversation: clear selection and fall back to the empty conversation column rather than leaving the panel pointing at a conversation the server no longer has. Trim the client store to in-flight turn state only, removing the committed-message array that the server now owns, and update the store's type accordingly.
  </action>
