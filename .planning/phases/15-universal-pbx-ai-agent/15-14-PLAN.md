<objective>
Build the card that turns an agent's proposal into a decision a person makes with a button.

Purpose: D-19 replaces textual agreement with an explicit control, and the reason is not ceremony. Typed agreement is ambiguous about which of several proposals it refers to, it is trivially produced by the model quoting the user, and it leaves no record distinguishable from ordinary conversation. A card carries a proposal identifier, shows exactly what will change, and its confirmation is an authenticated request the server can tie to a person and a role — which is also what makes the audit trail in 15-05 meaningful.

Output: the change card with all five states, the confirm and reject mutations, and its placement in the conversation.
</objective>

  <behavior>
    - A pending card renders the entity label, every change line and both actions with the contract's Russian labels
    - Pressing the confirm action sends only the proposal identifier and moves the card to applied
    - Pressing the reject action moves the card to rejected without sending an apply
    - Both actions are disabled while a request is in flight and the card shows a busy indication
    - A card appearing mid-stream is placed in the conversation at the position of the turn that produced it
  </behavior>
  <action>
Build the card as a presentational component driven by the proposal view the server returns, with the confirm and reject mutations added to the chat query module. Send only the proposal identifier: tenant, author and role come from the token server-side, and a card that also sends an entity identifier or a confirmation flag invites a tampered request to mean something.

Use the exact Russian action labels from the design contract. They read as applying and rejecting changes rather than as a generic yes and no, which matters because the same two buttons appear next to proposals ranging from adding one directory row to reloading a dialplan.

Disable both actions while a request is in flight and show the busy state. Double-pressing confirm is the most likely way a user produces two apply requests, and while the server treats the second as nothing-pending, an interface that lets it happen makes the user believe two changes went through.

Place the card in the conversation at the position of the turn that produced it, rendering it from the proposal event the stream emits. It is part of the transcript, not a modal — a proposal that interrupts with a dialog loses the surrounding explanation the agent just gave.

  <name>Task 2: The settled, denied and failed states (D-19, D-21)</name>
  <files>packages/frontend/src/features/ai-chat/ui/DiffConfirmCard/DiffConfirmCard.tsx, packages/frontend/src/features/ai-chat/ui/DiffConfirmCard/DiffConfirmCard.module.scss, packages/frontend/src/features/ai-chat/ui/DiffConfirmCard/DiffConfirmCard.test.tsx</files>
  <behavior>
    - An applied card shows the applied badge and time, and neither action is rendered
    - A rejected card shows the rejected badge and neither action is rendered
    - A denied card shows the permission explanation and neither action is rendered
    - A card whose apply returned an error stays pending, shows the error text and offers a retry
    - An expired card shows that it can no longer be applied and offers to ask the agent again
  </behavior>
  <action>
Implement the settled states as terminal: no actions rendered at all rather than disabled ones. A disabled button on a card from last week invites a click and a "why is this greyed out" question; an absent button plus a badge answers it.

Render the denied state with the permission explanation from the locale keys rather than the raw server message, since the server's refusal is a coded reason and the user needs to know it is about their role, not about the change being invalid. This is the visible half of D-21: the agent did not do something the user cannot do, and it says so.

Keep the failed-apply state pending with the error and a retry. The server deliberately leaves a proposal pending when the database write succeeded and the switch reload failed, so this is the state that makes a half-applied change visible and repeatable — showing it as failed-and-final would hide exactly the case that needs attention.

Add the expired state, since proposals carry an expiry and a conversation reopened days later will contain them. Offer to ask the agent again rather than a retry, because re-applying a stale payload against changed state is not what the user means.
  </action>
