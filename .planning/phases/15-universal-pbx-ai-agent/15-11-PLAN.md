<objective>
Make routes the domain the agent edits properly: a typed action chain, validated before it is offered, applied through the same orchestrator the interface button uses.

Purpose: this is the largest single debt in the handwritten tool set. The old route tool accepts a raw application name and an argument string, which bypasses the typed action chain this product moved to in Phase 12 — so the agent writes routes in a form the interface's own editor cannot round-trip. The old apply tool is worse: it reassembles the context itself and calls the low-level applier directly, skipping the directory binding policies and duplicating the context naming rule. Both are replaced here by a typed draft that is validated before the user ever sees a card, and by folding application into confirmation per D-20 so there is no model-callable "apply" left to fire on its own.

Output: the route adapter, a chain-draft validator, and the routes domain skill.
</objective>

  <behavior>
    - A draft chain of valid typed actions produces a pending proposal whose summary lists the steps in order and states that the dialplan will be reloaded
    - A draft containing an unknown action kind, a missing required parameter or a reference to a non-existent entity is refused with the failing step index and reason
    - Confirming the proposal writes the route and calls the route apply orchestrator exactly once
    - Confirming does not call the low-level dialplan applier directly and does not rebuild the context name
    - The proposal for a route in another tenant's context is refused at tool time
  </behavior>
  <action>
Create the chain-draft validator as a pure function taking the model's drafted step list and the tenant's entity references, returning either a typed chain accepted by the shared route action contract or a refusal naming the failing step index and reason. Validate against the shared types the interface editor already uses, so anything the agent proposes is something that editor can open — the raw application-and-arguments form the handwritten tool used is exactly what breaks that property.

Create the route adapter with a list tool, a tool that describes the assembled chain of a context, and mutating tools for creating and deleting a route. Set `proposes` true on the mutating tools so the 15-05 `callTool` persist path runs (D-18). The create handler validates the draft, then returns a pending proposal carrying the typed chain in its apply payload, a step-by-step summary, and the flag declaring that confirmation must reload the dialplan.

Confirmation goes through the proposals service from 15-05, which calls the route apply orchestrator. Never call the low-level category applier from this adapter and never reassemble the context name here. The orchestrator writes the directory binding policy categories and then the route context with a reload, in that order; the handwritten apply tool skipped the first half and duplicated the naming, which is how the agent's applied routes ended up missing binding policies the interface's own button installs correctly.

Assert the orchestrator-only property in the spec with a mock on both the orchestrator and the low-level applier: exactly one call to the former, zero direct calls to the latter. That is the assertion that keeps the bug from returning by convenience.

<task type="auto" tdd="true">
  <name>Task 2: Retire the standalone apply tool and cover precedence at proposal time (D-19, D-20)</name>
  <files>packages/backend/src/modules/routes/routes-ai.adapter.ts, packages/backend/src/modules/routes/routes-ai.adapter.spec.ts</files>
  <behavior>
    - The registry contains no model-callable tool that applies the dialplan on its own
    - A route proposal whose resulting pattern order would place a catch-all above a specific or emergency pattern is refused at tool time with both patterns named
    - A delete proposal for a route names the pattern and the destination that will stop working
    - A proposal touching an inbound or catch-all pattern carries an impact note in its summary
    - Confirming a route proposal whose reload fails leaves the proposal pending with the error recorded
  </behavior>
  <action>
Do not port the standalone apply tool. Applying is a consequence of confirming a change per D-20, so a separate model-callable apply is both redundant and a way to reload production without a card. Assert its absence from the registry in the spec, because a later contributor reading the old tool list will reasonably assume it was an oversight.

Run the precedence check from 15-05 against the ordered pattern list the proposal would produce, at proposal time as well as at confirmation time. Checking twice is deliberate: at proposal time the refusal becomes an explanation the model can act on and re-draft, while at confirmation time it is a hard stop. A catch-all promoted above a specific inbound number or an emergency short number is this domain's most damaging silent failure, and dialplan behaviour is decided by rule order, which the model has no way to feel.

Add the impact note for proposals touching inbound or catch-all patterns, naming the main inbound numbers and emergency patterns in the affected context. The evaluation dimension for emergency and carrier-sensitive routing requires the card to state this, and a note assembled from the tenant's own patterns is both accurate and cheap.

Cover the failed-reload path: the proposals service records the error and leaves the status pending, and the route adapter's spec asserts the route write is visible while the proposal still shows as unapplied, so the half state is discoverable rather than reported as success.
  </action>
