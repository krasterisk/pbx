<objective>
Replace the external chat proxy with an agent turn that runs here, so step limits, tool discipline, confirmations, audit and cancellation are ours to enforce.

Purpose: D-06 is the load-bearing decision of the phase. Today the whole conversation is forwarded to an external service and the model-and-tools cycle happens outside this codebase — which means multi-step behaviour, skills, confirmation gates and audit are all decided somewhere we cannot test. Bringing the loop in-process is what makes every other decision in this phase enforceable. D-09 adds the two things a user needs when a turn takes thirty seconds: a line per step saying what the agent is doing, and a stop button that actually stops it.

Output: the turn service, stream framing, the rewired turn endpoint, and deletion of the proxy.
</objective>

<task type="tracer" tdd="true">
  <name>End-to-end "one question, one tool, one answer" in process (D-06, D-13, D-26)</name>
  <files>packages/backend/src/modules/ai-chat/pbx-agent-loop.service.ts, packages/backend/src/modules/ai-chat/pbx-agent-loop.service.spec.ts, packages/backend/src/modules/ai-chat/agent-sse.util.ts, packages/backend/src/modules/ai-chat/agent-sse.util.spec.ts</files>
  <behavior>
    - A turn whose fixture model response requests one read tool then answers yields the events: progress, tool call, tool result, text, done
    - The tool is dispatched through the single hardened dispatch point with the tenant taken from the turn context, never from model arguments
    - The user message, the tool exchange and the final answer are appended to the conversation in order
    - Token counts reported by the model response are accumulated onto the conversation row
    - The stream frames each event with its name and a single serialized payload line, and emits a heartbeat when idle beyond the configured interval
  </behavior>
  <action>
Create the turn service with a single public method taking the user message, the conversation reference and a turn context carrying tenant, author and role, and returning an async iterable of stream events. Its loop is: build the message array from the system prompt and the stored conversation, call the model client from 15-04 with the registry's tool list wrapped in the provider's tool format, and then branch — a text response ends the turn, tool calls are dispatched and their results appended as tool messages before the next model call.

Dispatch every tool through the hardened entry point from 15-01 and nothing else. The reason is structural: a confirmation gate or a tenant rule enforced on one dispatch path is bypassable through any other, and this codebase currently has three paths. One path is the only shape in which the guarantees hold.

Emit a progress event before each tool dispatch naming the tool in the user's language, then the tool call and tool result events the existing stream contract already defines. Keep tool results out of the answer text — the model summarises them per D-13, and pasting raw payloads into the reply is what makes the agent sound like a terminal.

Persist as you go, not at the end: append the user message before the first model call and each assistant or tool message as it is produced, so a dropped connection leaves a readable conversation rather than an empty one. Accumulate token counts onto the conversation row per D-08.

Create the stream framing helper with the manual header-and-write approach already used elsewhere in this codebase rather than the framework's stream decorator, because the turn needs to write interleaved event types and a heartbeat on one response, and the decorator's observable shape fights that. Include the heartbeat: proxies in front of this service close idle connections, and a turn that spends forty seconds inside one tool call looks idle.
  </action>

<task type="auto" tdd="true">
  <name>Task 2: Step ceiling, cancellation and pending proposals in the stream (D-09, D-18)</name>
  <files>packages/backend/src/modules/ai-chat/pbx-agent-loop.service.ts, packages/backend/src/modules/ai-chat/pbx-agent-loop.service.spec.ts</files>
  <behavior>
    - A fixture that requests a tool on every step stops at the configured ceiling, emits the ceiling error and makes no further model call
    - Aborting mid-turn aborts the in-flight model request, dispatches no further tools and emits the cancelled error as the terminal event
    - Aborting between tool calls skips the remaining calls of that batch
    - A mutating tool returning a pending proposal emits a proposal event and the turn continues without a write
    - Invalid tool arguments produce a structured tool error back to the model, and a second failure on the same tool ends the turn rather than retrying forever
  </behavior>
  <action>
Read the step ceiling from configuration with a documented default and count a step per model call. On reaching it, stop before the next model call and emit the ceiling error as the terminal event — stopping after the call would spend the tokens the ceiling exists to bound.

Thread one abort signal from the turn context into the model client's request and check it before every tool dispatch and before every model call. Cancellation that only stops the loop but leaves the model request in flight keeps burning tokens for a user who already walked away, which is the failure this decision names. Cover both positions in tests with an explicit abort controller: aborting during the model call and aborting between tool calls are different code paths and only one of them is obvious.

When a dispatched tool returns a pending proposal from 15-05, emit it as its own stream event so the panel can render a confirmation card, append a short marker to the conversation, and let the turn continue so the model can explain what it proposed. Do not treat any model-supplied confirmation argument as agreement — 15-01 already strips those, and this loop must not reintroduce a second reading of them.

Validate tool arguments against the declared schema before dispatch and return validation failures to the model as tool errors with the offending fields named, capped at the retry limit from the design contract. An uncaught validation throw would end the stream with a generic failure and lose the turn; a bounded retry lets the model correct itself once.
  </action>
