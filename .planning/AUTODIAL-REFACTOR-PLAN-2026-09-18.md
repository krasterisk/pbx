# Автообзвон: поэтапный план рефакторинга

Дата: 2026-09-18. Статус: реализация начата по подтверждению пользователя. Выполнен первый implementation slice R1, остальные этапы не объявлены завершёнными. Подробности и ограничения: [журнал реализации](./AUTODIAL-REFACTOR-IMPLEMENTATION-2026-09-18.md).

Основание: [анализ A01-A24](C:/Users/Professional/WebstormProjects/krasterisk_v4/.planning/AUTODIAL-REFACTOR-ANALYSIS-2026-09-18.md). План не объявляет существующие фазы GSD 17/17.1-17.5 завершёнными и не заменяет их исторические решения.

## 1. Стратегия

Рекомендуется несколько небольших вертикальных изменений с проверяемым результатом, а не одна ветка «переписать весь автообзвон». Исправление контрактов и сохранности данных предшествует масштабному извлечению компонентов. Изменения звонкового поведения проходят PBX harness до включения на существующих кампаниях.

Порядок: **R0 -> R1 -> R2 -> R3 -> R4 -> R5 -> R6**.

- R3 UX можно делать после стабилизации DTO R1 параллельно с backend R2, если появятся отдельные исполнители. Это не разрешение автоматически запускать агентов.
- R4 расширенный trunk/CID зависит от безопасного runtime R2.
- R5 настоящее сообщение автоответчику зависит от compiler/outcome R2.
- Чистый rename/layout PR допустим раньше, но не закрывает R2 и не должен менять семантику настроек.

## 2. Решения о поведении

Следующие решения явно меняют текущее поведение. Рекомендации ниже не считать разрешением на незаметную миграцию.

| ID | Вопрос | Рекомендация | Совместимость |
|---|---|---|---|
| B01 | Роль queue_names | Сценарий отвечает за направление, темп обзвона за пул операторов | Legacy fallback развернуть в явный target после сравнения маршрута |
| B02 | Нет расписания / все выключены | Нет правил: явно выбранный круглосуточный режим; правила есть, но все отключены: набор закрыт | Предупреждение и версия семантики для существующих конфигураций |
| B03 | Неверная зона | Отклонять сохранение/start, не подставлять UTC молча | Показать список проблемных старых настроек |
| B04 | Локальные часы абонента | Реально проверять перед набором; источник допустимого интервала сделать явным | Не включать произвольные 09:00-20:00 без решения; текущий offset хранить без автопересчёта |
| B05 | AMD voicemail | Не обещать работающую запись до реализации machine-ветки | Старые настройки показать как legacy/требующие настройки; не заменять автоматически на continue |
| B06 | Короткий разговор | Различить время после ответа и разговор с оператором | Legacy metric сохраняется до осознанного переключения/версии |
| B07 | Stop | Прекратить новые попытки, дать активным завершиться; немедленное завершение отдельно | Не переводить live dialing в pending; подписи/документация должны совпадать |
| B08 | Редактирование используемой базы | Стабильные ID; опасное удаление поля/номера и replace запрещены либо согласованы с задачами | Не переносить существующие задачи на другие номера автоматически |
| B09 | DNC в campaign form | Сводка + отдельное управление; либо явно независимая немедленная запись | «Отмена» черновика не обещает rollback DNC; scope по умолчанию локальный при его наличии |
| B10 | Retry interval 0 | Сохранить 0 как явное значение; пусто значит default | Нулевой retry всё равно подчиняется scheduler/DNC/лимиту попыток |
| B11 | CID/carousel | Versioned per-trunk policies, legacy adapter | Не менять последовательность старого rotate в том же «рефакторинге без поведения» |
| B12 | Неподдержанный scenario step | Диагностика и запрет запуска вместо молчаливого NoOp | Read/edit старой кампании доступны, проблемные шаги видны |
| B13 | Defaults и поиск | Общие defaults для новых записей; телефонный поиск отдельным расширением | Сохранённые значения не нормализовать в новые defaults автоматически |

Часть исправлений обязательна независимо от выбора UX: A01-A06, отсутствие двойного звонка, атомарность сохранения, tenant validation и last-mile DNC. Продуктовые варианты B01-B13 нужно зафиксировать перед соответствующим этапом; сейчас дополнительных ответов для завершения анализа не требуется.

## 4. R1. Сохранность данных и HTTP-контракты

**Закрывает:** A01-A07, часть A11/A12/A22. Это первый рекомендуемый implementation slice.

Работы:

1. В shared выделить read DTO, Create/Update DTO, ContactPage и error contract. На минимальном первом шаге frontend может принять существующий `{items,total}`; добавление page/page_size не должно быть фиктивным cast. При необходимости совместимости использовать явный переходный adapter.
2. Добавить GET контакта по uid с проверкой base+tenant; форма редактирует именно запрошенный контакт, не ищет его в первой странице.
3. Заменить replaceFields на diff по stable UID. Переименование label/key не меняет идентичность; смена type/remove имеет проверку зависимых values/import profiles/scenario variables.
4. Обновлять phones по стабильному UID. Смена raw/normalized номера является изменением адресата и требует согласованной политики задач; изменения комментария не затрагивают телефоны.
5. Вынести общий pure contact validator/normalizer для ручного ввода и import; phone-required проверять в phone-данных. Различить undefined, null и пустую строку. Применить строгую валидацию numeric/boolean/enum, не считать строку «false» истинной.
6. Общий parse/normalize/validate pipeline для preview/import. Mapping колонок по стабильному индексу с подписью, не только header string. Профиль и его изменения явно попадают в итоговый import plan.
7. Исправить intra-file и existing-base dedup phone/external_id; задать поведение строки с несколькими номерами и частичным совпадением. Счётчики imported/skipped/errors относятся к строкам и согласованы.
8. Replace выполняется только после валидации и подтверждения. Ноль пригодных строк не удаляет данные; конфликт revision после preview требует повторного preview. Проверить активные/ожидающие задачи до замены.
9. Зафиксировать поддерживаемые CSV/TXT/XLSX; `.xls` либо явно отклонять до upload с объяснением, либо добавить отдельный проверенный parser как расширение.

**Критерии:**

- HTTP integration + UI integration: создание стандартной базы и ручного контакта с required phone успешно; контракт списка совпадает без `as never`.
- Контакт №60+ открывается с правильными данными; ошибка загрузки не превращается в пустой редактируемый контакт.
- Rename/reorder/add field сохраняет старые values и channel variable mapping; отменённая транзакция не меняет schema revision.
- Сохранение только comment сохраняет phone_uid и валидность ac_tasks; очистка comment/external_id действительно сохраняется.
- Delete phone/contact, change base, replace import не создают задач на исчезнувший/другой адресат; история попыток не теряется.
- CSV с повторными заголовками, без header, другим delimiter, quoted newline; XLSX; дубликаты и все ошибочные строки дают предсказуемый preview и commit.
- Replace с 0 валидных строк и искусственной DB-ошибкой оставляет исходные контакты целыми.
- Total при нескольких phones считает контакты, а не join-строки. Foreign tenant base/contact/profile/field/phone недоступны.

## 5. R2. Корректный звонковый lifecycle и сценарии

**Закрывает:** A13-A22. Разбить на отдельные PR R2a/R2b/R2c, не смешивать с новой CID-каруселью.

### R2a. Конфигурация, compiler, deploy

- Объединить validation и capability matrix editor/runtime. Дать autodial явный adapter к общему renderActionChain; настроить channel variables, preamble/finalize, tenant resolution, TTS preparation. Не расширять metadata на неподдержанный backend.
- Проверять disabled/условные/недостижимые шаги, современные ValueSource и ссылки на queues/trunks/directories/prompts. Для dynamic queue объявить допустимый пул операторов, а не угадывать его.
- Конфигурация и schedules сохраняются в одной DB-транзакции после всей валидации. Deploy после commit имеет status/error/appliedRevision; start/resume проверяют актуальную применённую ревизию.
- Optimistic concurrency: ожидаемая revision в update, 409 при конфликте, без last-write-wins по умолчанию.

**Приёмка:** modern target направляет в выбранную очередь; legacy fallback после adapter эквивалентен; поддержанные TTS/playback/условия/переходы исполняются; неподдержанный шаг даёт конкретную ошибку до start. Fault injection DB/deploy не оставляет ложного running. Другой tenant не может сослаться на чужой ресурс.

### R2b. Состояние ARI и результат попытки

- Явные состояния: reserved -> created -> dialing -> answered -> handed_off -> finalized. Зарегистрировать correlation до событий, сделать transitions идемпотентными. StasisStart не означает answer при create+dial.
- Настроить CID поддержанным способом до dial; отдельно проверить SIP/провайдера. Ошибка после create освобождает канал/резерв и закрывает attempt ровно один раз.
- Финализация объединяет ARI, hangup-handler и CDR evidence монотонно. Не стирает непереданное поле; late enrichment не противоречит уже запланированному retry. Предусмотреть bounded ожидание финальных данных либо контролируемое reconciliation до следующей попытки.
- Разделить answer time, queue wait, agent talk и AMD. Согласовать B06 до изменения success/retry/predictive.
- Lease heartbeat/fencing; живой channel не становится pending по возрасту lease. После restart сверяться с PBX и durable attempts, а не только локальной Map. Stop/drain и смена базы не создают второй live attempt.

**Приёмка:** event permutations create/StasisStart/Up/Destroy/HTTP result, повторы и потеря событий дают один outcome и одно advanceTask. Разговор >120 с, pause/resume, stop/start и backend restart не вызывают повтор того же живого номера. Тестируются отказ create/dial/continue и очистка ресурсов. Отчёты/predictive получают согласованные показатели.

### R2c. Eligibility и capacity

- Общая проверка перед стартом каждой попытки: статус/revision кампании, существование адресата, DNC и окно времени. Уточнить линеаризацию конкурентного DNC add: блокировка действует на новые, ещё не начатые попытки, без обещания автоматического hangup.
- Нормализация DNC и телефонов согласована; global/base/campaign и expiry проверяются tenant-scoped.
- Каждый capacity provider возвращает число новых доступных слотов. Не смешивать total limit и remaining. Дедупликация операторов и резервы на общем ресурсе, включая две кампании.
- Выбор транка видит его availability и reserve; occupancy snapshot имеет возраст/TTL и явный degraded mode. При неизвестной доступности безопасная политика зафиксирована, а не случайный fail-open.
- Учесть worker topology: при нескольких инстансах durable/shared reservations или один назначенный dialer owner с fencing. Не вводить новый Redis без проверки существующей инфраструктуры.
- Подключить subscriber-hour gate после B04; invalid timezone и all-disabled semantics после B02/B03. Восстановление окна не сбрасывает счётчик попыток.

**Приёмка:** tenant10/active4 даёт 6 новых слотов при отсутствии других ограничений; trunkFree6 не теряет ещё 4; saturated trunk не выбирается. Mixed unlimited/limited, один агент в двух очередях, две кампании на одном транке, stale AMI и конкурентные leases не превышают лимит. DNC, добавленный после генерации tasks, блокирует новую попытку. UTC/DST/даты/границы интервалов/отключённые правила проходят deterministic clock tests.

## 7. R4. Универсальные транки и per-trunk CallerID

**Закрывает:** расширение по замечанию 6, опирается на исправленные A14-A16/A22.

Работы:

1. Определить versioned dialing-policy: selection strategy, per-trunk limit/timeout/CID, campaign fallback, allowed technical failover causes. Read adapter поддерживает legacy weighted + static/rotate/per_trunk.
2. Общая модель CID: static, pool(random/round_robin), directory с явным lookup key для host autodial. Отсутствие значения: настроенный fallback либо отказ с диагностикой, не случайный чужой CID.
3. Извлечь независимо используемые editor primitives в entities/trunk или другой согласованный нижележащий слой. Нейтральные контролы не знают RTK/конкретный campaign draft; feature передаёт справочники и capabilities.
4. Общие normalizers/resolvers с отдельными dialplan и ARI adapters. Не переносить Asterisk Dial()-строки в ARI-originator.
5. Независимые конкурентно безопасные курсоры выбора транка/CID; случайность инъецируемая для тестов. Учесть веса, пустые/дублированные CID, смену списка и scoped cursor identity.
6. Failover создаёт технические legs внутри ограниченной попытки, не маскирует повторный контакт. Busy/no_answer по умолчанию идут в retry policy, не мгновенно в другой транк.
7. Effective-limit preview и проверка caller ID в SIP на тестовом маршруте. Использовать только разрешённые организацией/провайдером номера.

**Критерии:**

- Legacy fixtures дают тот же target/CID до upgrade, старые кампании не переписываются при открытии формы.
- Два транка с разными статическими CID, два независимых pool, directory hit/miss, пустой pool, saturated trunk и технический отказ покрыты unit/integration.
- Concurrency не выдаёт один и тот же reservation сверх лимита; round-robin определён при параллельных workers.
- SIP capture/серверная диагностика подтверждает фактически переданный CID. UI-конфигурация сама по себе не считается доказательством.
- Regression tests редактора маршрутов подтверждают, что его carousel не изменился из-за общего компонента.
- UI объясняет стратегию и источник effective value; фильтрация возможностей по host не скрывает сохранённое legacy значение.

Работы:

1. Зафиксировать актуальные AMDSTATUS/AMDCAUSE и параметры поддерживаемой PBX. Настройки эксперта показывать только если backend их реально поддерживает; defaults текущего amd.conf не выдумывать.
2. Машинная ветка: завершить / продолжить / воспроизвести сообщение. Для последнего требуется запись из существующего модуля prompts либо текст через существующий TTS и успешная подготовка media.
3. Явно разделить обнаружение автоответчика, ожидание готовности к записи и воспроизведение. Timeout/fallback обязательны. Не обещать гарантированную доставку сообщения без подтверждаемого критерия.
4. Сохранить исход классификации и исполнения media; один результат попытки, согласованный retry. NOTSURE/HANGUP имеют описанную политику.
5. ML/ASR альтернатива только отдельным spike: сравнение точности, false-human/false-machine, задержки, нагрузки/стоимости и приватности аудио. Не заменять stock AMD на основании слова «современный».

**Критерии:**

- До ответа AMD/сценарий не запускается; ранний media не считается ответом.
- Тестовые человек/автоответчик/тишина/шум/неопределённость дают сохранённые status/cause и ожидаемую ветку.
- «Оставить сообщение» действительно проигрывает выбранный материал в machine-ветке, а не Hangup. Missing media/TTS failure видны до start либо имеют явно выбранный fallback.
- Длительность AMD не выдаётся за разговор оператора. Результат соответствует monitor/report/retry.
- Threshold качества определяется по тестовому набору, а не заявляется процентом без измерений.

## 9. R6. Сквозная проверка и ввод

Матрица happy path + failures:

| Поток | Проверка |
|---|---|
| База -> импорт -> контакт -> переменная сценария | Стабильные UID, типы, значения, revisions |
| Campaign -> Save -> Apply -> Start | Нет звонков по неприменённой/невалидной версии |
| Create -> Dial -> Answer -> Scenario -> Finalize | Единственная попытка и корректный outcome |
| DNC/schedule -> pending task -> new attempt | Блокировка по актуальным правилам |
| Транк/CID -> SIP -> outcome | Ограничения и фактическая идентификация |
| Pause/Stop/Restart + long call | Нет второго живого звонка |
| Два tenant / две кампании / несколько workers | Изоляция и общий лимит ресурсов |
| Browser form -> mutation error -> retry | Сохранённый ввод, понятная ошибка, нет ложного успеха |

Обязательные команды перед объявлением implementation «готово»:

```bash
npm run lint
npm run test:backend
npm run test:frontend
```

Дополнительно: build/typecheck по scripts проекта, DB-backed integration, browser UAT, тестовая PBX и fault injection. При существующих unrelated failures записать точные команды/ошибки и не выдавать общий CI за зелёный.

Измерения производительности: фиксированный fixture и окружение, baseline p50/p95 API contacts/search/import, число запросов при наборе поиска, память import, длительность pacer tick и отставание event processing. Прогнать 1k/10k и репрезентативный максимальный размер базы; при недостаточной ёмкости отдельно согласовать chunked/job import и SQL индексы. Не обещать «миллион контактов» без замера.

Ввод и откат:

- Additive schema/API сначала, adapters для старых JSON и конфигураций. Любая data migration имеет dry-run, backup и журнал affected UID.
- Если старые field_uid уже утрачены, остановить автоматический repair и восстанавливать соответствия только из достоверной истории/backup. Новая схема сама не возвращает старые данные.
- Сначала тестовый tenant, затем выбранные кампании с drain активных попыток; не переключать runtime посреди живого вызова.
- Kill switch останавливает новые originate, сохраняя наблюдение/финализацию активных. Откат версии не откатывает завершённые реальные звонки и не должен повторно выдавать их задачи.
- Перед rollback проверить, умеет ли старая версия читать новые policy/schema. Неподдерживаемую новую конфигурацию не отдавать старому runtime; оставить feature выключенной или использовать заранее подготовленный backward adapter.
- Только после подтверждённой приёмки обновить STATE/ROADMAP и создать SUMMARY/VERIFICATION. Публикация/деплой требуют отдельного разрешения, этот план их не выполняет.

## 10. Минимальный следующий шаг

Начать с R0 + первой части R1: общий контракт списка, detail endpoint, required-phone validation и сохранение UID полей/телефонов с DB-backed regression tests. Это ограниченный результат с наибольшей пользой для сопровождения и защиты данных. Не начинать с переименования десятков каталогов или универсального form-builder.

Результат исходного анализа: два документа анализа/плана, 161 существующий профильный тест проверен, пять read-only диагностических проб выполнены. Последующая реализация и её проверки фиксируются отдельно в журнале реализации; исторический анализ не является verification нового кода.
