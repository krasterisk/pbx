# Автообзвон: внешние gates, 2026-09-18

Scope: локальный frontend/backend против тестовой БД и `ipbx.krasterisk.ru`. Пользователь разрешил любые номера на тестовом стенде. На момент старта в `ac_campaigns` не было кампаний; существующий автообзвон не запускался. Во время последующих проверок дефекты исправлялись в рабочей копии кода.

После последнего среза: `npm run lint` завершился без ошибок (warnings); backend production build и frontend typecheck прошли; `npm run test:backend` дал 250 suites / 2892 passed, 11 skipped. Autodial frontend slice дал 17 files / 87 passed. Unit-контракт ARI проверяет `callerId` в query `/channels` и остальные переменные в body.

Дополнительный запуск актуального backend для campaign-to-DB gate остановился на `SchemaReadinessBootstrap`: существующая тестовая MySQL является unversioned legacy schema и новая DB-02 проверка намеренно не принимает её без migration journal. Миграцию либо обход guard не выполняли. Нет кампаний, активных задач и незакрытых попыток в исходной тестовой БД на момент preflight. Отдельная versioned fixture DB может проверить backend/DB lifecycle, но SIP PBX читает PJSIP realtime из исходной БД; это разные gates.

Затем отдельная versioned fixture `krasterisk_ci_ac20260918z` была создана с канонической миграцией и CI seed. В ней через HTTP созданы база, контакт, кампании и тестовый PsEndpoint. Транк намеренно отсутствовал на PBX, поэтому внешнего вызова быть не могло. Первая попытка start выявила отсутствующий каталог `/etc/asterisk/krasterisk/autodial`; каталог создан на тестовой PBX. Повторный start создал одну задачу и одну завершённую ошибкой попытку с ожидаемым CallerID. Cleanup выявил FK-дефект удаления неиспользуемой базы; `AutodialBasesService.remove` исправлен, DB integration regression прошёл, после перезапуска backend повторный cleanup прошёл. Удаление кампании оставляет `ac_attempts` без существующей кампании/задачи: это отдельный вопрос политики хранения истории, не закрытый очисткой fixture. Исходная тестовая БД не менялась этими HTTP-прогонами.

## Изоляция и очистка

- Для AMD был создан только динамический контекст `codex-ac-gate-20260918-1545` с `Local/human`, `Local/silent`, `Local/machine` и `run`. Все четыре extension и сам контекст удалены после проверки.
- SIP logger был включён только для host `127.0.0.1` и отключён после capture. SIP-звонок адресован только loopback `127.0.0.1:59999`, без внешнего провайдера или реального абонента.
- Для сравнения ARI-контрактов дополнительно создан собственный IP-транк `t_codex_cid_loop_20260918_0` с contact `sip:127.0.0.1:5060` и динамический контекст `codex-cid-loop-20260918-0` с двумя ответными номерами. Оба CallerID и несуществующий маршрут проверены через этот контекст. Транк и контекст удалены; SIP logger выключен; PBX после очистки показала 0 active channels / 0 active calls. Пользовательский backend не останавливался.
- Временный dialplan `ac_2.conf` versioned fixture удалён после проверки, контекст `krsk-ac-1` отсутствует, PBX показывает 0 active channels / 0 active calls. Созданный каталог `/etc/asterisk/krasterisk/autodial` оставлен как необходимая инфраструктура для применения кампаний. Собственный backend остановлен, fixture DB `krasterisk_ci_ac20260918z` удалена с проверкой маркера; удаление не восстанавливается, в ней были только созданные этим прогоном данные.
- После первого gate тестовый контекст отсутствовал, было 0 активных каналов и вызовов; временное ARI-приложение и запущенный для gate локальный backend были остановлены. При дополнительной проверке самозаворота пользовательский backend работал и не останавливался нами.
- Пробный Local CDR на PBX вызвал существующую ODBC-ошибку `Column 'usrc' cannot be null`; это не ошибка runtime AMD, но любые CDR-метрики этого синтетического теста недостоверны.

## Следующий приоритет

1. Повторить CallerID capture через реальный campaign path после перезапуска backend с исправленным кодом. Отдельно проверить tenant trunk policy: провайдер может переопределять `From`/PAI/RPID независимо от ARI.
2. Пройти матрицу ARI event order (early `StasisStart`, `Up`, hangup до ответа, дубли, delayed callbacks) и terminal DB state. Изолированная failure-ветка `ChannelDestroyed:Down` уже проверена.
3. Перед multi-worker/restart gate реализовать durable lease owner/fencing и reconciliation. Перед voicemail gate определить media source и playback, не включать опцию без исполнимого сценария.

## Дополнительный campaign SIP gate

Versioned fixture и отдельный скрытый локальный backend подтвердили полный путь campaign → task → ARI → SIP loopback → `answered_short`: PJSIP capture содержит `From`, `P-Asserted-Identity` и `Remote-Party-ID` с `74954445566`, а принимающий временный контекст был достигнут. Первые запуски с `ARI_APP_NAME=krasterisk_robot_dev` не считаются evidence финализации: на PBX активна `krasterisk_voicerobots`, поэтому для валидного прогона backend был запущен с этим именем. При корректной application ARI доставил `StasisStart`, `ChannelHangupRequest`, `StasisEnd` и handoff в `krsk-ac-1`; attempt стал terminal `answered_short`.

Порог полноценного `success` требовал отдельного продолжительного сценария. Повторный изолированный запуск с `collect_input(timeout=16)` завершил реальную задачу как `completed`, а попытку как `success`; `answered_at` и `ended_at` различаются на 17 секунд, `caller_id=74954445566`. Во время этого прогона выявлен и исправлен конфликт обработчиков одного ARI application: `VoiceRobotsService` завершал канал `ac-*` без `robotUid` раньше, чем `AutodialOriginatorService` передавал его в сценарий. Теперь `ac-*` оставляется модулю автообзвона; добавлен unit regression. На проводе CallerID уже был подтверждён в предыдущем campaign loopback capture (`From`/PAI/RPID); итоговый success gate подтвердил тот же CallerID в фактической campaign attempt.

После success gate штатный API удалил обе тестовые кампании и базы, исходный временный endpoint/AoR/identify удалён helper-ом, а временный dialplan-файл удалён после проверки его маркера. Финальный `dialplan reload` вернул `There is no existence of 'codex-ac-campaign-loop-20260918-2' context`; `krsk-ac-1` также отсутствует. Собственный backend остановлен, fixture DB `krasterisk_ci_ac20260918z` удалена только после marker check. На PBX не осталось тестового канала, транка или контекста.
