# API 9057: call_tts

Адрес: `https://mpbx.krasterisk.ru/api/9057/index.php`. POST, `application/x-www-form-urlencoded`; существующий ключ API9057 в заголовке `Authorization: Bearer <ключ>`. JSON-тело не разбирается.

| Параметр | Назначение |
|---|---|
| `action` | Обязательно `call_tts` |
| `lead_id` | Обязательный положительный числовой ID; передаётся существующей Bitrix-интеграции |
| `tts` | Обязательный непустой текст UTF-8 в одну строку |
| `phone` | Обязательный номер; `+`, пробелы, скобки, точки и дефисы удаляются; остаётся 3–20 цифр |
| `inner_id` | Внутренний номер сотрудника Битрикс, по умолчанию `8888` |
| `ivr_id` | ID меню, по умолчанию `7` |
| `callerid` | АОН, по умолчанию `+79639584261`; фактический АОН зависит от оператора |
| `channel` | По умолчанию `SIP/beeline_expert/{phone}`; `{phone}` заменяется нормализованным номером. Можно указать полный канал либо префикс `SIP/my_trunk` — номер допишется автоматически |
| `answer_hook`, `hangup_hook` | Необязательные HTTP(S)-адреса; при наличии проверяются и передаются в переменные `ANSWER_WEBHOOK`, `HANGUP_WEBHOOK`, как в `call` |
| `usercallid` | Необязательный внешний ID попытки, передаётся в `USERCALLID` |

Пример (Linux/macOS; вместо `API9057_KEY` подставьте свой ключ через переменную окружения):

```bash
curl 'https://mpbx.krasterisk.ru/api/9057/index.php' \
  -H "Authorization: Bearer $API9057_KEY" \
  --data-urlencode 'action=call_tts' \
  --data-urlencode 'lead_id=12345' \
  --data-urlencode 'phone=+79990000001' \
  --data-urlencode 'tts=Иван, подтвердите запись. Нажмите один для подтверждения.'
```

Без дополнительных параметров используются внутренний8888, IVR7 и исходный транк/АОН. Для переопределения добавьте, например, `--data-urlencode 'ivr_id=8'`, `--data-urlencode 'callerid=+79991112233'`, `--data-urlencode 'channel=PJSIP/{phone}@my_trunk'`. Передавайте запросы последовательно либо с ограничением параллельности, соответствующим настройкам АТС.

Успешный ответ: `{"status":"ok","action":"call_tts","bitrix_call_id":"...","data":{"response":"Success",...}}`. Это постановка вызова в обработку AMI, не подтверждение дозвона. Нет/неверно обязательное поле → HTTP400; ошибка регистрации Битрикс → HTTP502 без запуска звонка; отказ AMI → `status:error`. Формат ошибок400/502 наследуется от API (`statusCode`, `messsage`, `error`).

Контекст после ответа — существующий `tts_dial`. Сейчас он запускает фиксированный бизнес-процесс для `DYNAMIC_150_<lead_id>` и использует существующее завершение звонка. `lead_id` не является произвольным `deal_id`. IVR7 — действующее DTMF-меню с озвучиванием `${tts}` и кнопкой1; произнесённое «да» само по себе этим меню не распознаётся.

**Ограничение вебхуков:** новый метод принимает и передаёт `answer_hook`/`hangup_hook`, но общий `tts_dial` их сейчас не вызывает: он использует фиксированные Bitrix-уведомления. Его `tts_hh` отправляет `ANSWERED` и пустую запись. Метод не добавляет AMD, финальный отчёт о недозвоне или запись. Обработка этих данных требует отдельного изменения контекста; в этой поставке dialplan не изменяется.

Регистрация вызова сохраняет настройки исходного API2; его приватный REST-адрес копируется только внутри сервера при публикации. Никакие ключи в эту документацию не включены. На сервере API9057 использует существующий `user_uid=2`; название каталога9057 не меняет кабинет.
