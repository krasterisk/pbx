## 0. Правила работы с npm пакетами

> **ОБЯЗАТЕЛЬНО выполнять при каждой установке нового пакета:**

### 🔴 Проверка актуальности перед установкой

Перед `npm install <package>` **всегда** выполнять:

```bash
# 1. Проверить последнюю стабильную версию и dist-tags
npm show <package> version dist-tags

# 2. Проверить peerDependencies на совместимость
npm show <package>@latest peerDependencies

# 3. Проверить критические breaking changes (смотреть CHANGELOG или README)
# Особенно если мажорная версия > той что ты знаешь
```

### Когда проверять особенно тщательно

- **Мажорная версия изменилась** (например, v9 → v10) — всегда читать CHANGELOG
- **Пакет активно развивается** (MCP SDK, AI-библиотеки) — могут быть breaking changes даже в минорных версиях
- **Транспортный/протокольный слой** (`@modelcontextprotocol/sdk`, `socket.io`) — API меняется часто

### Примеры выявленных проблем

| Пакет | Версия | Проблема |

## 1. Мульти-Тенантность и Изоляция Данных
Система спроектирована как **Multi-Tenant SaaS**. Это означает, что несколько организаций (тенантов) могут существовать в одной базе данных (`krasterisk`) без пересечения их данных.

### Принцип `vpbx_user_uid`
Ключевым атрибутом изоляции является поле `vpbx_user_uid`.
- **В БД:** Каждая сущность (пользователь, роль, sip-клиент, номер) имеет колонку `vpbx_user_uid` со значением ID "владельца тенанта" (организации).
- **На уровне Контроллера:** Все контроллеры (защищенные авторизацией) извлекают `vpbx_user_uid` из контекста запроса `@Req() req` (`req.user.vpbx_user_uid`). Слой контроллера не доверяет идентификаторам тенанта из `Query` или `Body`.
- **На уровне Сервиса:** Бизнес-логика (findAll, update, delete) **всегда** требует передачи `vpbx_user_uid` вторым или обязательным параметром. Внутри сервиса автоматически формируется фильтр SQL-запроса: `where: { vpbx_user_uid }`.

**Итог:** Залогиненный пользователь видит и имеет право изменять только те записи, которые принадлежат его тенанту (`vpbx_user_uid`).

## 2. Аутентификация и Защита (Auth & RBAC)

### Access и Refresh Токены (Multi-Session)
Бэкенд использует продвинутую JWT систему:
- **`accessToken`** (живет короткое время, например, `15m`): используется для всех авторизованных запросов. Хранится в памяти или `sessionStorage` на Frontend'е.
- **`refreshToken`** (живет долго, например, `7d`): используется для получения нового `accessToken` без ввода пароля. Возвращается при входе.
- **Мульти-Сессии (`user_sessions`):** `refreshToken` сохраняется в таблицу `user_sessions` (каждый вход с браузера/телефона создает отдельную сессию). Если пользователь заходит с нового устройства, старая сессия не сгорает.
- **Rotation (Вращение токенов):** При обращении к `POST /auth/refresh` со старым Refresh-токеном, бэкенд верифицирует его, сбрасывает старую запись в БД, и возвращает новую безопасную пару `accessToken` + `refreshToken`.

### RBAC - Ролевая модель (`RolesGuard`)
Система управления доступом на основе уровней:
- Создан кастомный декоратор `@Roles(UserLevel.ADMIN)` (`src/modules/auth/roles.decorator.ts`).
- Создан `RolesGuard` (`src/modules/auth/roles.guard.ts`).
- Защита эндпоинтов осуществляется путем наложения ограничения прямо на контроллер или метод. Гуард автоматически читает `user.level` из JWT-контекста и пропускает или блокирует запрос.

## 3. Модуль Аудита / Логирование
Все активные, деструктивные или критические изменения логируются.

### `action_logs`
- **БД Отражение:** Таблица `action_logs`, модель `ActionLog` (`logger/action-log.model.ts`).
- **Модуль и Сервис:** `LoggerService` предоставляет метод `logAction`.
- **Как работает:** Внедряется (`inject`) в любой контроллер/сервис. Вызывается после успешного завершения CRUD операций, чтобы записать: *кто (userId), что сделал (action), над какой сущностью (entityType: user, peer и др.), и в каком тенанте (vpbx_user_uid).*

## 4. Интеграция с внешними сервисами

Для оповещения пользователей и администраторов реализованы два модуля-коннектора:

### Mailer (`MailerModule`)
Использует библиотеку `nodemailer` (подключение через SMTP, задаваемое в `.env`: `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`).
- **Как работает:** `MailerService` отправляет HTML-письма клиентам (напр. `sendActivationMail`).
- **Интеграция:** Используется `AuthService` для отправки 6-значных кодов активации при регистрации (`POST /auth/register`). Пользователь должен затем подтвердить код через `POST /auth/activation`.

### Telegram (`TelegramModule`)
Использует `node-telegram-bot-api` (`TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`).
- **Как работает:** Инициализируется как фоновый API клиент; может рассылать сообщения по заданным `chatId`.
- **Интеграция:** Глубоко встроен в `LoggerService`. В случае важных системных событий (логин, регистрация, удаление) бот автоматически дублирует сообщения в администраторский чат, обеспечивая моментальный оперативный контроль за состоянием PBX.

## 5. Модуль Endpoints (PJSIP) и Телефония

Модуль управляет внутренними абонентами (Extensions/Peers) через архитектуру **Asterisk PJSIP Realtime** (Alembic/ODBC).

### Прямая интеграция с БД (Realtime)
Вместо генерации статических конфигурационных файлов (типа `pjsip.conf`), бэкенд пишет конфигурацию напрямую в SQL-таблицы Asterisk Realtime:
- **`ps_endpoints`** — базовые настройки, транспорт, кодеки, контексты, ACL (`permit`/`deny`).
- **`ps_auths`** — логины и пароли абонентов (связаны с endpoint через `auth=`).
- **`ps_aors`** — настройки регистрации (max_contacts) и раутинг вызовов.
- Опционально читается статус регистрации из **`ps_contacts`**.

Asterisk настроен на автоматическое чтение данных из БД (sorcery), поэтому при сохранении DTO абонента никаких дополнительных `reload` команд или `apply` на стороне Asterisk делать не нужно. Данные подхватываются прозрачно и моментально.

### Изоляция абонентов (Tenancy) в телефонии
В отличие от большинства стандартных таблиц платформы, Asterisk Realtime не знает про поле `vpbx_user_uid` напрямую (схема таблиц жёстко задана Астериском). Поэтому безопасность и изоляция достигается на логическом уровне:
1. **Контексты маршрутизации (Dialplan):** Суффикс арендатора неявно привязывается к контексту (например, `sip-out12`, где `12` — это `vpbxUserUid`).
2. **Перехват вызовов (Pickup Groups & Call Groups):** Asterisk имеет глобальное пространство имён для групп перехвата. Чтобы тенанты не могли перехватывать вызовы чужих компаний, при создании группы слаг (slug) аппаратно "неймспейсится" идентификатором арендатора.
   *Пример:* Тенант создает группу «Отдел продаж». Имя генерирует слаг `prodazhi`. В Asterisk уходит: `t{vpbxUserUid}_prodazhi`. Это полностью исключает коллизии между арендаторами.

### Расширенные параметры (Advanced Builder Pattern)
Стандарт PJSIP поддерживает более 100 различных параметров (timers, fax, session timers, media options). Создавать в коде и TypeScript DTO все эти 100+ полей - антипаттерн, приводящий к раздуванию кода.
- Реализован паттерн **Dynamic Settings Builder**.
- Любые расширенные ключи (`rtp_timeout`, `fax_detect`, `direct_media`) динамически добавляются пользователем через UI.
- На фронтенде собирается JSON объект в поле `advanced`.
- На бэкенде эти ключи безопасно извлекаются и с помощью спреда (spread `...advancedState`) аккуратно раскатываются по столбцам таблицы `ps_endpoints` при `create/update`.

### Фоновая обработка (Bulk Operations)
Создание или удаление большого массива абонентов (сотни штук) - ресурсоёмкий процесс для БД, так как затрагивает каскадно таблицы `ps_endpoints`, `ps_auths`, `ps_aors`.
Вместо удержания (blocking) HTTP-запроса используется асинхронный паттерн с **Background Jobs**:
1. Клиент забрасывает профили на `/endpoints/bulk`.
2. Бэкенд генерирует задачу и моментально отдаёт `jobId` со статусом `pending`.
3. Отдельный In-Memory Worker в цикле обрабатывает создание (batching), логируя прогресс (processed/total).
4. Клиент опрашивает `/bulk/status/:jobId` (`Long Polling` / интервалы), отображая прогресс-бар в реальном времени. В конце обновляет таблицу.

## 6. MCP Server (AI Tool Protocol)

Модуль `McpModule` — внешняя JSON-RPC точка (`/api/mcp`) и единый dispatch `McpToolsService.callTool`. Инструменты **не** регистрируются вручную в этом сервисе.

### Транспорт: Streamable HTTP

```
POST   /api/mcp  — JSON-RPC запросы (инициализация + tool calls)
GET    /api/mcp  — SSE-поток уведомлений (опционально)
DELETE /api/mcp  — закрыть сессию
GET    /api/mcp/sessions — debug: активные сессии
```

`SessionId` — заголовок `Mcp-Session-Id`. Сессия привязана к тенанту, который её создал; resume с чужим JWT отклоняется.

### Аутентификация (D-28)

Только пользовательский JWT (`JwtAuthGuard`). Тенант берётся из `req.user.vpbx_user_uid`.

Больше не читаются на `/api/mcp`:
- `KRASTERISK_SERVICE_TOKEN` + `X-Vpbx-User-Uid` — service-token ветка снята
- заголовок тенанта при валидном JWT игнорируется, не ошибка

`AIPBX_URL` / `AIPBX_CHAT_ID` / `AIPBX_TOKEN` больше не читаются — in-process loop (15-08) заменил chat proxy. aiPBX и прочие внешние API остаются **провайдерами модели** (`cc_ai_providers`), не оркестраторами инструментов.

### 🔴 ОБЯЗАТЕЛЬНОЕ ПРАВИЛО (D-16): новый модуль → адаптер + skill + классификация

Норматив. Модуль без этой пары считается недоделанным. Проверка — не ревью, а падающий тест.

1. Рядом с сервисом модуля — `<module>-ai.adapter.ts`, который регистрируется в `AiAdapterRegistryService`. Инструменты **не** добавляются в `McpToolsService`.
2. Каждый tool принимает `vpbxUserUid` параметром вызова и не захватывает его замыканием и не объявляет в `inputSchema` (D-22 / D-23).
3. Мутирующий tool возвращает `AgentDiffProposal` (`proposes: true`) и не пишет в АТС сам.
4. Рядом с модулем — актуальный `src/skills/<domain>/SKILL.md` (или явный `sharedSkill` в классификации, если несколько доменов честно делят один файл).
5. Каталог модуля занесён в `src/modules/ai-platform/module-coverage.registry.ts`: `covered`, либо `infrastructure` / `excluded` с непустой причиной.

**Где проверяется:** `ai-adapter-completeness.spec.ts` (D-17). Новый каталог в `src/modules/` без строки в реестре, covered без адаптера, covered без скила, битый frontmatter скила, tool вне классифицированного домена — красный прогон. Молча вычеркнуть домен нельзя: у `infrastructure` и `excluded` обязана быть причина.

**Реестр:** `AiAdapterRegistryService` (`getDomains()` — ключи для сверки).  
**Dispatch:** `McpToolsService.callTool(name, args, vpbxUserUid)` — uid всегда параметр вызова.  
**Промпт:** блоки знаний адаптера + каталог скилов (`read_skill`), не `.docs/`.  
**Пояснение для агента:** `src/skills/developer-convention/SKILL.md`.

### Инвентарь инструментов

Число и имена — живой реестр адаптеров (`getAllTools()`), не таблица в этом файле. Рукописные 18 имён фазы 1 сняты (15-15). `apply_dialplan` снят как standalone (применение — часть confirm маршрута, 15-11).

### Аудит до миграции (T-15-72)

Две локации, данные не сливали:
- `action_logs` — `LoggerService.logAction`, action `ai_tool` (handwritten MCP и текущий `callTool`)
- `cc_ai_audit_log` — записи AI-агентов; колонка `thread_uid` с 15-03

## 8. Версии Asterisk

Проект **не привязан к одной версии** Asterisk. Решения по приложениям и опциям опираются на диапазон поддержки и известные пробелы, а не на жёсткий пин («должно быть ≥16, иначе стоп»).

### Наблюдаемый прод (M1, 2026-08-20)

Целевой PBX `ipbx.krasterisk.ru`:

```
Asterisk certified-22.8-cert2 built by root @ ipbx.krasterisk.ru on a x86_64 running Linux on 2026-04-11 06:47:19 UTC
```

Это **пример боевой установки**, не единственная поддерживаемая линия.

### Политика диапазона

| Линия | Статус | Как относиться |
|---|---|---|
| **22+** (включая Certified 22) | Предпочтительная | Документация приложений фазы 12 (`Playback`/`noanswer`, `ControlPlayback`, `Progress()`, `Record()` + `k`, `hangup_handler_push`, `QUEUE_PRIO`, `QUEUESTATUS`) сверена с Asterisk 22 |
| **16** | Возможна | Те же приложения в целом есть на LTS 16; перед опорой на конкретную опцию (`Record()` `k`, `Playback` `noanswer`) проверить на целевом хосте |
| **11** | Возможна, больше пробелов | Hangup handlers есть с 11; слой этого бэкенда — **PJSIP Realtime** (см. §5), тогда как 11-era по умолчанию `chan_sip`. Часть поздних опций `Record`/`Playback`/`Queue`/`Dial` может отсутствовать. 11 — best-effort: прогонять нужные приложения на хосте, не считать отсутствие опции блокером всей платформы |

### Известные пробелы (не стоп-гейт)

- Генератор dialplan фазы 12 писался и тестировался по семантике **Asterisk 22**. На 16/11 расхождение опции — известное ограничение хоста, а не дефект генератора, пока приложение на этой линии отсутствует или ведёт себя иначе.
- `Progress()` + early media (D-52) зависит ещё и от SIP-провайдера, не только от версии Asterisk.
- Голосовая почта (`Record()` + `k` + `hangup_handler_push`, D-54…D-59) вынесена в Phase 12b — проверять опцию `k` на 11/16 там, не здесь.

При добавлении нового Asterisk-приложения или опции: документировать, на какой линии оно проверено, и не превращать предпочтение 22+ в жёсткий минимум без явного решения.

## 9. Боевые факты фазы 12 (M9, M12)

Зафиксировано 2026-08-20 с `ipbx.krasterisk.ru`. Не выдумывать другие значения.

### M9 — путь записей

Прод `.env`: `RECORDS_BASE_PATH=/usr/records`. Совпадает с унифицированной константой генератора (`/usr/records`). **Ретаргет не нужен, файлы записей не переносить.**

Строка `system_settings.records_base_path` в этой проверке не читалась — источник факта: `.env` на проде. Приоритет в коде: таблица `system_settings` > `.env` > дефолт `/usr/records`.

### M12 — осиротевшие PHP (`usr/scripts`)

Baseline на текущем PBX (один замер, деплоя генератора фазы 12 на этот хост ещё может не быть):

```
grep -c 'usr/scripts' /var/log/asterisk/full
→ 0
```

Ноль — сейчас в `full` нет обращений к `/usr/scripts`. **Полный гейт M12** (пара до/после тестовых звонков notify/TTS *после* деплоя фазы) ещё не закрыт: после-счётчик не снимали. Повторить после выкладки генератора.

**Общая реализация паттернов:** [ModalLayout](../../frontend/src/shared/ui/ModalLayout/ModalLayout.tsx). Для новых и модернизируемых форм использовать FormDialogContent, ModalBody, ModalSection, ModalTabs и ModalToggle через публичный shared UI API. Примеры ниже объясняют геометрию и поведение; не копировать весь SCSS shell в каждую фичу. Крупные модалки сохраняют size="large", компактные редакторы используют соответствующий size. Маленькие confirm и read-only viewer сохраняют свой сценарий и используют общий Dialog/Sheet.

### 10.1. Каркас и владение состоянием

Крупная форма с вкладками использует `FormDialogContent size="large"`: фиксированная высота оболочки, header, вкладки, прокручиваемое тело и footer. При переключении вкладок, раскрытии секций и появлении ошибок окно не прыгает. Header, вкладки и footer не сжимаются; скроллится только тело (`flex: 1; min-height: 0; overflow-y: auto`). Высота уже задана в shared Dialog: 85vh на desktop и 90dvh на мобильном. Не копировать эти значения в каждую фичу и не задавать минимальную высоту больше экрана.

Родитель хранит черновик и выполняет mutation. Вкладки получают значения, callbacks и ошибки через props. Размонтирование вкладки не сбрасывает черновик. Create/edit/copy явно инициализируют форму; новая сессия не наследует ошибки и значения предыдущей записи. Крупную модалку декомпозировать на компоненты вкладок; повторяющиеся контролы выносить в shared UI или переиспользуемый компонент соответствующей FSD-фичи.

Пример каркаса (компонент вкладки и функции предоставляются родительской формой):

```tsx
<Dialog open={isOpen} onOpenChange={(open) => !open && handleClose()}>
  <FormDialogContent size="large" aria-describedby={undefined}>
    <DialogHeader><DialogTitle>{t('module.editTitle')}</DialogTitle></DialogHeader>
    <ModalTabs items={tabs} value={activeTab} onChange={setActiveTab}
      label={t('common.settings')} />
    <ModalBody>
      {activeTab === 'general' && (
        <ModalSection title={t('module.parameters')} action={
          <ModalToggle compact label={t('common.active')} checked={draft.active}
            onCheckedChange={handleActiveChange} />
        }>
          <GeneralFields {...generalProps} />
        </ModalSection>
      )}
    </ModalBody>
    <DialogFooter>
      <Button type="button" variant="outline" onClick={handleClose}>{t('common.cancel')}</Button>
      <Button type="button" onClick={handleSave} disabled={isSaving}>{t('common.save')}</Button>
    </DialogFooter>
  </FormDialogContent>
</Dialog>
```

Если есть описание, использовать `DialogDescription` и связать его с диалогом. `aria-describedby={undefined}` применяется при отсутствии описания. Видимый `DialogTitle` обязателен.

### 10.2. Вкладки

Названия короткие и предметные: «Основные», «Dialplan», «Webhooks», «Схема». Не добавлять вкладки без отдельного пользовательского сценария. Основные настройки открываются первыми. Не делать отдельную вкладку только ради подсказки или действия, которое логичнее разместить в редакторе шага.

Строка вкладок отделяется от тела одной линией `--color-border`. Активная вкладка отличается цветом, мягкой поверхностью `--color-muted` и индикатором 2px `--color-primary`; индикатор перекрывает линию контейнера (`margin-bottom: -1px` у ряда). Не создавать двойное подчёркивание. Использовать базовый класс вкладки вместе с активным. На узких экранах разрешены перенос строки, как в маршруте, или горизонтальный скролл только панели вкладок; сами поля формы не выходят за ширину экрана.

У shared Tabs сохранять его клавиатурную навигацию и ARIA-контракт. Если навигация собрана из shared Button, обозначать состояние через `aria-pressed`, как в маршруте. Не назначать `role="tab"` без связанных tabpanel, `aria-selected` и клавиатурного поведения. Переключение вкладок не сохраняет форму и не очищает поля.

### 10.3. Логические секции и визуальная иерархия

Вкладка состоит из тематических карточек, а не сплошного списка полей. В маршруте это «Параметры маршрута», «Условия выбора маршрута», «Запись и аналитика».

| Элемент | Паттерн |
|---|---|
| Карточка | Поверхность `--color-card`, рамка `--color-border`, радиус `--radius-lg`, мягкая тень `--shadow-sm` |
| Шапка секции | Lucide-иконка на приглушённой подложке, заголовок через Text, разделитель снизу |
| Главный статус | Подписанный Switch справа в шапке; на узком экране допускается перенос |
| Поля | Label над контролом, tooltip возле Label, сообщение ошибки под контролом |
| Строка опции | Поверхность `--color-background`, тонкая рамка, подпись слева и контрол справа |
| Footer | «Отмена» как outline и основное действие «Сохранить»; видим на всех вкладках |

Отступы эталона: 16px между секциями, 12px между полями в строке, 16px внутри карточки; на мобильном внутренние отступы сокращаются до 12px. Не добавлять крупные пустые зоны, повторяющиеся заголовки и постоянные технические пояснения. Иконки помогают различать секции, но не заменяют подписи полей.

### 10.4. Переключатели и сворачивание

Для состояния «включено / выключено» (например, «Активен») использовать shared `Switch`, а не Checkbox. Checkbox подходит для выбора элементов и подтверждения отдельного условия. Подпись связана с контролом через `Label htmlFor` и `id`; клик по подписи и клавиатура должны менять состояние.

```tsx
<HStack gap="8" className={styles.activeToggle}>
  <Label htmlFor="entity-active">{t('common.active')}</Label>
  <Switch id="entity-active" checked={active} onCheckedChange={setActive} />
</HStack>
```

В форме с кнопкой «Сохранить» Switch сразу меняет локальный черновик; mutation выполняется при сохранении. Для toggle, который сохраняется на сервер сразу и читает checked из RTK Query cache, обязателен optimistic patch через `onQueryStarted`, откат `undo()` и понятное сообщение ошибки. Не переносить мгновенную mutation в форму с общим Save без отдельного решения.

Необязательные секции без настроенного содержимого по умолчанию свёрнуты; при создании «Запись и аналитика» также свёрнута. При редактировании настроенная секция может открываться сразу. Состояние раскрытия отдельно от состояния опций: сворачивание ничего не отключает, не удаляет и не отправляет на сервер. Заголовок секции является shared Button на всю ширину, содержит chevron, `aria-expanded` и `aria-controls`, работает с клавиатуры. После ручного сворачивания обычный rerender не должен принудительно раскрывать секцию.

### 10.5. Редакторы списков и дополнительные действия

Основной клик по карточке шага открывает его настройку. Дублирующая кнопка «Настроить шаг» не нужна. Кнопки drag, условий и меню останавливают всплытие клика, чтобы не открывать редактор одновременно со своим действием.

Вторичные операции (копировать, дублировать, включить/выключить, удалить) собираются в shared dropdown с кнопкой `MoreVertical` (⋮), доступным названием и tooltip. Удаление оформляется как destructive внутри меню. Операции с шаблонами размещаются в дополнительном меню редактора рядом с основным «Добавить шаг», а не отдельным рядом постоянных кнопок. Повторяющиеся меню оформлять общим компонентом, а не копировать реализацию Radix по фичам.

Условия, отключённый шаг, завершение, возможный выход из цепочки и недостижимость объединяются в одну Lucide-иконку Info на карточку. Tooltip перечисляет все применимые статусы отдельными строками. Trigger имеет доступное название «Информация о шаге», открывается наведением, фокусом и нажатием, включая мобильные устройства; его клик не открывает редактор шага. Не создавать отдельную иконку для каждого статуса. Не выводить сырые JSON, выражения условий и технические фразы поверх карточки. Подробности остаются в редакторе. Просмотровая «Схема» показывает схему; симуляторы и служебные баннеры не добавлять без отдельного пользовательского требования.

### 10.6. Стили и адаптивность

В feature-компонентах использовать `VStack`, `HStack`, `Flex`, `Text` и контролы из `@/shared/ui`. Не собирать layout нативными div/span с Tailwind или inline-стилями. Для форм задавать `align="stretch"` и `max` явно: выравнивание Stack по умолчанию может центрировать поля. Стили фичи находятся в её SCSS-модуле; общая геометрия Dialog и базовый вид Switch остаются в shared.

Использовать семантические `--color-*`, `--radius-*`, `--shadow-*` из дизайн-системы. Не копировать старые hex/HSL fallback, яркую заливку primary на каждую карточку и локальные z-index. Мягкая глубина создаётся рамкой, тенью и различием поверхностей; основной цвет оставлять для активного состояния и главного действия. Focus у полей внутри скролла рисуется внутри рамки.

Геометрия оболочки и карточек уже реализована в ModalLayout. В SCSS фичи достаточно описать специфичную раскладку полей:

```scss
.fieldsRow { width: 100%; flex-wrap: wrap; gap: 16px; }
.field { flex: 1 1 200px; min-width: 0; }
@media (max-width: 640px) {
  .fieldsRow { flex-direction: column; align-items: stretch; }
  .field { flex: 1 1 auto; width: 100%; }
}
```

У flex/grid-полей обязательны `min-width: 0` и доступная ширина. Сложные повторяющиеся строки делать grid с сокращением колонок на узких экранах; составные контролы при необходимости выносить на полную ширину. Footer адаптируется средствами shared DialogFooter. Проверять длинные RU/EN-подписи, раскрытую секцию, ошибку и небольшую высоту viewport, а не только пустую desktop-форму.

### 10.7. Подсказки, ошибки и критерии проверки

- Все пользовательские названия, tooltip, примеры и ошибки имеют RU/EN-ключи. Пользовательские имена сущностей не переводятся. В UI-подсказках не использовать длинное тире.
- Для справки использовать `InfoTooltip` или `Tooltip`. На том же trigger не задавать HTML `title`, чтобы не появлялись две подсказки. Tooltip объясняет назначение, варианты и короткий пример; служебные детали не заменяют понятную подпись.
- Ошибки backend сопоставляются полю или id шага и локализуются. Открывается нужная вкладка, проблемное поле или шаг выделяется и доступен переход/фокус. Под полем показывается исправимое сообщение; общая ошибка сохранения имеет `role="alert"`. Не печатать в модалке сырой ответ API или список DTO-ошибок.
- При сохранении блокировать повторный запрос. При ошибке черновик сохраняется; пользователь может исправить значения и повторить. «Отмена» закрывает форму без mutation.
- Проверки новой модалки: стабильность оболочки при смене вкладок; сохранение черновика; клики и клавиатура Switch; сворачивание без потери значений; RU/EN; переход к ошибке; меню без случайного открытия карточки; отсутствие горизонтального скролла полей и видимость Save/Cancel на мобильном. Автоматические проверки состояния не заменяют визуальную проверку viewport.

**Боковые формы:** используйте `FormSheetContent` из `shared/ui/ModalLayout` вместе с `SheetHeader`, `ModalBody` и `SheetFooter`. Прокручивается только тело; подписи и кнопки остаются видимыми. Небольшие формы ограничиваются `max-height` и подстраиваются под содержимое. Полноценные редакторы используют `size="large"`. Пример: `features/callcenter/ui/ContactBookForm/ContactBookForm.tsx`.
