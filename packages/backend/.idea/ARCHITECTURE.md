### 🔴 Проверка актуальности перед установкой

Перед `npm install <package>` **всегда** выполнять:

```bash
# 1. Проверить последнюю стабильную версию и dist-tags
npm show <package> version dist-tags

# 2. Проверить peerDependencies на совместимость
npm show <package>@latest peerDependencies

# 3. Проверить критические breaking changes (смотреть CHANGELOG или README)
# Особенно если мажорная версия > той что ты знаешь
```

### Когда проверять особенно тщательно

- **Мажорная версия изменилась** (например, v9 → v10) — всегда читать CHANGELOG
- **Пакет активно развивается** (MCP SDK, AI-библиотеки) — могут быть breaking changes даже в минорных версиях
- **Транспортный/протокольный слой** (`@modelcontextprotocol/sdk`, `socket.io`) — API меняется часто

## 1. Мульти-Тенантность и Изоляция Данных
Система спроектирована как **Multi-Tenant SaaS**. Это означает, что несколько организаций (тенантов) могут существовать в одной базе данных (`krasterisk`) без пересечения их данных.

### Принцип `vpbx_user_uid`
Ключевым атрибутом изоляции является поле `vpbx_user_uid`.
- **В БД:** Каждая сущность (пользователь, роль, sip-клиент, номер) имеет колонку `vpbx_user_uid` со значением ID "владельца тенанта" (организации).
- **На уровне Контроллера:** Все контроллеры (защищенные авторизацией) извлекают `vpbx_user_uid` из контекста запроса `@Req() req` (`req.user.vpbx_user_uid`). Слой контроллера не доверяет идентификаторам тенанта из `Query` или `Body`.
- **На уровне Сервиса:** Бизнес-логика (findAll, update, delete) **всегда** требует передачи `vpbx_user_uid` вторым или обязательным параметром. Внутри сервиса автоматически формируется фильтр SQL-запроса: `where: { vpbx_user_uid }`.

**Итог:** Залогиненный пользователь видит и имеет право изменять только те записи, которые принадлежат его тенанту (`vpbx_user_uid`).

## 2. Аутентификация и Защита (Auth & RBAC)

### Access и Refresh Токены (Multi-Session)
Бэкенд использует продвинутую JWT систему:
- **`accessToken`** (живет короткое время, например, `15m`): используется для всех авторизованных запросов. Хранится в памяти или `sessionStorage` на Frontend'е.
- **`refreshToken`** (живет долго, например, `7d`): используется для получения нового `accessToken` без ввода пароля. Возвращается при входе.
- **Мульти-Сессии (`user_sessions`):** `refreshToken` сохраняется в таблицу `user_sessions` (каждый вход с браузера/телефона создает отдельную сессию). Если пользователь заходит с нового устройства, старая сессия не сгорает.
- **Rotation (Вращение токенов):** При обращении к `POST /auth/refresh` со старым Refresh-токеном, бэкенд верифицирует его, сбрасывает старую запись в БД, и возвращает новую безопасную пару `accessToken` + `refreshToken`.

### RBAC - Ролевая модель (`RolesGuard`)
Система управления доступом на основе уровней:
- Создан кастомный декоратор `@Roles(UserLevel.ADMIN)` (`src/modules/auth/roles.decorator.ts`).
- Создан `RolesGuard` (`src/modules/auth/roles.guard.ts`).
- Защита эндпоинтов осуществляется путем наложения ограничения прямо на контроллер или метод. Гуард автоматически читает `user.level` из JWT-контекста и пропускает или блокирует запрос.

## 3. Модуль Аудита / Логирование
Все активные, деструктивные или критические изменения логируются.

### `action_logs`
- **БД Отражение:** Таблица `action_logs`, модель `ActionLog` (`logger/action-log.model.ts`).
- **Модуль и Сервис:** `LoggerService` предоставляет метод `logAction`.
- **Как работает:** Внедряется (`inject`) в любой контроллер/сервис. Вызывается после успешного завершения CRUD операций, чтобы записать: *кто (userId), что сделал (action), над какой сущностью (entityType: user, peer и др.), и в каком тенанте (vpbx_user_uid).*

## 4. Интеграция с внешними сервисами

Для оповещения пользователей и администраторов реализованы два модуля-коннектора:

### Mailer (`MailerModule`)
Использует библиотеку `nodemailer` (подключение через SMTP, задаваемое в `.env`: `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`).
- **Как работает:** `MailerService` отправляет HTML-письма клиентам (напр. `sendActivationMail`).
- **Интеграция:** Используется `AuthService` для отправки 6-значных кодов активации при регистрации (`POST /auth/register`). Пользователь должен затем подтвердить код через `POST /auth/activation`.

### Telegram (`TelegramModule`)
Использует `node-telegram-bot-api` (`TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`).
- **Как работает:** Инициализируется как фоновый API клиент; может рассылать сообщения по заданным `chatId`.
- **Интеграция:** Глубоко встроен в `LoggerService`. В случае важных системных событий (логин, регистрация, удаление) бот автоматически дублирует сообщения в администраторский чат, обеспечивая моментальный оперативный контроль за состоянием PBX.

## 5. Модуль Endpoints (PJSIP) и Телефония

Модуль управляет внутренними абонентами (Extensions/Peers) через архитектуру **Asterisk PJSIP Realtime** (Alembic/ODBC).

### Прямая интеграция с БД (Realtime)
Вместо генерации статических конфигурационных файлов (типа `pjsip.conf`), бэкенд пишет конфигурацию напрямую в SQL-таблицы Asterisk Realtime:
- **`ps_endpoints`** — базовые настройки, транспорт, кодеки, контексты, ACL (`permit`/`deny`).
- **`ps_auths`** — логины и пароли абонентов (связаны с endpoint через `auth=`).
- **`ps_aors`** — настройки регистрации (max_contacts) и раутинг вызовов.
- Опционально читается статус регистрации из **`ps_contacts`**.

Asterisk настроен на автоматическое чтение данных из БД (sorcery), поэтому при сохранении DTO абонента никаких дополнительных `reload` команд или `apply` на стороне Asterisk делать не нужно. Данные подхватываются прозрачно и моментально.

### Изоляция абонентов (Tenancy) в телефонии
В отличие от большинства стандартных таблиц платформы, Asterisk Realtime не знает про поле `vpbx_user_uid` напрямую (схема таблиц жёстко задана Астериском). Поэтому безопасность и изоляция достигается на логическом уровне:
1. **Контексты маршрутизации (Dialplan):** Суффикс арендатора неявно привязывается к контексту (например, `sip-out12`, где `12` — это `vpbxUserUid`).
2. **Перехват вызовов (Pickup Groups & Call Groups):** Asterisk имеет глобальное пространство имён для групп перехвата. Чтобы тенанты не могли перехватывать вызовы чужих компаний, при создании группы слаг (slug) аппаратно "неймспейсится" идентификатором арендатора.
   *Пример:* Тенант создает группу «Отдел продаж». Имя генерирует слаг `prodazhi`. В Asterisk уходит: `t{vpbxUserUid}_prodazhi`. Это полностью исключает коллизии между арендаторами.

### Расширенные параметры (Advanced Builder Pattern)
Стандарт PJSIP поддерживает более 100 различных параметров (timers, fax, session timers, media options). Создавать в коде и TypeScript DTO все эти 100+ полей - антипаттерн, приводящий к раздуванию кода.
- Реализован паттерн **Dynamic Settings Builder**.
- Любые расширенные ключи (`rtp_timeout`, `fax_detect`, `direct_media`) динамически добавляются пользователем через UI.
- На фронтенде собирается JSON объект в поле `advanced`.
- На бэкенде эти ключи безопасно извлекаются и с помощью спреда (spread `...advancedState`) аккуратно раскатываются по столбцам таблицы `ps_endpoints` при `create/update`.

### Фоновая обработка (Bulk Operations)
Создание или удаление большого массива абонентов (сотни штук) - ресурсоёмкий процесс для БД, так как затрагивает каскадно таблицы `ps_endpoints`, `ps_auths`, `ps_aors`.
Вместо удержания (blocking) HTTP-запроса используется асинхронный паттерн с **Background Jobs**:
1. Клиент забрасывает профили на `/endpoints/bulk`.
2. Бэкенд генерирует задачу и моментально отдаёт `jobId` со статусом `pending`.
3. Отдельный In-Memory Worker в цикле обрабатывает создание (batching), логируя прогресс (processed/total).
4. Клиент опрашивает `/bulk/status/:jobId` (`Long Polling` / интервалы), отображая прогресс-бар в реальном времени. В конце обновляет таблицу.

## 6. MCP Server (AI Tool Protocol)

Модуль `McpModule` реализует **Model Context Protocol Server** для интеграции с AI-агентами (aiPBX и другими клиентами).

### Транспорт: Streamable HTTP (актуальный стандарт MCP SDK 1.x)

```
POST   /api/mcp  — JSON-RPC запросы (инициализация + tool calls)
GET    /api/mcp  — SSE-поток уведомлений (опционально)
DELETE /api/mcp  — закрыть сессию
GET    /api/mcp/sessions — debug: активные сессии
```

Единый endpoint `/api/mcp` обслуживает весь протокол. `SessionId` передаётся в заголовке `Mcp-Session-Id`. Первый POST без заголовка создаёт сессию.

> **Примечание:** `SSEServerTransport` (legacy GET+POST раздельно) — deprecated в SDK 1.x. Используем `StreamableHTTPServerTransport`.

Каждое подключение создаёт изолированный `McpServer` с инструментами конкретного тенанта. Тенант идентифицируется через JWT или Service Token (`X-Vpbx-User-Uid` header).

### Аутентификация

Используется `JwtOrServiceTokenGuard`:
- **JWT** — обычный пользователь браузера
- **Service Token** — `Authorization: Bearer <KRASTERISK_SERVICE_TOKEN>` + `X-Vpbx-User-Uid: <uid>` — для aiPBX и других внешних агентов

### 🔴 ОБЯЗАТЕЛЬНОЕ ПРАВИЛО: Новые сущности → Новые MCP инструменты

> **При создании любой новой сущности АТС, с которой могут работать пользователи (абоненты, транки, IVR, очереди, контексты маршрутизации, группы перехвата, голосовые роботы и т.д.) — ОБЯЗАТЕЛЬНО добавить соответствующий инструмент(ы) в `McpToolsService`.**

**Файл:** `src/modules/mcp/mcp-tools.service.ts`  
**Метод:** `registerAll(server, vpbxUserUid)`

Шаблон для нового инструмента:
```typescript
private registerMyNewEntity(server: McpServer, uid: number) {
    server.registerTool(
        'create_my_entity',      // snake_case имя инструмента
        {
            title: 'Человекочитаемое название',
            description: 'Подробное описание: когда использовать, что делает, важные ограничения.',
            inputSchema: {
                name: z.string().describe('Описание параметра для LLM'),
                // ... остальные поля с z.string(), z.number(), z.enum(), z.array()
            },
        },
        async (args) => {
            const result = await this.myEntityService.create(args, uid);
            return {
                content: [{ type: 'text' as const, text: JSON.stringify(result, null, 2) }],
            };
        },
    );
}
```

Минимальный набор инструментов для новой сущности:
- `create_{entity}` — создание
- `delete_{entity}` — удаление  
- `update_{entity}` — обновление (если нужно)

Необязательно, но желательно — документировать в `registerAll()` общее количество зарегистрированных инструментов.

## 8. Версии Asterisk

Проект **не привязан к одной версии** Asterisk. Решения по приложениям и опциям опираются на диапазон поддержки и известные пробелы, а не на жёсткий пин («должно быть ≥16, иначе стоп»).

### Наблюдаемый прод (M1, 2026-08-20)

Целевой PBX `ipbx.krasterisk.ru`:

```
Asterisk certified-22.8-cert2 built by root @ ipbx.krasterisk.ru on a x86_64 running Linux on 2026-04-11 06:47:19 UTC
```

Это **пример боевой установки**, не единственная поддерживаемая линия.

### Политика диапазона

| Линия | Статус | Как относиться |
|---|---|---|
| **22+** (включая Certified 22) | Предпочтительная | Документация приложений фазы 12 (`Playback`/`noanswer`, `ControlPlayback`, `Progress()`, `Record()` + `k`, `hangup_handler_push`, `QUEUE_PRIO`, `QUEUESTATUS`) сверена с Asterisk 22 |
| **16** | Возможна | Те же приложения в целом есть на LTS 16; перед опорой на конкретную опцию (`Record()` `k`, `Playback` `noanswer`) проверить на целевом хосте |
| **11** | Возможна, больше пробелов | Hangup handlers есть с 11; слой этого бэкенда — **PJSIP Realtime** (см. §5), тогда как 11-era по умолчанию `chan_sip`. Часть поздних опций `Record`/`Playback`/`Queue`/`Dial` может отсутствовать. 11 — best-effort: прогонять нужные приложения на хосте, не считать отсутствие опции блокером всей платформы |

### Известные пробелы (не стоп-гейт)

- Генератор dialplan фазы 12 писался и тестировался по семантике **Asterisk 22**. На 16/11 расхождение опции — известное ограничение хоста, а не дефект генератора, пока приложение на этой линии отсутствует или ведёт себя иначе.
- `Progress()` + early media (D-52) зависит ещё и от SIP-провайдера, не только от версии Asterisk.
- Голосовая почта (`Record()` + `k` + `hangup_handler_push`, D-54…D-59) вынесена в Phase 12b — проверять опцию `k` на 11/16 там, не здесь.

При добавлении нового Asterisk-приложения или опции: документировать, на какой линии оно проверено, и не превращать предпочтение 22+ в жёсткий минимум без явного решения.

## 9. Боевые факты фазы 12 (M9, M12)

Зафиксировано 2026-08-20 с `ipbx.krasterisk.ru`. Не выдумывать другие значения.

### M9 — путь записей

Прод `.env`: `RECORDS_BASE_PATH=/usr/records`. Совпадает с унифицированной константой генератора (`/usr/records`). **Ретаргет не нужен, файлы записей не переносить.**

Строка `system_settings.records_base_path` в этой проверке не читалась — источник факта: `.env` на проде. Приоритет в коде: таблица `system_settings` > `.env` > дефолт `/usr/records`.

### M12 — осиротевшие PHP (`usr/scripts`)

Baseline на текущем PBX (один замер, деплоя генератора фазы 12 на этот хост ещё может не быть):

```
grep -c 'usr/scripts' /var/log/asterisk/full
→ 0
```

Ноль — сейчас в `full` нет обращений к `/usr/scripts`. **Полный гейт M12** (пара до/после тестовых звонков notify/TTS *после* деплоя фазы) ещё не закрыт: после-счётчик не снимали. Повторить после выкладки генератора.
